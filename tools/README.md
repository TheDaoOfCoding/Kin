# tools

Scripts for soak tests and benchmarks. Measured results go in `docs/results/`, not here.

## e2e-1-1.ps1, e2e-1-2.ps1, e2e-1-3.ps1, e2e-1-4.ps1

End-to-end checks on the emulator with the real `Kin.exe` (developer mode, loopback only, throwaway data dir and received folder) and the real debug APK. `e2e-1-1.ps1` is the base (emulator, install, pairing, ping, teardown); `e2e-1-2.ps1` and `e2e-1-3.ps1` run it with `-Milestone 1.2` / `1.3` and add the scenarios of `e2e-1-2-scenarios.ps1` (text, links, clipboard) and `e2e-1-3-scenarios.ps1` (files both ways, big file with a Wi-Fi drop, cancel, `disk_full`, `source_changed`, tricky file names, the text rules). They use the real PC clipboard: every format is saved first and put back at the end. Exit code 0 only if every check passed. The screenshots of a run go to `docs/results/phase-1-<n>-integration-screens` (one folder per milestone, so a run of 1.3 doesn't touch the 1.2 pictures; `-ScreenshotDir` overrides it). Run them from `powershell -ExecutionPolicy Bypass -File ...`; to capture the output from a tool that reads a pipe, send it to a file (`Start-Process ... -RedirectStandardOutput`), because the adb server a run starts holds the pipe open. `e2e-1-4.ps1` (`-Milestone 1.4`, scenarios in `e2e-1-4-scenarios.ps1`) adds the queue on both sides (Wi-Fi off / PC stopped / restarts), cancel, expiry (`--dev-clock-offset`, `EXPIRE --el ahead`), no-ack re-queue (a frozen receiver: `NtSuspendProcess` on Kin.exe, `SIGSTOP` on the phone app), the PC's stored `cancel` reaching a phone that was away and the 404 path (the PC forgets an upload after 24 hours, `--dev-clock-offset`; user Retry), sensitive text and the automatic clipboard offline, history parity, a notification burst (`-BurstTexts`, `-BurstFiles`; 60 and 15 for the full check), and the logs and Export logs on both sides; `-Only SX` is a probe that is not in a default run. A scenario that dies is recorded as a failed check and the run goes on (1.5: after it, Kin is always restarted **without** `--dev-clock-offset`, so a scenario that died during S5 or S7b cannot leave the later ones on a shifted clock). **They run beside the user's installed Kin** (v0.1.1: [kin-dev.ps1](#kin-devps1); the old "Kin.exe is already running: quit it first" refusals are gone, only a Kin on the run's own data directory is in the way). All the scripts run `Kin.exe` with `COMPUTERNAME=DESK-PC` (so no picture shows the real name of the computer) and refuse a `Kin.exe` that is not from `tauri build` (`cargo test --release` replaces it with a dev-server build): use `-Build`. Usage and the results: [phase-1-3-integration.md](../docs/results/phase-1-3-integration.md), [phase-1-4-integration.md](../docs/results/phase-1-4-integration.md).

**Pictures.** The e2e scripts (and `desktop\capture-windows.ps1`) never overwrite the tracked pictures of `docs\results`: they write to an ignored folder, `%LOCALAPPDATA%\Temp\kin-e2e-screens\phase-1-<n>` (`kin-capture-windows` for the windows), and say where. Pass **`-UpdateScreens`** to write the tracked folder of the milestone, or `-ScreenshotDir <folder>` for your own (a folder inside `docs\results` is redirected to the temp one unless `-UpdateScreens` is given).

**Steadier steps (1.4 review).** `e2e-1-4.ps1` S13's phone "Export logs" first brings the app to its Home tab (`Open-PhoneHomeTab`: it leaves the Debug screen with its Back button, the setup screen with BACK, then taps the first tab), scrolls until "Debug" is on screen and looks at the exports folder for the new zip instead of waiting a fixed time. `e2e-1-2.ps1`'s "notification action" (the tap on the service notification's "Send clipboard" button) starts from a quiet home screen, waits for the shade by looking, expands the row if it is collapsed and tries five times.

## kin-lock.ps1

One lock for every script that uses something only one script can use at a time: the real clipboard, the single-instance slot of `Kin.exe` and the emulator (`emulator-5554`). The e2e scripts, `android\tools\release-smoke.ps1`, `desktop\capture-windows.ps1`, `desktop\measure-idle.ps1` and the `desktop\check-*.ps1` scripts call `Enter-KinLock '<name>'` at the top. A second script says who has it ("Another Kin script is running: 'e2e-1-4' (process 1234, started ...)") and stops, instead of wrecking the first one's run. The lock is the file `%LOCALAPPDATA%\Temp\kin-scripts.lock`, held open by the running script: Windows drops it when the process ends, however it ends, so a lock left by a crashed or killed script is never in the way. A script that runs another one in the same process, or a child process, is not blocked by its own lock. Run the scripts as `powershell -File` (a process each); if you dot-source one in a window that stays open, call `Exit-KinLock` afterwards.

## kin-dev.ps1

Runs a test Kin.exe **beside the user's installed Kin** (v0.1.1), without ever touching the installed one. Every script that starts Kin dot-sources it after `kin-lock.ps1`. The app side is in [desktop/README.md](../desktop/README.md#a-test-kin-beside-the-installed-one): a Kin with its own `--data-dir` is a separate instance (own single-instance lock, toast identity, port, web view data; no mDNS, no default hotkey; its clipboard writes carry the opt-out format that an installed Kin skips).

```powershell
. (Join-Path $PSScriptRoot '..\tools\kin-dev.ps1')      # after kin-lock.ps1 (`desktop\` scripts: '..\tools\kin-dev.ps1', `android\tools\`: '..\..\tools\kin-dev.ps1')
Set-KinDev -Exe $Kin -DataDir $Data                      # once: the throwaway data directory (it may not be %APPDATA%\Kin) and the test build (not Program Files)
$p = Start-DevKin $KinArgs                               # refuses unless the arguments have --data-dir <ours> and --dev-bind; also refuses if a Kin is already on that directory
Invoke-Kin --send-clipboard                              # Kin.exe --data-dir <ours> --send-clipboard
Get-DevKinProcesses                                      # the processes of our instance: same program file AND --data-dir; never the installed Kin, never another script's
Stop-DevKin 10                                           # --quit to our data directory, wait, and if it hangs Stop-Process -Id of OUR processes only
Stop-OwnProcess $phoneProc                               # a process this script started (fake phone), by ID, after checking it is still that process
Set-QuietClipboardText 'text'                            # (clipboard-backup.ps1) real clipboard text that an installed Kin skips. Never Set-Clipboard in a test
Remove-DevDataDir $Data                                  # delete a throwaway directory, retrying while a web view process still holds it
Assert-NoGameRunning                                     # before anything that shows a window
```

**The rules.** (1) The installed Kin is never started, stopped, asked or killed from a script, and a script whose data directory is `%APPDATA%\Kin` stops with an error. (2) Every command to Kin carries `--data-dir`, which is what routes it to the test Kin; `Invoke-Kin` adds it, and `Kin.exe` itself refuses a launch with no data directory when the running Kin is another program file. (3) **Nothing is killed by name.** A process is ours if its program file is the one we were given and its command line names our data directory, and a script stops only such a process, by its ID. (4) "Another Kin is running" is refused only for a Kin on **our** data directory (and by the lock of `kin-lock.ps1`); the other Kin.exe processes are listed in a note and left alone. (5) Clipboard text is written with `Set-QuietClipboardText` (or by the test Kin: `--dev-set-clipboard`, which marks it itself), and `Restore-Clipboard` adds the same mark to what it puts back (`-NoMark` to leave the formats exactly as they were), so an installed Kin with its automatic sync on sends none of it to the user's phone: it skips content with `ExcludeClipboardContentFromMonitorProcessing` (checked in the 0.1.0 code, `clipboard::exclusion` and `process_clipboard_change`, and in the installed Kin's own log: "clipboard changed: not sent, the source app marked it ..."). The one thing that can't be made safe is **pressing the hotkey** (the installed Kin owns `Ctrl+Alt+Shift+K`): `check-1-2.ps1` no longer does, and `--send-clipboard` runs the same code. `check-dragdrop.ps1` moves the mouse and runs only with `-AllowMouse`.

**The game guard (`Assert-NoGameRunning`, narrowed 2026-10-17).** The rule is "no disturbance while the user PLAYS", so it stops a script only when (a) a game is running: a known game process (`FortniteClient-Win64-Shipping*`, `FortniteLauncher`, `FortniteBootstrapper`, any `EasyAntiCheat*` process except the idle `EasyAntiCheat_EOS` service, `BEService`, `GameOverlayUI`, a few more; or a process that runs from a game folder such as `steamapps\common`, `Epic Games\<game>`, `Riot Games\VALORANT`, `XboxGames`; extend `$names` / `$paths` in `Get-RunningGames`), or (b) Windows itself reports a game, full-screen or presentation state, `SHQueryUserNotificationState` = `QUNS_BUSY`, `QUNS_RUNNING_D3D_FULL_SCREEN` or `QUNS_PRESENTATION_MODE` (`Get-UserNotificationState`; this covers any game, and also a full-screen video). **Idle launchers and services do not block**: `EpicGamesLauncher`, `EpicWebHelper`, `EpicOnlineServicesUserHelper`, `EOSOverlayRenderer`, the Steam / Riot clients and the `EasyAntiCheat_EOS` service (which stays up for hours after a game closes). It prints what it saw ("Game guard: no game running (Windows notification state: ...)") or throws with the process names / the state. It is cheap: the scripts call it at the start of each visible step.

**`desktop\check-dev-beside-installed.ps1`** is the proof (31 checks): two test Kins beside the installed one, commands routed by data directory, the marked clipboard text (the installed Kin's log is read, never written), `--quit` reaching only its own instance, and the installed Kin unchanged at the end (process ID, start time, command line, port 47821, Run value, SendTo shortcut).

## net-check.ts

Phase 0, step 5 in [phase-0-setup.md](../docs/phases/phase-0-setup.md): checks that a phone on Wi-Fi can reach this PC.

```
bun tools/net-check.ts
bun tools/net-check.ts --minutes 30
```

- It serves "Kin Relay network check OK" and the PC's name on port 47821, on all interfaces.
- On start it prints a ready-to-type URL for each LAN address, and marks the one on the default route when there is more than one. It skips loopback, link-local and virtual adapters (Hyper-V/WSL, VirtualBox, VMware, Docker, VPNs), and lists what it skipped. It never skips the address on the default route, even if the adapter's name looks virtual, because a Hyper-V external switch (`vEthernet (...)`) can be the real LAN.
- It logs every request with the time and the remote address. Browsers also ask for `/favicon.ico`, so expect two lines per page load.
- It stops on Ctrl+C, or after 10 minutes. Change that with `--minutes N`.

How to use it:

1. Run it. The first time, Windows shows a firewall prompt. Allow it, and note whether it says Private or Public (this feeds D12).
2. On the phone, turn on Wi-Fi and turn off mobile data, on the same network as the PC. Open the printed URL in the browser.
3. You should see "Kin Relay network check OK", and a log line with the phone's address.

If the page doesn't load:

- The phone or the PC is on a guest network.
- AP or client isolation is on in the router, so Wi-Fi devices can't talk to each other.
- The firewall prompt was dismissed or closed. Windows then blocks the program silently, and running it again won't ask again. Allow `bun.exe` for the network (Private and Public) in Windows Security → Firewall & network protection → Allow an app through firewall.
- You used the wrong address. Try the other URLs that were printed.

## Removing the firewall rule afterwards

When you allow the Windows firewall prompt, Windows creates inbound rules for `bun.exe` (usually named "bun" or "bun.exe", one for TCP and one for UDP). They stay after the test. Removing them needs admin.

- **Settings route:** Windows Defender Firewall → Advanced settings → Inbound Rules → select the "bun" entries → Delete.
- **PowerShell route:** open PowerShell as administrator and run:

  ```
  Get-NetFirewallApplicationFilter | Where-Object { $_.Program -like '*\bun.exe' } | Get-NetFirewallRule | Remove-NetFirewallRule
  ```

  To see what it will remove first, run the same line with `| Select-Object DisplayName, Direction, Profile` instead of `| Remove-NetFirewallRule`.

This removes every inbound rule for `bun.exe`, not only this test's. Windows asks again the next time a Bun program listens on the network.
