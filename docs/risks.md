# Risks

| # | Risk | Likelihood | Impact | What we do about it | When we find out |
|---|---|---|---|---|---|
| R1 | OEMs (Xiaomi, Oppo, Vivo, Samsung) kill the background service, so PC → phone stops arriving | High | High | Battery-exemption onboarding with OEM-specific steps (built in 1.4, on the emulator only: no real OEM phone yet), plus the queue (1.4: what the phone sends waits and goes out after the next `hello`). If needed, the FCM wake-up push moves into Phase 1 | 1.1 soak test |
| R2 | The network blocks devices from talking to each other (guest Wi-Fi, campus networks, AP isolation) | Medium | High | Check your own network in Phase 0. Show a clear message instead of failing silently. The bridge arrives in Phase 2 | Phase 0, then the friends test |
| R3 | The Windows firewall blocks connections, especially on networks marked "Public" | Medium | High | The installer adds the rule (D12). The debug screen shows the current network profile | 1.5 |
| R4 | The Play Store rejects or delays the foreground service | Medium | Medium | Install the APK directly in the MVP. Prepare the declaration and demo video in Phase 2 | Phase 2 |
| R5 | Access to shared files expires before a queued file is sent | Medium | Medium | Pass file access on to the service. Copy small files to the cache. Ask the user to share large ones again | 1.3. **Checked in 1.3 on the emulator** with a second app and a provider that is not exported: the grant on the service outlives the share activity and the sending app, and without it access is lost within seconds. Reading through a normal (stable) provider reference let Android kill Kin when the sending app died, so shared files are read through an unstable client ([android.md](android.md)) |
| R6 | Agent-written Android and Windows code drifts from the protocol, or from each other | Medium | High | Shared protocol test vectors in `protocol/`, used by both apps' tests. Emulator-based integration tests every milestone. An Opus review before every commit | Every milestone |
| R7 | Appending to a file for resume behaves differently on some phones | Low | Medium | Fall back to writing in the app's folder and moving the file when it's complete | 1.3. **Checked in 1.3 on Android 10 and 17 emulators:** appending works (`"wa"`, and a read-write descriptor positioned at the end, which is what the app uses), so no fallback is built. Not yet checked on a real phone with an OEM MediaStore |
| R8 | The PC's open port is reachable on public Wi-Fi | Low | Medium | Every request is authenticated, TLS is required, and pairing attempts are rate-limited. A setting can limit listening to Private networks | 1.5 |
| R9 | Clipboard sync leaks secrets such as passwords | Medium | Medium | Skip password-manager content, provide an on/off toggle, and keep clipboard sync out of history | 1.2 |
| R10 | Toast buttons don't work for an app that isn't packaged | Low | Low | Click-only toasts | 1.3 |
| R11 | The Android Keystore key can't be used for the TLS client certificate on some phones | Low | Medium | Resolved by D15: the identity key is a software key, encrypted with a Keystore-held AES-GCM key. A hardware-backed key can be an upgrade later | 1.1 |
| R12 | On Android 17 (API 37) the "Nearby devices" permission (`ACCESS_LOCAL_NETWORK`) is denied, never asked, or revoked later, so every connection to the PC just times out with no error that says why | Medium | High | Onboarding explains it and asks for it when the app opens and before a pairing. While it is missing the phone shows a clear "Nearby devices permission needed" state (Home, the service notification, and the "PC not reachable" message of a send) with a button to the app settings, and tries again as soon as it is granted. It is checked again when the app opens and while connection attempts fail, so a revoke later is noticed | 1.1 (found on the emulator), phone tests in 1.5 |
| R13 | Any foreground app can silently send text to the PC through the exported share and "Send to PC" (`PROCESS_TEXT`) activities, as with any share target. Android doesn't say which app started them, and there is no confirmation step | Medium | Low | The PC treats everything from the phone as untrusted: a link is never opened on arrival, only when the user clicks it, and only if it is `http` or `https`. Text from the phone is never run or interpreted, and files are saved under cleaned names in one folder. The share activities stay exported on purpose, because that is what makes Kin appear in the share sheet | 1.3 (found in the 1.2 review) |
| R14 | The Play Store restricts `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`: a request for the one-tap exemption dialog needs a Play Console declaration, and the review may refuse it | Medium | Medium | Kin doesn't use it. The setup opens the system's battery optimisation list (`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, no permission, no declaration) and the user sets Kin to "Not optimised". Revisit with the Phase 2 Play submission, together with the foreground service declaration (R4) | 1.4 (decided); Phase 2 |
| R15 | The OEM settings activities that the setup opens (Xiaomi autostart, Samsung, ColorOS, Vivo, Huawei) are not public APIs and change between versions, so a step can open nothing | High | Low | One table (`setup/OemTable.kt`) lists them with short text steps; the first activity that exists is opened, otherwise Kin's own settings page, and the steps stay on screen. Check the table against the real phones in the friends test | 1.5 |
| R16 | The release signing key (`%USERPROFILE%\.kinrelay\release.jks` and `signing.properties`) is lost or leaked. Lost: no update can install over an existing install (Android refuses a different signature), and friends would have to uninstall, which deletes their pairing and queue. Leaked: someone could publish an update that installs over Kin | Low | High | The key lives outside the repo; `android/tools/make-keystore.ps1` makes it with a random password and never overwrites one. Back up the whole `.kinrelay` folder somewhere safe and private (a password manager's file storage, an encrypted drive). The certificate SHA-256 is recorded in `docs/results/phase-1-5-android.md`. For Play (Phase 2) use Play App Signing, so Google holds the app signing key and this one becomes an upload key that can be reset | 1.5 |
| R17 | The ZXing scanner (D16) reads QR codes worse than Google's on some phones: cheap cameras, no autofocus, glare, a small code on a far screen | Medium | Low | The pasted link and the deep link always work, and the camera is optional. The decoder is tested on generated codes (rotated, inverted, low contrast, small, padded rows) and the scan screen opened on the emulators, but **no real code was scanned by a real camera yet**: check on the friends' phones, and if it is poor, bigger codes on the PC or a tap-to-focus are the first fixes | 1.5 (friends test) |
