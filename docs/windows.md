# Windows app

## Basics

- **Tauri v2.** The Rust backend does all the real work. The TypeScript UI is only for windows: pairing, sending, history, settings and debug.
- Windows 10 and 11, x64. ARM64 comes later.

## Rust crates (planned)

| Job | Crate |
|---|---|
| Async runtime | `tokio` |
| HTTPS and WebSocket server | `axum` (with its WebSocket support), `rustls`, `tokio-rustls` |
| Certificates | `rcgen` |
| Encrypting the private key | DPAPI through the `windows` crate |
| mDNS advertising | `mdns-sd` |
| Database | `rusqlite` (bundled SQLite) |
| Clipboard read and write | The Win32 clipboard API through the `windows` crate: `AddClipboardFormatListener` on a hidden message-only window for the change events, `CF_UNICODETEXT` for the text, and `EnumClipboardFormats` for the opt-out formats. (`arboard` was in this plan. It would only have covered the text, and the listener and the format checks need Win32 anyway, so it was left out: one dependency fewer.) |
| QR rendering | `qrcode` (rendered as SVG for the UI) |
| Decoding a received image | The Windows Imaging Component (WIC) through the `windows` crate. No image crate is added (see [Images](#images-and-the-clipboard)) |
| The file dialog and the free space | `IFileOpenDialog` and `GetDiskFreeSpaceExW`, also through the `windows` crate |
| Tray, hotkey, notifications, autostart, single instance | Tauri's built-in tray, plus the `global-shortcut`, `notification` and `single-instance` plugins; "Start with Windows" is a small writer of the current user's `Run` key of our own (`autostart.rs`: the plugin could write the machine-wide key when elevated) |
| JSON | `serde`, `serde_json` |

Handlers need to know which device made each request, but axum doesn't pass the client certificate to them by default. That needs a custom TLS accept loop that attaches the peer certificate to every request. It's a known pattern, and it gets built in 1.1. Two rules from [protocol.md](protocol.md#transport) apply to it. The client certificate is mandatory in the handshake, and the custom verifier accepts any chain but must still verify the TLS 1.3 signature (`verify_tls13_signature`), so a replayed public certificate can't pass. And axum's default `Json` extractor answers `415`/`422` in plain text, so the app uses its own extractor that returns `400 bad_request` JSON (see [protocol/README.md](../protocol/README.md#notes-for-the-implementers)).

## Process model

- One process. It starts when you sign in and lives in the tray.
- Windows are created when opened and **destroyed** when closed, not just hidden. An open WebView2 costs tens of MB, and destroying it keeps idle memory low.
- Single instance: a second launch (for example from "Send to") passes its arguments to the running instance and exits. **The instance is its data directory (v0.1.1):** the installed Kin's own `%APPDATA%\Kin` is *the* instance, and a Kin started with another `--data-dir` is a separate one that runs beside it, with its own single-instance lock, toast identity, port and web view data, and no mDNS, no default hotkey and a clipboard it marks so the installed Kin skips it. A launch with no data directory never hands its command line to a running Kin that is another program file. The rules and how to run a test Kin beside the installed one: [desktop/README.md](../desktop/README.md#a-test-kin-beside-the-installed-one).

## Tray

- The icon shows whether the phone is connected (a green dot), away (amber) or not paired (no dot). The tooltip says the same, with the progress of a transfer ("Kin: Pixel 8 connected, sending 45%").
- **The status line** (the first, greyed line of the menu): "Phone connected: Pixel 8", or when the phone is away **"Phone offline – last seen 14:32"** (the time in the user's own time zone: `14:32` today, `yesterday 14:32`, `Mon 14:32` within a week, `12 Oct 14:32` before that; "Phone offline: Pixel 8" if it was never seen). **" · 2 queued"** is added while sends wait in the queue. The tooltip has it too.
- **While a phone's media is shown** (2B.3, [Media controls](#media-controls-2b3)) the tooltip adds ", media playing" or ", media paused" (never the title), and the menu gets three items under the status line: **Play/Pause phone media**, **Next**, **Previous**. They leave the menu when the phone's session goes.
- **Left-click** opens the drop window. Windows doesn't support dropping files onto a tray icon, so this window is the drop target. **Shift + left-click** opens the debug window (it is also a button in Settings).
- **Menu:** status line, Send files…, Send clipboard to phone, Pair new phone, Open received folder, History, Settings, Quit. (What 1.3 had besides — Ping phone, the clipboard-sync check item and Open log folder — is gone from the menu: `--ping` is on the command line and a button of the debug window, the sync switch is in Settings, and the logs are exported from the debug window.)

## Sending to the phone

- **Drop window:** the tray's left click opens it (`Kin.exe --drop` does the same). Drag files from Explorer onto it, or click it (or the tray's "Send files…") to choose files in the Windows file dialog. It also shows what is going on: one row per transfer with a progress bar, the speed, and a **Cancel** button, and the last few finished ones. The window is destroyed when it is closed. The tray's tooltip follows the numbers too ("Kin: Pixel 8 connected, sending 45%").
- **Explorer "Send to":** a shortcut in `%APPDATA%\Microsoft\Windows\SendTo` runs the app with `--send <paths>`; Explorer adds the selected files to its command line. The running instance gets them (the single-instance rule: a relative path is resolved against the folder the second launch was started in) and the second process exits. On Windows 11 it's under "Show more options". The modern menu entry comes in Phase 2. **Since 1.5 the app makes the shortcut itself** (`Kin.lnk`, listed as "Kin"), at every start, as the signed-in user: see [Install](#install) for why it isn't the installer. `desktop\make-sendto-shortcut.ps1` still makes it by hand (give it `-Folder` to try it in a test folder first, `-Remove` to take it out).
- **What gets sent.** The files are *offered* over the WebSocket (`offer`) and the phone downloads them from the PC, which reads them from where they are (nothing is copied, and a file that changes after the offer makes the phone's request fail with `source_changed`). An offer lasts 24 hours from the moment it was sent. **A phone that isn't connected gets it when it is back** (see [Queue](#queue)). More than 800 files go in several offers.
- **Folders are not sent in 1.3.** A dropped folder is skipped with a message ("A folder can't be sent yet"), and the files that were dropped with it are sent. Flattening a folder would lose its structure and clash names, and sending the structure needs a protocol addition.
- **Progress and cancel:** in the drop window, and `status.json`. Cancel sends a `cancel` message (reason `user`) and the partial files on the receiving side are dropped. **With several files going at once** (v0.1.1) the row of a transfer shows `3 of 50 files · 120 MB of 171 MB · 45 MB/s · 4 at once`: bytes and speed are those of the whole transfer, and `status.json` has `filesActive` next to `filesDone`.
- **Hotkey** (default `Ctrl+Alt+Shift+K`, configurable): sends the current clipboard text as a `text` message. The tray's "Send clipboard to phone" and `kin.exe --send-clipboard` do the same. See [Hotkey](#hotkey). Text goes out with **LF line ends** and, if it is **over 128 KiB**, as a `Text.txt` file through the same offer path (a temporary file of ours in `outgoing\`, removed when the phone has it or the offer expires).
- **Automatic clipboard sync** (on by default, can be turned off): each clipboard change sends a `clipboard` message.
  - Debounced by 300 ms.
  - Text only in the MVP.
  - **Skips password-manager content.** That means content carrying any of the formats apps use to opt out: `ExcludeClipboardContentFromMonitorProcessing`, or `CanIncludeInClipboardHistory` / `CanUploadToCloudClipboard` set to 0.
  - Over 128 KiB: not sent, and `status.json` says `too_large`.
  - **Loop prevention:** remember a hash of the text last set from the phone, and ignore the change event it causes. The hash is of the **wire form** (LF line ends), so the CRLF text on the clipboard and the LF text the phone sent are the same text.

### Hotkey

**Default: `Ctrl+Alt+Shift+K`** ("K" for Kin). It is picked to stay out of the way of what people already use:

- **Windows keeps every `Win+<key>` for itself** (`Win+V` is the clipboard history, `Win+Shift+S` the snipping tool, `Win+K` casting, and so on), so none of those is used.
- **Two-modifier shortcuts are what apps use** (`Ctrl+Shift+K` opens the web console in Firefox, for one, and editors bind many `Ctrl+Alt+<letter>` commands). A global hotkey wins over the app in front, so it would break those. With three modifiers it sits where far fewer commands are bound.
- **`Ctrl+Alt+<letter>` is `AltGr+<letter>` on many keyboard layouts**, which is how they type characters (`€`, `@`, Polish `ł` and `ś`, and so on). A global `Ctrl+Alt+<letter>` takes that character away from the people who type it. Adding `Shift` keeps it clear of the common ones.
- **Checked on the development PC:** Windows accepted the registration, so no other program holds it there. The check is repeated on every start (a program that holds the key makes the registration fail, which shows in the log, in `status.json` and in a toast). Every program on every PC can't be checked, which is why it is configurable.

**Changing it.** In the **Settings window** (click the box, press the combination, press Set; Turn off and Default are there too), or by hand in `%APPDATA%\Kin\settings.json`:

```json
{ "autoClipboardSync": true, "hotkey": "Ctrl+Alt+Shift+F9" }
```

The syntax is the accelerator syntax of the Tauri global-shortcut plugin: modifiers `Ctrl`, `Alt`, `Shift` and `Super`, a letter, a digit or a name such as `F9`, joined with `+`. **What is refused, with a message that says why and suggests the default (1.4 review):** a hotkey needs **Ctrl, Alt or Win** in it, or must be a function key (F1 to F24) on its own, so `K`, `Shift+K` and `Shift+Space` (which would take capital letters and the space bar away from every program) are refused; and a **common shortcut** is refused: Ctrl+C, V, X, Z, Y, A, S, N, O, P, F, W, T and R on their own, Ctrl+Shift+Z, T, N and Esc, Alt+F4, Tab, Esc, Space, Enter and the arrows, Ctrl+Alt+Delete, and every `Win+<key>` with Win as the only modifier (Windows keeps those: Win+L locks the PC, Win+D shows the desktop). An empty string turns the hotkey off. **From the Settings window the change applies at once, and conflicts are reported:** the new key is registered first, and if another program already has it (Windows refuses the registration) the old hotkey stays in place and the window says "<key> can't be used: another program already has it". A hotkey that is wrong in `settings.json` at start makes the app start without a hotkey and say why once (a toast, the log, and `hotkey.error` in `status.json`).

**What the hotkey does.** It reads the clipboard at the moment of the press and sends the text as a `text` message, which the phone treats as an explicit send (a notification, and later an entry in the history). Two rules differ from the automatic sync, because someone pressed a key on purpose: it also sends content that a password manager marked "don't record" (the person asked) **with `sensitive` set**, so the phone shows no preview and keeps it out of its history (a sensitive text over 128 KiB is not sent at all: a file can't carry the mark), and the toast on success is "Sent to <phone>". **If the phone isn't connected, or gives no `ack` within 5 s, the text is queued** and the toast says so ("The text is queued and will be sent when the phone is back"); the one exception is a text marked sensitive, which is never stored and so never queued ("A text marked sensitive is never queued, so it was not sent"). A clipboard with no text gets "The clipboard has no text to send."

## Queue

Milestone 1.4. The rules are in [protocol.md](protocol.md#queue); this is how the Windows app keeps them.

- **What is queued.** The tray's "Send clipboard to phone", the hotkey and `--send-clipboard` (a `text`, or a `Text.txt` offer above 128 KiB), and the drop window, "Send to" and `--send` (an `offer`): each is a row of the `transfers` table with the status `queued` **before the first attempt** (a text's body is in `transfer_texts`; an offer's files are the source paths, which are read when the phone downloads, as before). **Never queued:** the automatic clipboard (dropped when the phone is offline, with `phone_offline` in `status.json`), and a `sensitive` text (it would have to be stored).
- **Flush.** When the phone's `hello` is accepted, and whenever something is queued while it is connected, the queue goes out **in creation order, one item at a time**; the next one goes after the `ack` of the previous. Items made during a flush go to its end. An acked text is `done`; an acked offer is `active` (the phone downloads it). **Each phone's items go to that phone**, over its own connection: the target device is carried through to the send, and every connected phone is flushed (with two paired phones, the newest connection is not where everything goes). **The `cancel` messages the phone has not acked go first** (see below), then the queue.
- **An item is held while it is sent** (1.4 review). The flush takes each item with its status read again, and a **Cancel waits only for the item that is being sent right now** (at most the 5 s ack timeout), never for the rest of the flush; an item the user canceled meanwhile is never sent. The `ack` of an offer only makes it `active` if it is **still queued**: a cancel, a `complete` or an expiry that came during the ack wait is not undone. **An offer is marked sent, and its 24 hours started, only after its frame was written to the connection** (a send that never left stays a queued item with its 7 days, and nothing is served for it). A text stored at the moment the phone connects is flushed too: the connection is looked at again after the insert, so a hotkey press during a reconnect can't be left waiting.
- **`cancel` messages are kept until acked** ([changelog 52](protocol.md)): a cancel (the user's, or an expiry) is stored in `pending_cancels` first, sent at once if that phone is connected, and sent again with the same message ID after every `hello` until the phone acks it (or answers with an `error`, or is unpaired). The PC no longer waits up to 3 s for a `complete` after a `bad_request` (that wait blocked the queue): an older phone that answers a repeat with `bad_request` fails the item at once, and its `complete`, when it comes, marks the offer **done**. **An offer that was sent and not acked is loaded again at start** (a queued item with a send time), so its files are still served after a restart.
- **No pings from the PC.** The PC never pings the phone to find out whether it is gone (that would wake its radio and cost battery). A connection that is dead is found out the way it always was: an item whose message gets **no `ack` within 5 s** closes the connection (the tray goes amber) and **the item stays `queued`**, to be sent again after the next reconnect, under the same `id` (a repeat is harmless: the phone remembers the ID). Only an `error` from the phone fails an item.
- **Expiry** is decided on the PC's clock, at start, every hour and before a flush: a queued text after **7 days**; an offer **24 hours after it was sent** (the last attempt on an open connection: a send into a dead connection may have reached the phone, so its files stay served), or after **7 days** if it was never sent. It then shows in the history as `failed` with the error `expired`. An offer that had been sent also gets a `cancel` (reason `expired`).
- **Cancel** (the history's button, or `--dev-history cancel <id>`): a queued item is marked `canceled` and never goes out; no message is sent, because the phone never heard of it. If the offer had been sent into a dead connection it is canceled the ordinary way, with a `cancel` message.
- **A source file that is gone or changed while the offer waited** fails the item at the flush, with `source_gone` or `source_changed`, instead of at the phone's `GET`.
- **Retry** (a failed send from this PC, once): a **new item with a new ID** is queued from the stored text, or from the same source files if they are all still there; the old row stays and is marked as retried. (Retrying an item whose files are gone says so and makes nothing.) The link to the old item is written in the same transaction as the new item and a **unique index on `retry_of`** refuses a second retry, so a double click makes one item ("That item was already sent again."); the History window also keeps the button disabled while the call runs.
- **The temporary `Text.txt` of a long text** is removed by the clean-up of `outgoing\` only when **no transfer in memory and no queued or active row of the database** uses it: a queued long text lives in the database alone until it is flushed, and its file is the only copy of the text. (It used to be removed after 24 hours, and the item then failed with `source_gone`.) A folder that no record names goes after a day.
- **The database does not grow without limit.** `transfers` keeps every row for good (a transfer ID is never reused). The **bodies** of texts beyond the newest 500 items (the history shows 500) are deleted, except those of queued or active items; the send log (`sends`) keeps 90 days. Both run **at start and every hour**. The queries are covered by indexes on `transfers` (status, direction, device and creation time; creation time; expiry; finish time) and on the path of a file.

## Receiving from the phone

- **Files** go to the Downloads folder of the user, in `Kin\` (Windows is asked where Downloads is, so a moved folder works), or to `receivedFolder` of `settings.json`. Each one is streamed to `name.ext.part` (never held in memory, 1 MiB at a time) and, when the last byte is in, `fsync`ed, checked to be exactly as long as announced, marked with the Mark of the Web (see [What a received file may do](#what-a-received-file-may-do)) and moved to `name.ext` **without ever replacing a file** (`MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`; a name that is taken gets ` (1)`, ` (2)`, …, up to ` (99)`, also when it was taken during the transfer; if all 100 names are taken the file fails with `internal`). Names are cleaned by the rules of protocol.md ("File names"). **Finishing a file does not depend on the request:** the `fsync`, the mark and the move run in a task of their own, with the database told the name before the move and the result after it, so a phone that gave up waiting and asks again finds the file complete (never a second copy), and the `PUT` is answered as soon as the file has its final name. The toast and the image for the clipboard come after that, in another task: a slow decode or a busy clipboard never holds the phone's `200`. Folders deeper than 259 characters work: the final move and the disk-space check use the `\\?\` form of a long path.
- **Several files at once (v0.1.1).** The 0.1.1 phone sends up to 4 files of one transfer at the same time and pipelines small ones on one connection (protocol.md, "Concurrent file requests"). Each file has its own `.part` file, its own writer lock, its own offset and its own finish, so nothing about the files of one transfer is shared except the transfer's record and its speed; the transfer is done once, when the last file has its final name, whatever the order. **A `POST` for a transfer that already exists no longer stops the writers of all its files** (it used to, which with four files going would have failed the other three each time one was resumed): it stops a writer only if no byte arrived for a second (a dead connection), waits up to 250 ms for a writer whose connection just closed, and otherwise leaves it alone, reporting that file at the bytes stored so far. A request that is still being served when the transfer is canceled is answered `404`. The PC does not limit the number of file requests per transfer; the phone keeps to 4 (the connection pool, 24 paired connections, is the only bound).
- **The database is written without an `fsync` at every commit (v0.1.1):** `journal_mode = WAL`, `synchronous = NORMAL` (`storage.rs`), because four commits of two `fsync`s per received file, one after the other, were the slowest part of a photo batch (50 photos of 3.4 MB over loopback: 1.2 s before, 0.3 to 0.6 s after). After a power cut the last moments of progress may be missing from the database (never a corrupt file), which the resume rule already covers (it trusts the smaller of the database and the `.part` file); at worst a file that was being moved to its final name at that moment arrives twice. `kin.db-wal` and `kin.db-shm` sit next to `kin.db`.
- **Resume.** A `.part` file is kept for 24 hours after its last progress, and the transfer continues from the bytes that are there (the smaller of what the database says and what is on disk). A clean-up at start and every hour drops transfers with no progress for that long (their `.part` files go), offers that expired, and the `.part` files that the database still assigns to a transfer that is over. **It deletes only paths a record names:** a `.part` file in the received folder that no record names (a browser download, a file the user saved) is the user's and is never touched, and neither is a finished received file, even one that is named `*.part`. A `.part` file belongs to the transfer whose record names it: the names of unfinished transfers count as taken even when their file is missing, so another transfer never ends up with the same `.part` file and a resume never adopts a file the database doesn't assign to it. **A transfer ID is never used twice:** the records of finished, canceled and failed transfers stay in the database; a finished ID answers (the offsets, or `200` to a repeated empty `PUT`) for 24 hours and is then `404`, and a canceled or failed ID is `404` at once.
- **When the last file of a transfer has arrived:** a toast "<n> file(s) from <phone>". **Clicking it** opens the file (one file) or the folder (several), but only a file of a type on the **allow-list** below: any other type is never opened by a click, its folder opens with the file selected instead.
- **Images** (what is an image is decided by the content, not by the name or the type the phone gave) are also put on the clipboard (on by default; `imagesToClipboard` in `settings.json`), so Ctrl+V works right away. See [Images and the clipboard](#images-and-the-clipboard).
- **Text and links** go to the clipboard, with a toast (and, unless sensitive, a row in the history). Clicking a link's toast opens it in the browser. A text the sender marked **sensitive** goes to the clipboard with the formats that keep it out of the clipboard history and the cloud clipboard (`ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory` = 0 and `CanUploadToCloudClipboard` = 0), the toast says only "Text from <phone>" with no preview and nothing to open, and nothing about it (not even its length) goes to the log or `status.json`. Text lands with CRLF line ends.

### Toast buttons (R10)

**Finding (checked on Windows 11 with the real app, 2026-10-15): the buttons work for an app that isn't packaged.** A toast for one received file shows **Open** and **Show in folder** buttons (only **Show in folder** if the file's type isn't on the allow-list), a toast for several files **Open folder**, and a click on a button reaches the app (verified: a click on "Show in folder" logged `showed the received file in its folder` and opened Explorer with the file selected). The rules that come with it:

- A click or a button press is reported **only while the toast is on screen**. Once it has moved to the Action Center, pressing it does nothing (the notification plugin keeps the handler in the running process; there is no registered activator to start the app again). That is why the *file is always also in the folder and the log says where*.
- An unpackaged app has no app ID of its own, so Windows shows the toast under **"Windows PowerShell"** with PowerShell's icon (this is what a run from the build folder, `target\release`, still shows: the notification plugin uses the PowerShell ID there on purpose). That is cosmetic. **Since 1.5 an installed Kin has its own:** the app user model ID `app.kinrelay.desktop` (the bundle identifier). The installer's Start Menu shortcut carries it (Tauri's NSIS template writes `System.AppUserModel.ID` on the shortcut), the notification plugin names it as the origin of every toast when the app runs from an install folder, and the process names it too (`SetCurrentProcessExplicitAppUserModelID` at the very start, `integration.rs`), so toasts say "Kin" with the app's icon. The buttons don't depend on it: the click handler is in the running process, whatever the toast's ID. (`desktop\verify-install.ps1 -Toast` shows a test notification under the ID, to look at.)
- A click that doesn't say which toast it was opens nothing (1.2 used to open the newest link, which could open a link the user hadn't clicked).

So toasts are **not** click-only: the buttons are on. If a Windows update ever stops reporting button presses, the click on the toast itself does the first button's job, and that part is the same code.

### What a received file may do

Any app on the phone can send a file to the PC (R13), so a received file is as untrusted as a download. Two rules keep a click from running it:

**1. The Mark of the Web.** Every received file gets the NTFS alternate data stream `Zone.Identifier` with `[ZoneTransfer]`, `ZoneId=3` (the Internet zone) and `HostUrl=about:internet`, written on the `.part` file just before the final move (so the file has it from the moment it has its name). **SmartScreen and Office Protected View now apply to received files**, as they do to a browser download: a program asks for confirmation (and the "unknown publisher" warning), a Word or Excel file opens in Protected View with macros and active content off until the user allows them, and Explorer shows "This file came from another computer" in its properties. A volume with no alternate data streams (FAT, exFAT, some network shares) can't carry the mark: the file is received all the same and the log says so, with no name in it.

**2. An allow-list for "Open".** A click on the toast (or its **Open** button) opens a single received file with its default program only if its **last** extension, compared ASCII case-insensitively, is one of:

| Kind | Extensions |
|---|---|
| Pictures | `jpg` `jpeg` `png` `gif` `webp` `heic` `heif` `bmp` `tiff` |
| Audio and video | `mp3` `m4a` `aac` `flac` `wav` `ogg` `opus` `mp4` `mov` `mkv` `webm` `avi` `3gp` |
| Documents | `pdf` `txt` `csv` `md` `docx` `xlsx` `pptx` `odt` `ods` `odp` |

`csv` and `md` open as text (`csv` with whatever program the user has for it). The macro-enabled Office types (`docm`, `xlsm`, `pptm`, …) are not on the list. **Everything else gets "Show in folder"** (Explorer opens with the file selected) and the toast has no Open button: programs, scripts and anything another program registers for itself (on a developer's PC `.sh` opens in Git Bash and `.pyz` runs under Python), shortcuts and installers, archives, and files with no extension. Only the last extension counts, so `report.pdf.exe` is not openable and `report.exe.pdf` is a PDF; trailing dots and spaces are ignored (Windows ignores them too), and a name that holds a stream (`:`) is never openable. (The first 1.3 version had a deny-list; it missed `.sh`, `.pyz`, `.pyc`, `.wsb`, `.theme`, `.ahk`, `.appinstaller`, `.website`, `.vsto`, `.jnlp` and more, and could not be kept complete. The mark is the second line of defence: the Open button on an allow-listed file still hands it to SmartScreen and Protected View.)

### Images and the clipboard

An image from the phone is put on the clipboard so that Ctrl+V works in the apps people paste into. **Exactly one image in a transfer** goes there (several images leave the clipboard alone: one clipboard can't hold them as pictures, and picking one at random would be a surprise). The formats:

| Format | Why |
|---|---|
| `CF_DIBV5` | A 32-bit BGRA bitmap with an alpha channel. Windows builds `CF_DIB` and `CF_BITMAP` from it on demand, so Paint, Word, Outlook, Photoshop and any app that asks for a plain bitmap gets one, and an app that wants alpha gets alpha |
| `PNG` | The original PNG bytes, if the file is a PNG: Chrome, Edge, Firefox, Teams, Slack and Office prefer it |
| `CF_HDROP` | The path of the file in the received folder: Explorer pastes the file, and chat apps attach the original file (full quality, with its name) instead of a bitmap |

The picture is decoded with the Windows Imaging Component (PNG, JPEG, BMP, TIFF, the first frame of a GIF, and WebP, HEIC or AVIF where the user has the codec): no image library is added to the app. **A file is an image if the decoder opens it as one**, whatever its name or MIME type says, and the `PNG` format is written when the decoder says the container is PNG. **A phone photo has its rotation in the EXIF data and not in the pixels**, and an app that reads a bitmap never looks at EXIF, so the rotation (all eight orientations) is applied while decoding. The picture is read **row by row, in order**, and every pixel is written straight to its place in the bottom-up bitmap (no WIC flip-rotator, which asks a JPEG decoder for a scanline per pixel and took over 400 s for a 12 MP photo with orientation 6; now about 45 ms, as fast as an unrotated one). **Memory is bounded:** the pixels are decoded straight into the one block of memory that becomes the clipboard's `CF_DIBV5`, 4 bytes a pixel, and an image that needs more than 64 MiB of pixels (about 16 megapixels: a 12 MP phone photo fits, a 48 MP one doesn't) is not put on the clipboard, with the reason in the log. The same limit applies to the `PNG` format (a file over 64 MiB). Verified with the real clipboard: an 8 × 4 PNG with transparency pastes as 8 × 4 with its colours (and the PNG format holds the original bytes), and a JPEG stored sideways with EXIF orientation 6 pastes upright.

## Links and the browser extension (2B.1)

Milestone 2B.1 (decisions D19 and the contract in [extension.md](extension.md); the wire rules are in [protocol.md](protocol.md#links-link)).

### A link from the phone

A `link` message (`{url, title?, sourceApp?}`) is stored in the history like a text (the title next to the URL) and then **opened or offered**:

- **"Open links from phone automatically"** (Settings, **on by default**; `openLinksAutomatically` in `settings.json`): the link is opened with `ShellExecute` of a validated `http` or `https` URL only (the last line of defence is in `links::ShellOpener`, which refuses anything else, and the receiver has refused it before: a bad link is `error` `bad_request` and nothing is stored). The toast says **"Opened link from phone"**, with the title and the real host of the URL under it, and has a **Copy** button. A click on that toast does nothing: it was opened already.
- **The setting off:** nothing opens. The toast says **"Link from phone"** and has **Open** and **Copy**.
- **The address is the browser's reading, and a warning stops the auto-open** (changelog 55, `links::link_address`, the `url` crate = the WHATWG parser with IDNA): the line under the title is the host a browser will connect to (lower case, punycode, `0x7f.1` as `127.0.0.1`, IPv6 compressed, the default port left out), never the text as written. It gets a **⚠** in front when the host as written is not ASCII, has an `xn--` label, is an IP address, or is one a browser refuses; **such a link is never opened by itself, whatever the setting**: the toast is "Link from phone" with Open and Copy (Open works, on purpose). Links with `@`, `\` or `%` in the authority never get this far: the rule refuses them (`https://evil.example\@google.com`), on receive, for the extension's sends (`BAD_URL`) and in the image downloader. Look-alikes in plain ASCII (`paypa1.com`) are not detected.
- **A fullscreen game, a presentation, quiet time, or a locked or away user** (`SHQueryUserNotificationState` says `QUNS_RUNNING_D3D_FULL_SCREEN`, `QUNS_BUSY`, `QUNS_PRESENTATION_MODE`, `QUNS_QUIET_TIME` or `QUNS_NOT_PRESENT`, `quiet.rs`): **the browser is not opened even with the setting on**, because a browser that appears over a game steals its focus (and with an anti-cheat running that can cost a match), and one that opens on a locked PC or behind the screen saver lands where nobody sees it (`QUNS_NOT_PRESENT` counted as free before the review cleanup). The toast is the "Link from phone" one with Open and Copy, and the history keeps the link. When the call fails the state counts as free: a failure of this check must not take links away. The decision is one pure function (`phonelinks::decide`) and the state comes through a trait, so the tests say "a game is running" without one.
- **Copy** puts the URL on the clipboard through the history's copy path, so the automatic sync does not send it straight back. A link never goes to the clipboard by itself.
- **The log never has the URL or the title**, only its length and what was done with it ("not opened (the setting is off; user state free), offered in a toast").
- **`--dev-no-open`** (developer setting, `KIN_DEV_NO_OPEN=1`): nothing is ever opened, not a link and not a file or folder; the log says it would have, with the length of a link. For a test run that receives links from a phone and must not start a browser on the PC of the person who runs it.

### What this PC sends

`link` is queued like a `text` (protocol.md "Queue": persisted first, 7 days, in order after the `hello` messages) and shown in the history as a link. **The wire form is chosen when the message goes out** (`ws::wire_form`): a `link` goes as a `link` to a phone whose latest `hello` listed the `link` capability, and as a **`text`** (the same id, `isUrl` true, no title) to a phone that did not (a 0.1.x phone), so a link queued for an old phone and sent after the phone updated arrives as a link and the other way round. This PC's own `hello` lists `"capabilities": ["link"]`.

### The browser extension's way in

The extension talks to `kin-native-host.exe` (a standalone crate, `desktop\native-host\`, 243 KiB, no Tauri), which the browser starts and which relays each request over a **named pipe** to the running Kin (`nativehost/`):

| | |
|---|---|
| Pipe | `\\.\pipe\app.kinrelay.desktop.<user SID>` for the installed Kin. **Every other Kin** (a debug build, any developer setting, a `--data-dir` of its own: `HostKind::for_config`) uses `\\.\pipe\app.kinrelay.dev.<SID>` (with `.<suffix>` when `KIN_DEV_PIPE_SUFFIX` is set, so two test Kins can listen at once), so a test can never talk to the user's Kin and the user's Kin never answers a test |
| Security | A protected DACL with one entry, the current user (`D:P(A;;GA;;;<SID>)`: read back from the pipe in a test), `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first instance (if the name is taken Kin says so in the log and runs without the extension pipe, it never falls back), byte mode, one request per connection, a new instance made before a client is served, each client on its own thread, a client that sends no whole request in 30 s is cut off, a request over 64 MiB + 1 MiB is dropped unread |
| What it does | `status` (the devices: id, name, online, items waiting; the default device), `start` (answered like `status`: the host starts Kin), `open` (`main` is the drop window, `pairing` starts a pairing), and `send` of a `text`, `link`, `page` or `image`. Nothing changes settings, unpairs a device or reads the history |
| Limits (checked again here) | 30 `send` per 10 s (`INTERNAL`, "Too many requests, slow down"); a URL as in protocol.md (http or https, no whitespace, 8 KiB; `BAD_URL`); a title cleaned like a file name and cut to 300 characters; a text up to 4 MiB (`TOO_LARGE`), over 128 KiB it goes as `Text.txt`, never `sensitive`; image bytes up to 32 MiB; a picture is a picture only if its **bytes** say so (PNG, JPEG, GIF, WebP, BMP, TIFF, AVIF, HEIC; not SVG: `NOT_AN_IMAGE`, or `IMAGE_NEEDS_BYTES` for a download) |
| Images by URL | Kin downloads the URL itself (`imagefetch.rs`, own small HTTP/1.1 client over tokio and rustls with the web's root certificates): `GET`, **no cookies, no credentials, no user information**, redirects up to 5 (http and https only, **never https to http**), 30 s in all, **64 MiB** (the read stops at the cap), a browser's `User-Agent`, `Referer` when given. A failure a browser might get past (401, 403, 404, 429, 5xx, a timeout, a connection error, an HTML page) is `IMAGE_NEEDS_BYTES` and the extension fetches it inside the page; over 64 MiB is `TOO_LARGE`. The file goes through the ordinary file transfer, named by the page's name, else the URL's last segment, with the extension of what it really is |
| Offline phone | Queued: `ok: true`, `queued: true`, `DEVICE_OFFLINE_QUEUED` |
| Logs | Counts and codes only ("extension: send link (51 characters): acked"). No URL, no text, no title, no name (a test greps the log for them) |

### Registering the host with the browsers

The installer is per machine and runs elevated, so **Kin registers the host itself, as the signed-in user, at every start** (`nativehost/registry.rs`), like the "Send to" shortcut: it writes the two manifests to **`%APPDATA%\Kin\native-messaging\`** (the Chromium one with `allowed_origins` = the stable dev extension ID, plus `STORE_ORIGINS` for the store IDs (**a clearly marked TODO**: Edge reads only the first manifest it finds, so every ID goes in this one file); the Firefox one with `allowed_extensions`) and the `HKCU` keys that point at them: `Software\Google\Chrome`, `Chromium`, `Microsoft\Edge`, `BraveSoftware\Brave-Browser`, `Vivaldi` (`...\NativeMessagingHosts\app.kinrelay.desktop`) and `Mozilla\NativeMessagingHosts\app.kinrelay.desktop`. Opera shares the Chrome key (**not verified**, the user checks it on real hardware at v0.2.0). The manifest's `path` is the absolute path of `kin-native-host.exe` next to the running `Kin.exe`, so a moved install repairs itself at the next start. **Only the installed Kin does this** (`registry::may_register_release`: a release build that runs the way a user runs it, not from a build folder, with the host beside it); a debug build, any developer setting, a data directory of its own or any test never writes these keys, and Kin never writes keys for the dev host name (`app.kinrelay.dev`: a test that needs its key writes `HKCU\Software\Chromium\NativeMessagingHosts\app.kinrelay.dev` itself and removes it in a `finally`). The keys exist from the first start after the install (the installer's finish page starts Kin).

The installer carries `kin-native-host.exe` next to `Kin.exe` (`desktop\build.ps1` builds it in release mode with no features, refuses a host that contains the dev strings, and adds it to the bundle with `src-tauri\windows\bundle-native-host.json`). **Uninstall** removes exactly the six keys of the release host name in both contexts (this process's and the signed-in user's, `hooks.nsh`) and the two manifests; nothing else under any browser key.

## Phone notifications (2B.2)

Milestone 2B.2. The wire rules are in [protocol.md](protocol.md#notifications-notif) (changelog 56); the design and its reasons are in [phase-2b-2-design.md](phases/phase-2b-2-design.md); what was measured is in [phase-2b-2-spike-s1.md](results/phase-2b-2-spike-s1.md) and [phase-2b-2-desktop.md](results/phase-2b-2-desktop.md). Code: `desktop/src-tauri/src/mirror/`.

**Off by default.** Settings → "Phone notifications" → "Show phone notifications on this PC". The PC lists `notif` in its `hello` only while it is on, and sends a new `hello` when it changes. Nothing is registered with Windows, no thread is started and nothing is shown while it is off.

### Its own toast layer, its own identity

The Phase 1 toasts (`tauri-plugin-notification`, the AUMID `app.kinrelay.desktop`) are untouched. The plugin can't do a text box, a tag and group, an update, an expiry or a removal from the history, so phone notifications use the `windows` crate's WinRT toasts directly (`mirror/surface.rs`, one worker thread in the MTA) under **their own app identity**: `app.kinrelay.desktop.phone`, shown in Windows Settings → Notifications as **"Kin: phone notifications"**, so the user can mute them without touching the others. All of it is written by the app itself, under `HKCU`, at each start while the switch is on (no admin, no Start Menu shortcut, no MSIX; spike S1):

```
HKCU\Software\Classes\CLSID\{6B0A1D3E-2F54-4E8A-9C71-3D5B8E2A4F90}                (Default) = Kin phone notifications activator
HKCU\Software\Classes\CLSID\{6B0A1D3E-...}\LocalServer32                          (Default) = "C:\Program Files\Kin\Kin.exe" --toast-activated
HKCU\Software\Classes\AppUserModelId\app.kinrelay.desktop.phone                   DisplayName, IconUri (%APPDATA%\Kin\notif-app-icon.png), CustomActivator = {CLSID}
```

* **Only the installed Kin writes these names**, and only in a normal release run (not a debug build, not with a developer setting, not from a build folder: `Config::autostart_is_real` and `integration::is_build_folder`). **Every other instance** (a copy beside it with its own `--data-dir`, and every test) uses an identity of its own, `app.kinrelay.desktop.dev-<key>.phone` and a CLSID made from the key, and **removes every key it wrote at exit, including the two that Windows itself creates for an AUMID that has shown a toast** (`Notifications\Settings\<aumid>` and `PushNotifications\Backup\<aumid>`; the second can appear minutes later, so a test looks again after a while).
* Turning the switch off removes the toasts and the two keys of Kin's own. The uninstaller removes the same two keys in both contexts (`windows/hooks.nsh`); the two OS-owned ones hold the user's own choices and stay.
* **`Show` succeeds for any AUMID, registered or not** (spike): a missing registration is not an error. If the keys or the COM class can't be written or registered the toasts fall back to **text only** (no reply box, no buttons), and so does the setting "Text only" (decision 2: kept as a switch in case a Windows version doesn't call the class).

### A click: the COM class

The shell reads `CustomActivator`, asks COM for the class and calls `INotificationActivationCallback::Activate(aumid, arguments, inputs)`; if Kin is not running COM starts it (`Kin.exe --toast-activated -Embedding`, both ignored by the command line parser). `mirror/activator.rs` registers the class from **a thread of its own that joins the MTA** (the main thread is an STA) and hands every call to the core through a channel at once. `core.mirror_activation` is the one function a click ends in (the COM class, the toast object's own `Activated` event for a popup, and `--dev-toast`); a repeat of the same arguments within 3 s is one click (a **different** reply text under the same Send within 3 s is not sent and the user is told so; a reply over 2,000 characters is refused with a message, nothing is sent; the 5 presses per 10 s count from the first press, also for a phone Kin has no status for yet). A toast is shown on a blocking-pool thread, not on one of the runtime's, because it waits for the toast thread for up to 10 s. A hint or button label is kept on the toast, in the ledger and in `notif.action.label` in its **toast form** (U+2028, U+2029, U+FFFE and U+FFFF as a space, ends trimmed: `toast_xml::toast_label`), so a toast read back from Windows' history after a restart still matches what the phone compares.

* The arguments are **identifiers only**: `kin=1&d=<phone short ID>&n=<nid>&a=tap|reply|copy|btn[&i=<index>]`, read back strictly (`mirror/args.rs`, vectors `toastIds[]` and `toastArguments[]`). **Any program of the same user can call the class**, so a click is believed only if the arguments are exactly ours, the phone is paired, the `nid` is on screen (the ledger) or in Windows' history for this AUMID (after a restart of Kin), the button is one the toast offered, and fewer than 5 presses went to the phone in 10 s.
* **Reply** sends `notif.action` with the typed text (trimmed, 1 to 2,000 characters), the phone's index and, as `label`, the hint the toast showed. **A button** sends `notif.action` with its index and label. **Copy** needs no phone (below). A click on the toast itself does nothing visible. After a press the user is told in a small Phase 1 toast what came of it ("Reply sent to <phone>.", "The notification changed on <phone>. Nothing was sent.", "No answer from <phone>...": 5 s, **never sent again**, and the connection is not closed for it). If Kin was started by the click, it waits up to 10 s for the phone to connect.
* After a restart of Kin the ledger is empty, but the toasts are in Windows' history with their tag, group and XML: the reply box, the code and the buttons are read back from it (`toast_xml::offered_from_xml`; the "no hint" placeholder carries an invisible mark so it can be told from a hint that is really "Reply").

### What a toast says

Title (the phone's title, else the conversation, else the app), **at most two body lines** (the last two messages of a conversation: `Name: text` in a group, the text alone in a chat of two, `You: ...` for the user's own; else the long text if it is longer than the short one; else the first two lines), the attribution **`<app> · <phone>`** (always: the app label is 40 characters of the phone's text and must not pass for Windows), the app's icon (from the cache, below), and at most five buttons: the reply box with **Send**, **Copy <code>**, then the phone's own (at most 3). Every value is escaped in one place and set as the text or the attribute of a node of a small tree, so `</text><action .../>` in a title is just text; U+2028 and U+2029 are drawn as spaces; the XML is cut to **4,800 bytes** (the limit of a toast is 5 KB) by shortening text, never structure (`mirror/toast_xml.rs`, with a hostile-string test and a fit test).

* **`sensitive`** (the phone's flag for banking, authenticator and password apps, decision 1, and for lock-screen-secret notifications the user allowed), and the PC's own **"Hide notification content"**: title = the app, text "Private notification", no reply box, no buttons, no code. **`redacted`** (Android 15+ hid a one-time code from Kin, decision 4): "Code hidden by Android", no code, no buttons.
* Silent unless "Play a sound for phone notifications" is on. `silent` posts and `importance` ≤ 2 are added to the Action Center with **`SuppressPopup`**. `NotificationMirroring = Disabled` (the spike's correction to the design's `Disallowed`) keeps Windows from mirroring the toast on to other devices.
* **Tag = the `nid`, group = `kin-<phone short ID>`**: a post for a `nid` that is on screen **replaces** it (no `Dismissed` for the old object, spike), a `notif.remove` removes it (`RemoveGroupedTagWithId`, also for a toast of a dead process), `notif.sync` removes this phone's toasts that the phone no longer has (works after a restart of Kin). At most **30** toasts per phone: the oldest go first.
* **Expiry** (`ExpirationTime`, and `ExpiresOnReboot` always): 8 h, 2 h for a silent one, **10 min** for a private one, a redacted one or one with a code. **The honest sentence: a mirrored notification's text lives in Windows' Action Center until it expires or the user clears it.** Kin can't change that; it shortens it, and the Settings window says so.
* **Rate limits** (receiver, per phone: a reconnect doesn't refill the bucket): a token bucket of 20 refilled 1 per second, an identical post for a `nid` within 2 s ignored (no new popup), one `error rate_limited` per 10 s at most.

### Closing a toast, and the 60-second clear

* **X on the PC dismisses it on the phone** (decision 3, setting "Closing a phone notification here also dismisses it on the phone", on by default): only the exact `Dismissed(UserCanceled)` of the toast object of the **current** generation sends `notif.dismiss`. A popup that timed out, a toast the app hid, a `SuppressPopup` toast (which reports `TimedOut` at once), a replaced one and one the phone removed send nothing. **Known gap:** clearing an entry from the Action Center may not raise the event in Kin's process, and toasts shown before a restart of Kin have no handlers. Kin does not poll the history to guess ("a wrong guess cancels a real notification").
* **Copy <code>** writes the code with the **sensitive clipboard formats** (`ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory` = 0, `CanUploadToCloudClipboard` = 0), so Windows' history and cloud clipboard keep it and **Kin's own automatic clipboard sync never sends it back to the phone**. 60 seconds later the clipboard is emptied **only if its change counter (`GetClipboardSequenceNumber`) and its text are still what Copy left** (one open of the clipboard; anything else the user copied is left alone and not read); a second Copy starts the 60 seconds again; quitting Kin runs the same check once.

### What is stored and logged

Stored: **the icon cache** `%APPDATA%\Kin\notif-icons\<hash>.png` (a PNG that passed the wire checks and a decode by WIC; named by its hash, never overwritten, at most 200 files or 8 MiB, removed with the last phone), `notif-app-icon.png` (Kin's own icon, for Windows Settings), four booleans and one more in `settings.json` (`mirrorNotifications`, `mirrorSound`, `mirrorHideContent`, `mirrorDismissToPhone`, `mirrorTextOnly`) and the `HKCU` keys above. **No database table, no notification text, no `nid`.** The ledger, the limiters and the clipboard record are in memory. **Logs have counts and a keyed tag** (`<notif 1a2b3c4d>`-style, 8 hex digits of the log key's HMAC) and never a title, text, reply, label, code, app name, `nid` or key; `status.json` has `mirror.view` (the settings and each phone's line) and `mirror.counts` (numbers only). Tests grep the log, the data directory and `status.json` for the strings they posted.

### For a developer

`--dev-toast-quiet` (every phone toast goes to the Action Center with no popup and no sound), `--dev-set mirrorNotifications|mirrorSound|mirrorHideContent|mirrorDismissToPhone|mirrorTextOnly <true|false>`, `--dev-toast reply <nid> <text> | copy <nid> | button <nid> <index> | dismiss <nid>` (the same functions as a click and the X, no Windows). `cargo run --example toast_probe -- history|clear|activate|registry ...` reads what Windows holds for an identity and does what the shell does for a click (`CoCreateInstance` and `Activate`, no input injection); `fake_phone --notif ...` plays the phone. `tools\check-2b2-desktop.ps1` runs all of it once against a real dev Kin and cleans up (it refuses to run while a game is running).

### A slow `show()` holds that phone's connection (known limit, 2B.2 review)

`ToastSurface::show` waits for the toast thread for up to **10 s** and runs on the blocking pool, but the connection task of that phone **waits for it** (so a phone's posts and removes stay in order). While it waits, that connection reads nothing: the phone's later messages sit in the socket, and an `ack` that the phone already sent for something the PC sent earlier is not read either, so if the wait goes past the 5 s that `ack` is due in, the connection is closed as dead and the phone reconnects. Other phones are not affected (each has its own task). In practice a toast shows in milliseconds, so this has not been seen; it is written down so nobody is surprised by a reconnect after Windows' notification service hung for a few seconds. (The media code of 2B.3 does the same with the flyout: `MediaSurface::show` also waits up to 10 s for its thread, on the blocking pool, and a `media.*` message of that phone waits behind it.)

### Not verified (a person has to look)

That the shell itself calls the registered class when someone **clicks** (everything up to the call is proven: the registration, COM starting the class, `Activate` with the arguments and the reply text, with Kin running and not running); what a real reply box, the buttons and the icon **look like**; the **X** on a popup and on an Action Center entry; Windows 10; and that `NotificationMirroring` does what it says. The list is in [phase-2b-2-desktop.md](results/phase-2b-2-desktop.md) ("Manual checklist") for the user's real-click test.

## Media controls (2B.3)

What plays on one device is shown, and controlled, on the other, in both directions at once, each behind its own switch in Settings > Media, **both off by default** (decision of the user, 2026-10-17): "Show the phone's media on this PC" (`mediaShow`) and "Share this PC's media with the phone" (`mediaShare`). The protocol is [protocol.md](protocol.md) "Media controls" (changelog 57), the design [phase-2b-3-design.md](phases/phase-2b-3-design.md), the results [phase-2b-3-desktop.md](results/phase-2b-3-desktop.md). Code: `src-tauri/src/media/`.

### PC to phone: reading the PC's media (GSMTC)

* **Windows' own media sessions** (`GlobalSystemMediaTransportControlsSessionManager`, Windows 10 1809 and later) are read from an unpackaged exe with no capability (design section 2). `media/reader.rs` runs it on **a thread of its own** (MTA): it keeps the manager and, for each allowed session, three event registrations (media properties, playback info, timeline); every event only tells the core, which looks **300 ms later** (a track change is several events; **nothing ticks while a video plays**, there is no polling and no position stream). The position is extrapolated: `Position + (now - LastUpdatedTime) x PlaybackRate` (`position::windows_source_position`).
* **Which session:** `media/pick.rs` (the protocol's rule): never Kin's own, one with a title, `playing`, `paused` or `buffering`; the current one stays while it plays; else the first playing one (the system's current session first); no candidate is a `media.clear` after **1.5 s**; a session paused for 30 minutes is dropped. The picture is read again only when the track changed (a thumbnail that isn't there yet is looked for once more after 1.5 s), and `media/art.rs` makes it a PNG or JPEG of at most 24,576 bytes and 256 pixels (a thumbnail that fits, such as Edge's 2,419-byte PNG, goes through untouched; any other is decoded with WIC, scaled, and written as a JPEG at 256, 192, 128, 96, then 64 pixels until it fits). Names: a small table of players (`reader::display_name`), else the AUMID without `.exe`.
* **`media/source.rs`** is the engine (pure, times as arguments): a trailing 250 ms throttle for states, an identical state never sent again (the position is left out, but a jump of more than 1,500 ms from the extrapolation is a seek and is sent), the volume through its own trailing throttle, the 30-minute expiry, the 1.5 s clear. The core fans what it says out to every phone that may get it (`media/policy.rs`: share on, the phone lists `media`, the phone's status says `show: true`), the picture first and once per connection (20 per 60 s), each phone under its own bucket (10, one per 250 ms).
* **Commands from the phone** (`media.cmd`): `policy::cmd_result` is the one function that knows the order: `share` off is `disabled`, over 20 per 10 s `rate_limited` (one answer per 10 s), no session `not_found`, another `sid` or a button the session doesn't list `stale`, a refusal `action_failed`; success has no reply. `play`/`pause`/`toggle`/`next`/`prev` are `TryPlayAsync`... and `seek` is `TryChangePlaybackPositionAsync(ms x 10,000)`, on the session the engine shows and no other. **Volume** is the master volume of the default playback device through `IAudioEndpointVolume` (`media/volume.rs`): `level` sets the scalar, `delta` moves **at least one of Windows' 51 steps** (2 %), `mute` the mute flag; the user's own changes (slider, keys) reach the phone through `RegisterControlChangeNotify`, and the endpoint is looked up again on every call (headphones can be plugged in).

### Phone to PC: the Windows media flyout

* **A session of Kin's own** in the flyout (volume keys menu, lock screen controls): `SystemMediaTransportControls` through `ISystemMediaTransportControlsInterop::GetForWindow` on **a dedicated hidden top-level window** (`media/surface.rs`; class `KinMediaControls`, no parent, style 0, never shown). **A message-only window fails with `E_INVALIDARG`** (verified), so Kin's clipboard window can't be used. No audio, no `MediaPlayer`, no media foreground service. One thread owns the window, its message loop and **every SMTC call**; it never waits for GSMTC (reading its own session's thumbnail from the thread that owns the SMTC deadlocks: found by the design's probe), which is also why the reader lives on another thread and skips Kin's own session (`SourceAppUserModelId` = this process's AUMID).
* **What it shows:** the title (else the app), the artist, the album line **`<phone> · <app>`** (whether the flyout shows the album line is not known), the picture from an in-memory stream, the timeline (start 0, end = the duration, the position as the extrapolation says, seeking only if the phone listed `seek`), `PlaybackStatus` (playing, paused, changing, stopped), and the buttons the phone listed (`toggle` enables play and pause). The flyout's name and icon are those of the process AUMID (`app.kinrelay.desktop`: "Kin" with the Start Menu shortcut's icon); a name of its own for it would need a second AUMID (not tried). While the status is `Playing` the timeline is refreshed every 5 s (whether the flyout moves its bar by itself is not known). A press or a drag of the bar is a `media.cmd` to the phone (never guessed: the display only changes with the phone's next state); a dragged bar is one command at once and the last value 150 ms later, at most 20 commands per 10 s.
* **While Windows is locked** the session is disabled and cleared (`WTSRegisterSessionNotification` on that window), and shown again after the unlock: a phone's now-playing title must not sit on a lock screen. If `GetForWindow` fails (a Windows N edition without the Media Feature Pack, an old Windows 10) Settings says "Windows can't show media here" and the tray and the panel below carry on.
* **The tray menu and the drop window** (the fallback, and the place the device is always named): while a phone's session is shown the tray menu gets **Play/Pause phone media**, **Next** and **Previous** under the status line (no title in the menu or the tooltip: "Kin: Pixel 8 connected, media playing"); the left-click window gets a media strip with the cover, the title and artist (they are shown **there**, in a window the user opened), `<app> on <phone>`, the buttons the phone listed, a seek bar (the strip is read again every 0.7 s with the extrapolated position) and the phone's volume slider if it sent one; below it "PC media -> phone: <title> - <artist>" read-only while the PC's media is shared, and the PC's own volume slider.

### The test-run guard (design 6.1): only the installed Kin touches your real media and volume

`media/guard.rs`, pure and tested: **only the installed Kin** (a release build, run the way a user runs it, no developer setting, no data directory of its own, not from a build folder) reads and controls the user's real media sessions and writes the PC's real master volume. **Every other instance, every test and every debug build runs in test mode:**

* it reads and controls **only** the session whose `SourceAppUserModelId` is `--dev-media-aumid <id>`, and that has to start with `app.kinrelay.dev.mediatest-` (a session of Kin's own making: the option refuses any other id, so a dev Kin can't be pointed at a real app); with the option missing it reads no session at all. `reader::Guarded` compares the id **before** the backend is asked for anything but the id: a real session's title, thumbnail and timeline are never requested, and a command never reaches a session that isn't the one;
* the master volume is a **fake** (a number in memory, 51 steps); the real `Set*` is reachable only with `--dev-media-real-volume`, which no automated test or agent ever passes (only the person's own manual test);
* its flyout session is **never `Playing`** (a `Playing` Windows session takes the keyboard's media keys): `playing` is shown as `Paused`; `--dev-media-quiet` says so out loud and is implied.

### What is stored and logged

Stored: **two booleans** in `settings.json` (`mediaShare`, `mediaShow`). Nothing else: no table, no file, no cover, no `sid`. The pictures, the sessions and the position anchors are in memory (at most 8 pictures per phone), and are dropped with the connection. **Logs have counts** (`media status of device <8 chars>: show, share, access`, `sharing the PC's media with the phone (test run)`) **and never a title, an artist, an album, an app name, an AUMID, a `sid` or a picture**; `status.json` has `media.view` (the switches, the kind of run, a line per phone, `none|playing|paused` for each direction) and `media.counts` (numbers). Tests grep the log, the data directory and `status.json` for the strings they used.

### For a developer

`--dev-media-aumid <id>`, `--dev-media-real-volume` (never in a test), `--dev-media-quiet`; `--dev-set mediaShare|mediaShow <true|false>`; `--dev-media play|pause|toggle|next|prev|seek <ms>|volume <0-100>|volume-delta <n>|mute|unmute` (what a flyout press does, without Windows: a `media.cmd` to the phone whose media is shown); `--dev-dump-view media`. `cargo run --example media_test_session -- serve|read <aumid>|control <aumid> <cmd>|volume-read` is a **silent session of its own** (hidden window, `Paused`, a random nonce title, no audio) and a read-only reader that accepts **only** `app.kinrelay.dev.mediatest-<n>` (a session of its own) or `app.kinrelay.desktop.dev-<key>` (a dev Kin's flyout session), each with a non-empty suffix, and refuses everything else, **including the installed Kin's own `app.kinrelay.desktop`** (`guard::tool_may_look_at`; reading it would show the user's real phone, and a `control` would skip their track); `fake_phone --media --media-status/--media-state/--media-image/--media-clear/--media-volume/--media-cmd` plays the phone. `tools\check-2b3-desktop.ps1` runs all of it once against a real dev Kin and cleans up.

### Not verified (a person has to look)

How the flyout **looks** (the name, the icon, the album line, whether the bar moves while `Playing`); `Playing` on Kin's session and the keyboard's media keys; the lock screen; Windows N editions and Windows 10; **a real change of the PC's volume and mute through the phone**; real players (Spotify, a browser, VLC, a cast session) and what they list; a long run (battery, memory). The list is in [phase-2b-3-desktop.md](results/phase-2b-3-desktop.md) ("Manual checklist").

## Install

**Milestone 1.5.** `desktop\build.ps1` makes `desktop\src-tauri\target\release\bundle\nsis\Kin_0.1.0_x64-setup.exe` (3.59 MiB). It is a **Tauri NSIS installer, per-machine** (`bundle.windows.nsis.installMode` is `perMachine` in `tauri.conf.json`), so it asks for administrator rights (the UAC prompt) and installs to `C:\Program Files\Kin\`. The program is `Kin.exe` (`mainBinaryName`; Windows ignores the case, so the `kin.exe` of decision D13 is the same file). The installer's own steps are in `desktop\src-tauri\windows\hooks.nsh`, which Tauri's NSIS template calls at four points (`bundle.windows.nsis.installerHooks`).

**Who does what, and why.** An elevated process can be another account than the person at the keyboard (a standard user who types an administrator's password: `%APPDATA%` and `HKCU` are then the administrator's, not the user's). So **the installer does only what is machine-wide, and everything that belongs to the signed-in user is done by the app**, which always runs as that user:

| What | Who and when | Details |
|---|---|---|
| **Firewall rule "Kin Relay"** | The installer (`NSIS_HOOK_POSTINSTALL`) | `netsh advfirewall firewall add rule name="Kin Relay" dir=in action=allow program="$INSTDIR\Kin.exe" enable=yes profile=private,public protocol=TCP remoteip=LocalSubnet`. **Private and Public** both (D12): Windows 11 marks a new network Public by default, and every request is authenticated (see R8 in [risks.md](risks.md)). **Since v0.1.1 only from the local subnet** (`remoteip=LocalSubnet`, the D12 addendum): the port is not reachable from outside the PC's own network. If a router puts the phone on another subnet than the PC, the phone can't connect any more: open Windows Defender Firewall with Advanced Security, Inbound Rules, "Kin Relay" > Properties > Scope > Remote IP address, and add the phone's subnet (or choose Any IP address) A rule of that name is deleted first, so a reinstall, an upgrade or an install in another folder never leaves two. If `netsh` fails the installer says so (and carries on) |
| **Firewall rule "Kin Relay mDNS"** | The installer | Inbound UDP 5353 for `Kin.exe`, the same profiles, and since v0.1.1 the same `remoteip=LocalSubnet` (mDNS is link-local, so the queries come from the subnet). **Added in 1.5 beyond the plan's single TCP rule:** the phone finds the PC again by its mDNS name when the PC's address changes, and those queries come in over UDP. The Windows Firewall drops them for a program that has no UDP rule. Untested on a real network (mDNS never ran on the development PC, which has no phone on its LAN), so it is cheap insurance; remove its two lines in `hooks.nsh` to go back to TCP only |
| **Start Menu shortcut "Kin" with the app user model ID** | The installer (Tauri's template: `CreateOrUpdateStartMenuShortcut`, all users' Start Menu) | The shortcut carries `System.AppUserModel.ID` = `app.kinrelay.desktop` (the bundle identifier), which is what makes a toast say "Kin" with the app's icon instead of "Windows PowerShell" (see [Toast buttons](#toast-buttons-r10)). The app gives its process the same ID at the start (`integration.rs`, `SetCurrentProcessExplicitAppUserModelID`) |
| **Explorer "Send to" shortcut "Kin"** | **The app**, at every start (`integration.rs`) | `%APPDATA%\Microsoft\Windows\SendTo\Kin.lnk` → `Kin.exe --send`, in the SendTo folder of the user who runs Kin (asked from Windows: it can be moved). **Why not the installer:** an elevated installer would write into the administrator's folder when the two accounts differ. It is **made if missing and rewritten if it points elsewhere** (an install in another folder), so it comes back after an upgrade too. `"sendTo": false` in `integration.json` (below) removes it and keeps it away. It is made when Kin first runs: the installer's last page starts Kin as the user (the box is ticked by default) |
| **Start with Windows** | **The app**, at every start | The value `Kin` of the *current user's* Run key (`autostart.rs`: HKCU only, the quoted path of `Kin.exe`). **On by default**, decided once, when the profile is new (the identity was just created): "start with Windows" is the point of a tray app, and it is one switch in Settings to turn off. A profile that already existed (a developer build of 1.4) keeps the choice it has. What the person chose is kept in `integration.json`, and the start repairs the Run value to match it (an upgrade removes it, see below), so a person who turned it off never gets it back |
| **Native messaging host for the browser extension (2B.1)** | The installer lays down `kin-native-host.exe` next to `Kin.exe`; **the app** writes the manifests and the `HKCU` keys at every start | See [Registering the host with the browsers](#registering-the-host-with-the-browsers). The uninstaller removes the six keys of the release host name, in both contexts |

**`integration.json`** (in the data directory) holds what the person wants: `{ "startWithWindows": true, "sendTo": true }`. The Settings window's switch writes `startWithWindows`; `sendTo` is edited by hand (there is no switch). **None of this runs in a developer run** (a debug build, any `--dev-*` flag, a `--data-dir` of its own) **or from the build folder** (`target\release`): a script or a developer never gets a shortcut in their real SendTo folder or Kin in their real Run key.

**Uninstall** (`NSIS_HOOK_PREUNINSTALL`, `NSIS_HOOK_POSTUNINSTALL` and Tauri's template):

- Removes both firewall rules, the Start Menu shortcut (and unpins it), the installed files and the entry in the list of installed programs.
- Removes the **SendTo shortcut and the `Kin` Run value** in the context of the uninstaller **and** in the signed-in user's, which is started without elevation through `nsis_tauri_utils::RunAsUser` (it covers the case where the two accounts differ; it does not wait, because it needs nothing of ours).
- Removes the **native messaging host keys** (exactly the six `app.kinrelay.desktop` keys under Chrome, Chromium, Edge, Brave, Vivaldi and Mozilla) and `native-messaging\\` of the data folder, in the same two contexts.
- **Asks whether to delete the data:** the uninstall page has the box **"Delete the application data"** (Tauri's own, unticked: the default is to keep). Ticked, it deletes `%APPDATA%\Kin` (identity, pairing, history, settings, logs: the phone has to be paired again) as well as Tauri's `%APPDATA%\app.kinrelay.desktop` and `%LOCALAPPDATA%\app.kinrelay.desktop` (the WebView2 cache), and the installer's own key `HKLM\SOFTWARE\Kin Relay\Kin` (the install folder it offers next time). Left unticked, the data and that key stay, so a later install finds the pairing again.
- **It asks before it removes anything (v0.1.1).** If Kin is running, the template asks "Kin is running, close it?" and Cancel aborts the uninstall. That question used to come *after* the hook had deleted the firewall rules, the SendTo shortcut and the Run value, so a person who cancelled kept an install with no firewall rule. The hook now runs the same check (`CheckIfAppIsRunning`) first: Cancel aborts with nothing touched, and the template's own check afterwards finds Kin closed. (A test keeps the order. Not run for real: it needs the installer, which needs administrator rights.)
- **Phone notifications (2B.2) leave two things behind, on purpose.** (1) **Toasts that are already in the Action Center stay until they expire or Windows restarts** (8 hours for a normal one, 2 for a silent one, 10 minutes for a private one, a redacted one or one with a code; `ExpiresOnReboot` is always on): the uninstaller doesn't clear Windows' toast history, and a click on one of them does nothing (the class is no longer registered). Turn the switch off before uninstalling and Kin removes them itself. (2) **The icon cache `%APPDATA%\Kin
otif-icons\` stays until the application data is deleted** (the box above, ticked): it holds only the app icons the phone sent, named by a hash, never a notification's text. The registry keys of the activator (the CLSID and the AppUserModelId) are removed.
- Nothing is removed in the updater's call (`/UPDATE`).

**Upgrade.** Running a newer `Kin_x.y.z_x64-setup.exe` over an install finds the old one and (the template's own page) offers to uninstall it first, which is the default. The old uninstaller runs with its normal pages (it can't tell an upgrade from an uninstall): **leave "Delete the application data" unticked** and the data and the pairing are kept. It removes the firewall rules, the shortcuts and the Run value, and the new installer adds the rules and the Start Menu shortcut again; the app puts the SendTo shortcut and the Run value back at its first start (`integration.json` says whether the Run value is wanted). A start of the installer with `/P` (passive) or `/S` (silent) skips the pages.

**Code signing:** none in the MVP, so Windows SmartScreen shows "Windows protected your PC" on the installer (More info → Run anyway) and calls the publisher unknown. Sign before the public launch ([docs/TESTING.md](TESTING.md) tells the testers).

**Checking an install:** `desktop\verify-install.ps1` and `desktop\verify-uninstall.ps1` read the firewall rules, the shortcuts and their app user model ID, the Run value, the files and the registry, and say what is wrong. The installer itself was **not run during development** (it needs administrator rights): what was checked is in [phase-1-5-desktop.md](results/phase-1-5-desktop.md).

## Data locations

`%APPDATA%\Kin\` holds:

- Settings (`settings.json`: `autoClipboardSync`, `hotkey`, `receivedFolder`, `imagesToClipboard`, `openLinksAutomatically`, `deviceName`; the Settings window writes it)
- `integration.json` (1.5): what the person wants of the parts of the install that are the user's: `startWithWindows` (written by the Settings window's switch; missing means "not decided yet") and `sendTo` (the "Send to" shortcut, on unless it says `false`). See [Install](#install)
- Settings of phone notifications (2B.2) are in `settings.json` too (`mirrorNotifications` ... `mirrorTextOnly`). `notif-icons\\` (the cache of app icons that the phone sends, by hash: the only thing about notifications that Kin stores) and `notif-app-icon.png` (Kin's own icon for Windows Settings). The toast registration is in `HKCU` (see [Phone notifications](#phone-notifications-2b2)), not here
- `native-messaging\\` (2B.1): the two host manifests that Kin writes at every start (the `HKCU` keys of the browsers point at them). Not user data: removed by the uninstaller, made again at the next start
- The private key (DPAPI-encrypted)
- `log-key.dat`: the key of the tags that the log uses for texts and file names (see Logs), random per installation and protected with DPAPI (readable only by this Windows user on this PC). **Never exported.**
- The SQLite database (`devices`, the memory of message IDs, the `transfers` and `transfer_files` tables of [architecture.md](architecture.md#storage), and since 1.4 `transfer_texts` (the body of an explicit, non-sensitive text), `sends` (one row per send for the success rate: kind, times, outcome, no text and no name) and `connection_log` (the last 200 connects and disconnects))
- `outgoing\`: temporary files of ours (the `Text.txt` of a long text), each in its own folder, removed when the offer ends
- Logs (rotating, 5 files of 1 MB). **A file name is the user's own and is not in a normal log line:** where a line has to say which file, it has a short tag (`<file 1a2b3c4d>`) and the name is only logged at debug level, which is off. **The tag is keyed:** the first 32 bits of an HMAC-SHA256 under the per-installation key of `log-key.dat`, not of a plain hash, so a guessed text or name can't be checked against a log that was sent to someone. The same goes for the hash of a text in a log line. A `.part` path is never logged (it holds the file's name). (The toasts show the names. The log has the toast with the hash.)

Received files are not in there: they go to the received folder (`Downloads\Kin` by default).

## Pairing window

Tray: Pair new phone. It shows the QR code, the PC's name and short ID and a 5-minute countdown. **Copy pairing link** (1.5) is for a phone whose camera can't scan the code, or that was refused the camera permission: it puts the same `kinrelay://pair?...` link the QR code encodes on the clipboard, and the phone's first-run screen has a field to paste it in (send it to yourself first, for example by message). The page never sees the link: the `copy_pairing_link` command (pairing window only, in `capabilities/pairing.json` and `build.rs`) writes it in Rust. **It is written as sensitive text**, the same way the phone's sensitive texts are: `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory` = 0 and `CanUploadToCloudClipboard` = 0, so it stays out of Windows clipboard history, the cloud clipboard and Kin's own automatic sync to a paired phone. The link holds the one-time token: it works once and for 5 minutes, like the code, and the button is only there while the code on screen can still be used (not locked, expired or used). Neither the link nor the token is logged (the log says only that a link was copied). **Once the phone has paired, the link is taken off the clipboard again (v0.1.1):** if the button was used for this code and the clipboard still holds exactly that link, the clipboard is emptied (the check and the clearing are one step, so a copy the user makes in between is never touched). A clipboard that holds anything else, or a code whose button was never pressed, is left alone and not even read. A pairing that fails (a wrong code) leaves the link where it is, because the code still works. An expired code or a closed window doesn't clear it (the link is dead by then, and it may be what the user is about to paste).

## History, settings and debug windows

Milestone 1.4. The same page as the other windows (`index.html?w=history`, `settings`, `debug`), **destroyed when closed** like the others (the idle memory after opening and closing every one is measured in [phase-1-4-desktop.md](results/phase-1-4-desktop.md)).

**History** (tray: History). The newest **500** items, both directions, text and files: time, direction (↑ sent to the phone, ↓ received), status (Queued, In progress, Done, Failed, Canceled), size and the error code (`expired`, `disk full`, …). **Click a finished item to open it:** a file by the 1.3 rule (a single file whose type is on the allow-list opens with its default program, any other file is shown in its folder, selected; several files open their folder); a text is **copied** to the clipboard (any text, also one that is still queued or that failed), and the automatic sync is told, so the copy is not sent back to the phone. **Retry** on a failed item that the PC sent, **Cancel** on a queued (or running) one. **Never in it:** a `sensitive` text and the automatic clipboard sync (neither is ever stored).

**Settings** (tray: Settings). The device name (sent in `hello`, and in a new `hello` to the phone that is connected), automatic clipboard sync on/off, images to the clipboard on/off, the received folder (a Windows folder picker; the folder is checked by writing a file in it, and the old one stays if it is no good), the hotkey (see [Hotkey](#hotkey)), **Start with Windows** (a value `Kin` in the current user's `Run` key, holding the **quoted** path of `Kin.exe`; **only HKCU, never the machine-wide key, even when the app runs elevated**. **Only a release build that runs the way a user runs it writes the registry: a debug build (even with no flag), any `--dev-*` flag, or a `--data-dir` of its own uses a file, `autostart-mock.json`, and the Run key is never touched.** **Since 1.5 the switch is on by default for a new profile and is kept in `integration.json`**, so the app puts the value back after an upgrade and never turns it on for a person who turned it off: see [Install](#install). The uninstaller removes the `Kin` value), unpair (with a confirmation), and a button for the debug window.

**Debug** (Settings: Debug…, or Shift + left-click on the tray icon). **The share of sends that worked at the first try** over the last 30 days (target ≥ 99%, [targets.md](targets.md) #1; sends that were asked for while the phone was away are counted, and a second figure leaves them out; **a send that the user retried counts once**: the failed one is left out and the retry counts, never as a first try, as on the phone), per kind (text, clipboard, files to the phone, files from the phone); **latency** (tap to `ack` and the ping round trip: last, median, 95th); **recent errors** with their codes; the **connection history** (connects and disconnects with the reason); the **network profile** of this PC (Private or Public, from the Network List Manager: a Public network is the usual reason a phone can't connect); the queue; a Ping button; and **Export logs…**, which zips the log files and a redacted `status.json` (and the numbers of this window) to a place the user chooses. What the export takes out: the user's profile path **in its long and its 8.3 short form** (`C:\Users\ANNABE~1` as well as `C:\Users\Anna Berg`, the short one found with `GetShortPathNameW`) and **any other `C:\Users\<name>` folder** (it becomes `C:\Users\<user>`), **the folder that received files go to, wherever it is (`<received>`)**, IPv4 and **IPv6** addresses, the PC's and the phones' names (**in any letter case, and of every phone this PC has known, also one that was unpaired or renamed since**: the names are kept in a table of their own, `device_names`, for this), **the names of Wi-Fi networks (only Private, Public or Domain is exported)**, device IDs (cut to 8 characters) and file names. The key of the log tags (`log-key.dat`) is not in the zip.

## Window security

Each window gets only the commands it needs (1.4 review). `build.rs` lists every command of the app (`AppManifest::commands`), which makes Tauri refuse any command that no capability names for the calling window, and `capabilities/<window>.json` (`pairing`, `drop`, `history`, `settings`, `debug`) names those of that window and the two event permissions it needs to listen (`core:event:allow-listen` and `allow-unlisten`: **not `core:default`**, which also hands out window, webview, app and path commands). **Defence in depth:** every command also checks the label of the window that called it (`ui::only`) and refuses another, so a capability file that is edited too widely still can't make the history window change a setting. The page's CSP is `default-src 'self'; connect-src ipc: http://ipc.localhost; img-src 'self' data:; style-src 'self' 'unsafe-inline'; base-uri 'none'; object-src 'none'`.
