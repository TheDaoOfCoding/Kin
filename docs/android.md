# Android app

## Basics

- Kotlin, Jetpack Compose (kept basic), coroutines and Flow
- minSdk 29 (Android 10). targetSdk is the latest stable at the start of Phase 1
- **Release APK ABIs (v0.1.1):** `arm64-v8a` and `armeabi-v7a` only (`ndk.abiFilters` on the release build type). The app has no native code of its own; the eight `.so` files in the APK come from CameraX (image processing, surface util), AndroidX graphics-path and DataStore's shared counter, and all four exist as ARM and x86 builds. Dropping the two x86 sets took the release APK from 4,662,856 to 4,447,746 bytes. The debug build keeps every ABI (the emulator is x86_64). A consequence: **the release APK no longer installs on an x86 emulator** (`INSTALL_FAILED_NO_MATCHING_ABIS` on an image without ARM translation), so smoke tests use the opt-in `smoke` build type (`gradlew assembleSmoke -PkinSmokeAbis=x86_64`: the release configuration plus x86_64). **The smoke build has its own application ID, `app.kinrelay.android.smoke` (`applicationIdSuffix`), so it can never install over the real app** (the classes keep the namespace `app.kinrelay.android`, so `am start -n app.kinrelay.android.smoke/app.kinrelay.android.MainActivity`)
- **Libraries:**

  | Job | Library |
  |---|---|
  | HTTP, WebSocket, TLS | OkHttp |
  | JSON | kotlinx.serialization |
  | Database (devices, transfers, queue) | Room |
  | Settings | DataStore |
  | QR scanning | ZXing core (Apache-2.0) decoding CameraX frames on the phone. No Google Play services and no network. Needs the `CAMERA` permission, asked for when the user taps "Scan code" |

- No dependency injection framework. The app is small enough to wire up by hand.

## Look: skins and themes (`ui/theme/`)

One layout, two skins. **Warm** (the default: cream and apricot, round corners, illustrations) and **Simple** (calm teal, flat, plain icons where Warm has an illustration), each in light and dark. A skin changes only tokens (colours, radii, the 3 dp "press lip" under buttons, shadows) and whether an art slot draws an illustration or an icon; never the layout.

- **Tokens.** `KinTokens.kt` holds all 55 colours of the design for the four skin and mode combinations (`KinColors`, read as `KinTheme.colors`). `KinPalette` maps them to a Material3 `ColorScheme` and a `KinStyle` (shapes, press lip, shadows; `KinTheme.style`). No dynamic colour. Text is the system font: bold titles, semibold labels.
- **Choice.** Settings, "Appearance": skin Warm or Simple (with a small preview of each) and theme System, Light or Dark. Kept in `KinSettings` (`skin`, `theme_mode`; default Warm and System; an unknown value reads as the default). `KinAppTheme` reads it live and gives the status and navigation bars light or dark icons to match the chosen theme. The Ring, Pause and Scan screens use it too.
- **Parts.** `ui/KinComponents.kt` (card, button with press lip, chips, switch colours, segmented choice, the floating bottom nav) and `ui/theme/KinIcons.kt` (the design's icon set as vectors). `ui/theme/KinArt.kt` draws the illustrations on a Canvas (the PC and phone with faces that follow the link, the happy box, the record) and the Kin mark.
- **The mark.** The app icon and the in-app logo are always the Warm "kin-mark" on apricot `#F2804A`, in every skin and mode (`ic_launcher_foreground`, a monochrome layer for themed icons, and `ic_stat_kin` as a white silhouette for the notification bar).
- **Home** has a slot for the Send button (`sendButton`, right under the PC's status card). "Ping PC" is on the Debug screen.

## Why sending the clipboard is manual

Since Android 10, only the focused app or the active keyboard can read the clipboard. So we read it only right after the user taps something: the tile, the notification button, or the text selection menu. `ClipboardSendActivity` takes focus for a moment so it's allowed to read, then closes. On Android 14+, the tile has to start it through the `PendingIntent` version of `startActivityAndCollapse`.

Writing to the clipboard from the background is allowed, so PC → phone is automatic. Android 13+ shows a small system confirmation when that happens. That's expected.

## Text and clipboard (built in 1.2)

- **Receiving `clipboard`:** set silently from the service, never stored, never shown. The clip is marked sensitive on Android 13+, so the system's confirmation doesn't show a preview of it. The log holds only the length and a short keyed hash.
- **Receiving `text`:** copied to the clipboard and shown as a notification "Text from <PC>" with a preview (the lock screen shows only the title). **Since 2B.1 the copy follows the setting "Copy received text automatically" (Settings, default on = the behaviour since 1.2), and the notification always has a Copy button** ("Copy latest" when several texts are grouped; the sub text says "Copied" when the clipboard already has it). Copy takes the newest text from memory (a sensitive text is only ever there, and the clip is marked sensitive), or the history for an older notification; it is not in the `PendingIntent`. With the setting off nothing is written to the clipboard (and the loop guard is not armed). The automatic `clipboard` message is a different feature and is not affected. A text with `isUrl` gets an **Open** action only if the text really is one `http` or `https` URL (the phone checks again and never trusts the flag). An explicit text (a hotkey send) is recorded in the history (1.4); a sensitive text and the automatic `clipboard` never are. Messages are delivered in the order they arrived.
- **Sending (queue-first since 1.4):** `ShareActivity`, `ProcessTextActivity` and `ClipboardSendActivity` start `LinkService` while they are on screen (a visible activity may), hand the text to a sender that runs on the app's scope, and finish at once. The sender **saves the text as `queued` first** (the `texts` table), waits up to 4 s for a connection, and flushes the queue: one `text` at a time, each waiting 5 s for its ack. With no connection the text stays queued ("Saved. Kin sends it when <PC> is back"); with no ack it is **re-queued, not failed** (the message may or may not have arrived; it goes out again with the same ID, which the PC recognises). Only an `error` from the PC fails it. See "Queue, history, notifications (built in 1.4)". Text over 128 KiB (UTF-8, wire form) is sent as a `.txt` file through the ordinary upload (1.3), which is queued like any upload; a sensitive text over 128 KiB is not sent at all (a file has no `sensitive` mark).
- **Line ends (1.3):** the wire uses LF only. The sender turns CRLF into LF in one pass and leaves a lone CR; the receiver keeps the text as it came. The loop-guard hash is taken on the wire form: a received text is hashed as received, a clipboard text is converted first.
- **Sensitive text (1.3):** the phone sets `sensitive` on a `text` when the clip it sends carries `ClipDescription.EXTRA_IS_SENSITIVE` (API 33+; the clipboard send path, and a share whose clip data carries it). A received `sensitive` text is put on the clipboard marked sensitive, and its notification says "Text from <PC>" with no preview and no Open action. Nothing about it is logged, not even its length or hash.
- **Openable links (1.3):** the `isUrl` rule and the Open action use the shared rule of protocol.md ("Links: `isUrl` and openable URLs"), in `UrlRules`, with its own whitespace list, port and 8 KiB checks.
- **Loop prevention:** the hash of the last text the PC put on the clipboard is remembered for 60 s. A "send clipboard" of the same text in that time is skipped. Share and "Send to PC" are explicit and never skipped.
- **Arrival time:** the time from the tap (the activity's creation) to the PC's ack is kept for the Debug screen and the debug state dump.
- **Permission state:** while `ACCESS_LOCAL_NETWORK` is missing (API 37), `LinkService` makes no connection attempt and its state, the Home screen and the notification say "Nearby devices permission needed".

## LinkService

- **Started when:** the app opens, after pairing, after a reboot, or when the user shares something. Starting from a visible activity is always allowed.
- **Notification:** low importance and silent. It reads "Connected to Desk PC", "Looking for Desk PC", "Not on Wi-Fi" or "Nearby devices permission needed", with a "Send clipboard" action and (2B.4) a second and last action, "Pause 1 h" or "Resume". While connected it also says what the PC says about itself (`· 82% · charging` for a laptop, `· Kin paused on the PC until 14:30`) and, when this phone is paused, `· Paused until 14:30`.
- **Network:** a network callback watches for Wi-Fi and keeps track of every Wi-Fi network that is up. When Wi-Fi becomes available, the service connects over the newest one. When that one is lost and another Wi-Fi network is still up, it moves to that one; only when the last one is gone does it close cleanly, say "Not on Wi-Fi" and stop trying.
- Returns `START_STICKY`, so Android may restart it if it's killed. OEM battery managers often prevent that.
- **Wake locks:** none while idle. During a transfer, a partial wake lock is held only while bytes are moving.

## Links (built in 2B.1)

The `link` message ([protocol.md](protocol.md#links-link)) in both directions. Code: `links/` (`LinkRules`, `LinkOpener`, `LinkOpenActivity`, `LinkNotifications`, `LinkNotificationContent`), `protocol/LinkWire.kt`, `IncomingHandler.onLink`, `OutgoingSender.sendLink`.

### Receiving a link (PC → phone)

- **Checked again.** `MessageReceiver` validates `url` as sent (the openable-URL rule with no trimming, `http` or `https` only, at most 8 KiB) and cleans `title` and `sourceApp` (bidi controls to `_`, control characters to a space, collapsed, 300 and 64 code points); a bad link is `bad_request` with `ref`, the connection stays open and the ID is not remembered. `IncomingHandler.onLink` runs the rule once more before anything is shown. The URL is never rewritten: a YouTube `t=83s` reaches the opener as the same string.
- **The notification** (channel *Arrivals*, one per link): the page title on the first line and **the real address on the second line, in the collapsed and the expanded form**. The address comes from the URL (`LinkDomain`), never from the title, so a title like "https://accounts.google.com - Sign in" can't pass for the address. The address is **the host a browser connects to** ([protocol.md](protocol.md#showing-the-address-of-a-link), vectors `display[]`): lower case, an international name in its UTS 46 (non-transitional) punycode form (`android.icu.text.IDNA`, API 24+; `java.net.IDN` is IDNA 2003 and gives other answers), an IPv4 address in any spelling as dotted decimal, IPv6 compressed, the port only when it is not the scheme's default; a host a browser refuses is shown as written with every non-ASCII character as U+FFFD. It is marked with a warning sign when the host as written is non-ASCII, the shown host has an `xn--` label, the shown host is an IP address, or a browser refuses it (plain ASCII look-alikes such as `paypa1.com` are not detected on purpose). A URL with user information (`https://google.com@evil.example`), a backslash or a percent-escape in the authority (a browser reads `https://evil.example\@google.com` as `evil.example`, Android as `google.com`) is **not accepted at all** (changelog 55): the phone refuses it on receive, on a share (the text goes to the PC as plain text, `isUrl` false), on the tap and on Copy link. With no title the address is the title line. The expanded text is the address, the URL shortened to 200 characters (bidi and invisible characters replaced) and "From <PC>". The sub text says what a tap does: **"Open in YouTube"** when Kin can see a non-browser app that handles the link, and the neutral **"Open link"** otherwise (never "browser": a tap may still open an app Kin can't see).
- **The tap opens the link at once** (one tap after the notification: no auto-open, no "display over other apps"). The tap starts `LinkOpenActivity` (our own transparent activity: Android 12 and later refuse a notification that starts an activity through a service or a receiver, and the plan needs code at tap time for its fallback). On **Android 11 and later** it tries `ACTION_VIEW` with `FLAG_ACTIVITY_REQUIRE_NON_BROWSER` first (the system picks an app that owns the link) and falls back to the default browser when none does. On **Android 10** that flag doesn't exist, so a resolve check (`queryIntentActivities`, browsers found by resolving `http://` with no host, then removed) finds the non-browser apps: the system's pick if it is one, else the first, opened by package; with none the default browser gets it. Nothing can open it: a toast says "No app can open this link. Use Copy link."
- **`<queries>`** declares `ACTION_VIEW` of plain `https` and `http` (BROWSABLE: the web browsers, which the Android 10 resolve check needs in order to tell a browser from an app that owns a link) and, one entry each, **a list of well-known hosts** (youtube.com, youtu.be, open.spotify.com, x.com, reddit.com, instagram.com, tiktok.com, github.com and about forty more). **`QUERY_ALL_PACKAGES` is not used.** *Why the host list (found on the emulator):* a query that names only the scheme does **not** show an app whose filter has a host (YouTube's has `www.youtube.com`): the label stayed "Open in browser" for an app that owned the link. Naming the host makes that app visible. A site that is not on the list still opens in its app on a tap; only the label is the neutral "Open link". The debug build adds the host of the test app.
- **On Android 12 and later a web link goes to an app only if that app is verified for the host or the user approved it** (Settings > Apps > Open by default), so `FLAG_ACTIVITY_REQUIRE_NON_BROWSER` fails for any other app and the default browser takes it. YouTube is verified for youtube.com; the emulator test app is approved with `pm set-app-links` first.
- **The only button is "Copy link"** (a broadcast to `TransferActionReceiver`, which writes the clipboard from the background, allowed on every version). There is **no "Open in browser" button** (the user rejected it as redundant), and a link is **never** put on the clipboard or opened by itself.
- **Grouped.** Several links in a row share one group (`kin_links`) with a summary "N links from <PC>" listing their **addresses**, never their titles; at most 10 link notifications stay up (a new one beyond the cap takes the place of the oldest, `NotificationLedger`, as for the file arrivals), and the summary is posted at most once a second with the last request always posted (`TrailingThrottle`).
- **Lock screen.** The setting **"Show link previews on the lock screen"** (Settings, default **off**) decides the notification's visibility: off is `VISIBILITY_PRIVATE` with a public version that says only "Link from <PC>" (no title and no address); on is `VISIBILITY_PUBLIC`. **Android applies `VISIBILITY_PRIVATE` only when the phone's own lock-screen setting hides sensitive notification content** (Settings > Notifications > Lock screen; the AOSP emulator default shows everything, many phones hide by default), which Kin can't change; the Settings text says so.
- **History and logs.** The address and the cleaned title go to the history (a text row of kind `link`; tap copies the URL, as for texts). **No URL is ever logged** (protocol.md): the log has the scheme, the length of the URL, the length of the title and whether the address was marked.

### Sending a link (phone → PC)

- **The share sheet.** `ShareActivity` sends a **text that is exactly one web link** (after trimming) as a `link`, with the page title from `EXTRA_SUBJECT` (browsers) or else `EXTRA_TITLE`; a sentence with a link in it, two links, `javascript:` and a sensitive text stay a `text`. The "Send to PC" text menu and the clipboard send stay texts (an explicit text is sent as it is).
- **Same queue as a text.** A link is saved as `queued` first (the `texts` table, kind `link`, with the title; database version 5), waits for the PC and goes out in creation order after the `hello`, for at most 7 days, with an ack of 5 s and a re-queue without one. A URL that fails the rule is never queued: the user is told "That isn't a web link."
- **Old PCs.** The phone's `hello` lists `capabilities: ["link"]`, and the PC's latest accepted `hello` of the connection decides: a `link` goes as a `link` to a PC that lists it and as the bare URL in a **`text`** (same ID, `isUrl` true, no title) to any other. The choice is made **when the message goes on the wire** (`TextOutbox.sendOne`), so a link queued for an old PC goes out as a link after the PC updates. In the phone's own history it stays a link either way.
- **The PC decides** whether to open it (its setting "Open links from phone automatically", windows.md).

## Notification mirroring (built in 2B.2)

Phone notifications go to the PC's toasts ([protocol.md "Notifications"](protocol.md#notifications-notif)). Opt-in, per app, nothing stored. Code: `notifmirror/`, `protocol/NotifInbound.kt` (a stand-in for the PC's receiver, used by the test vectors only), `ui/MirrorScreens.kt`.

- **Listener.** `MirrorListenerService` is declared with `BIND_NOTIFICATION_LISTENER_SERVICE`. Access is a *special access* (no runtime permission): the user turns Kin on in the system's Notification access list. `onListenerDisconnected` asks once for a rebind. The callbacks only queue the notification (a `Channel`); one coroutine takes them in order, so a post and its removal never swap. A release build mirrors nothing of Kin's own; a debug build also mirrors Kin's own channels `kin_debug_mirror*` (the test notifications).
- **Allow list (default: every app off).** `MirrorPolicyStore` (a DataStore of its own, `kin_mirror`): master switch, allowed packages, packages allowed to show notifications hidden on the lock screen, "Dismiss on the phone too" (default on), "setup shown". **Nothing else is stored**: no content, no `nid`. The picker lists the apps with a launcher icon (`<queries>` has one `MAIN`/`LAUNCHER` entry; no `QUERY_ALL_PACKAGES`) plus the allowed apps that have none (label = package name). `AppCatalog` sorts them: messaging apps (a table; ticked on the first run), likely-sensitive apps (a table of authenticators, password managers, wallets and payments, or a whole word of the label or of a package segment such as `bank`, `wallet`, `otp`, `password`, `pay`: off, with a warning and a confirmation) and the rest. **A likely-sensitive app that the user allows sends only its app name** (no title, text, actions or code): the post is `sensitive` and its `title` is the app name (a post with nothing to show is `bad_request`, and the app name is no content). The same goes for a notification hidden on the lock screen that the user allowed for its app.
- **Skip rules (`MirrorFilter`, in this order).** Own package; not allowed; other profile (these three run on cheap fields before anything is read); ongoing, foreground service or not clearable; group summary; local only; media (2B.3); categories progress, service, system, status, **alarm, call**, navigation, or a determinate progress bar (calls and alarms are never mirrored in 0.2.0); minimum importance or a suspended app; hidden on the lock screen (the user's lock-screen choice for that notification beats the app's) unless allowed for the app; nothing to show. Removal: every reason except Kin's own cancel (10, 11) and the system regrouping (13, 16); a tap removes the toast.
- **What is read.** Title, text, big text, sub text, MessagingStyle messages (last 5, oldest first, own messages without a sender, `[Photo]` / `[Attachment]` for media-only; the `Person` only for its name and whether it has a contact URI), inbox lines, actions. **Never:** the large icon, pictures, `EXTRA_PEOPLE`, `Person.key`, data URIs, bubble metadata. Strings are cleaned and cut to the protocol's limits by the sender too (`NotifEncoder`, `LinkWire.cleanText`); a frame is cut to 16 KiB (big text, then lines, then the oldest messages).
- **Identity.** `nid` = the first 32 hex characters of SHA-256 of the notification key. The raw key never leaves the phone; the `nid` to key map is in memory only, and an action recomputes it from `getActiveNotifications()` when the map has no entry.
- **Reply and buttons (`NotifEncoder.pickActions`).** The reply is the first action with a free-form `RemoteInput` (the reply semantic wins), its hint the cleaned label of that input. At most 3 buttons: a title, no remote input, a `PendingIntent` that is not known to start an activity (API 31+: `PendingIntent.isActivity()`; API 29 and 30 can't tell, so the action is kept and a failure is reported), not contextual. Android blocks an activity started from a listener in the background (silently), so "Open" is never offered. `ActionHandler` answers `notif.action` in the order of protocol.md: `not_found`, `disabled`, `stale` (index and **cleaned title, or for a reply the cleaned remote-input label, must be what the PC showed**), `bad_request`, fire. A repeated ID gets the stored answer and never fires twice; at most 10 per 10 s; `ack` means "sent to the app". `notif.dismiss` calls `cancelNotification` (setting on, clearable) and the removal that follows is not echoed.
- **One-time codes (`OtpDetector`).** Phone only. A keyword of the 11 language groups (`OtpKeywords`) must be present; candidates are 4 to 8 digits (or `NNN NNN`, `NNNN-NNNN`) or 5 to 8 upper-case letters and digits; digits in any script are folded; not a date, an amount, a phone number, a percentage, a measurement or a year (unless it is alone); promo words kill a candidate; several candidates need one more than 10 characters nearer a keyword (the spec's example "Verification code 123456 or 654321" gives none); a friend's message (a contact URI) is never a code. Chinese, Japanese, Korean and Thai text may touch the digits. No code is sent for a sensitive or redacted post.
- **Android 15+ redaction (`RedactionMatcher`).** The one sign is the system placeholder text (`redacted_notification_message`, 81 translations in `RedactedStrings`, taken from the Android 37 SDK platform) as the text, the big text, a message or a line, on API 35+ only. The post is then `redacted` with the title only, and `notif.status.otpHidden` is true on API 35+. No exemption is attempted.
- **Icons.** The launcher icon drawn at 96 px (64, then 48, if the PNG is over 12,000 bytes so the frame stays under 16 KiB), cached in memory and in `cacheDir/mirror-icons` under a name made from package and version code; `notif.icon` goes once per connection before the first post that uses it. For an app Kin can't see, the notification's small icon on a circle of its colour.
- **Sender (`MirrorSender`).** One lock, no disk. Drops when there is no ready connection, no accepted `hello`, or a PC that does not list `notif` (checked per message). One post per `nid` per second with the last state when the second ends; an identical post is not sent; 20 posts per package per minute (checked first, costs no token); a bucket of 10 refilled 1 per 500 ms; removes exempt up to 50 per 10 s; a remove cancels a pending post and makes the `nid` new again. After each accepted `hello` (also a later one that changes the PC's capabilities): `notif.status` then `notif.sync`. Status changes go out at most once per 5 s. The state is per connection.
- **Battery.** No timers: the 1-second window is a coroutine `delay`, the log line (counts only, at most once a minute and only when something changed) is written by the next event, and a notification that has nowhere to go is not even read.
- **Logs and the export.** Counts only (`mirror: sent N, removed N, dropped {not_allowed: N, ...}`, `mirror: N apps allowed`). Never a title, text, label, reply, code, key, `nid` or the package of an app that is not allowed (a test greps a run's log).
- **UI.** Settings "Show notifications on your PC" (the switch, apps, "Dismiss on the phone too", the state in words), the setup (what it does, apps, access, result; offered once after the reliability setup), the apps list, a Home row while on and a warning card when access is lost. **Restricted setting:** `RestrictedSettings` (a hint from the install source on API 33+, an app-ops probe wrapped in a try, and the steps card whenever access is still missing after the user comes back). The access screen: `ACTION_NOTIFICATION_LISTENER_DETAIL_SETTINGS` with Kin's service on API 30+, the list on API 29.
- **Debug build only.** The Debug screen's "Mirror test" (a: a conversation with a reply, "Mark as read" and an activity "Open"; b: a code; c: ongoing; d: a group; e: hidden on the lock screen; f: low importance; g: a look-alike of the redacted placeholder) and the commands in android/README.md.

## Media controls (built in 2B.3)

What plays on the phone is shown and controlled on the PC, and what plays on the PC on the phone ([protocol.md "Media controls"](protocol.md#media-controls-media)). Both directions are **off by default**, each with its own switch (Settings → Media); nothing about what is playing is stored or logged, only counts. Code: `media/`, `ui/MediaScreens.kt`.
### Phone to PC: reading this phone's media

- **Permission: the notification access of 2B.2, nothing new** (no manifest change, no `MEDIA_CONTENT_CONTROL`). `MediaSessionManager.getActiveSessions` and `addOnActiveSessionsChangedListener` are given Kin's `MirrorListenerService` component; without the access they throw a `SecurityException` (checked on API 29 and 37), which becomes `media.status.access = "missing"` and the "Notification access is off" line. Sharing media does **not** need "Show notifications on your PC" to be on. Turning the switch on without access opens the system's access screen and shows the restricted-setting steps of 2B.2.
- **Only while it can be used.** `MediaSource` registers the listener and one `MediaController.Callback` per session (`onPlaybackStateChanged`, `onMetadataChanged`, `onSessionDestroyed`, `onAudioInfoChanged`) **only while** `share` is on, the access is granted, a connection is ready and the PC's latest `media.status` says `show: true`; it lets go of every controller the moment one of those goes away. **No polling, no wake lock**: the only delays are the 250 ms trailing window, the 1.5 s clear debounce and the one that drops a session paused for 30 minutes. Callbacks only queue an event; one coroutine takes them in order and recomputes the active session once per burst.
- **Which session** (`MediaPick`): not Kin's own, with a title, playing, paused or buffering; the current one stays while it plays; else the first playing one in Android's priority order; else the current one, else the first; none: `media.clear` after 1.5 s. Two sessions of one app count as one. A session paused for 30 minutes is dropped.
- **What is read:** package (only for `sid` and the label), title, artist, album, duration, the art bitmap, state, position, speed, update time, actions, volume. **Never** the `*_URI` keys, the queue, the session's extras (except the debug marker), media ids or ratings. The app label comes from the package manager; an app Kin can't see falls back to the session tag (API 30+, `getTag`) and then to "Media". Kin's own sessions are skipped (the PC-media session would echo back).
- **Wire** (`MediaSnapshot`, `MediaWire`, `MediaMapping`): `sid` = the first 32 hex of SHA-256 of the package name; the position is `position + (now - lastPositionUpdateTime) x speed` at the moment of sending (cut to the duration; -1 is none), `rateMilli` the speed in thousandths (0 to 4,000), the actions from the `PlaybackState` bits (`seek` only with a duration; the vectors `androidMap[]`). A state is re-sent on a change or a seek (position 1,500 ms away from the extrapolation), never on a timer.
- **Art** (`ArtworkEncoder`, `ArtLadder`): the largest of the album art, art and display icon bitmaps, never a URI, re-encoded only when the picture changed (a signature of its size and 64 sampled pixels, because a metadata callback hands over a new copy each time): longest side at most 256 px, JPEG quality 80, 70, 60, 50, then 192 and 128 px, until at most 24,576 bytes; none if even that fails. Hash = first 32 hex of SHA-256 of the JPEG. The last 8 results stay **in memory only**. The app icon goes as `kind icon` (the 2B.2 drawing code, **no disk cache**), once per connection.
- **Sender** (`MediaSender`): peer-status gate, 250 ms trailing throttle (identical state not sent), bucket 10 / 250 ms, an image before the first state that uses it on a connection (and again after a `media.clear`), at most 20 images per 60 s, clear debounce 1.5 s, one `media.clear` when `share` is turned off, `media.status` at most once per 5 s. It never starts `LinkService`; with no connection it drops and counts.
- **Commands from the PC** (`MediaCommandRunner`): `disabled`, `rate_limited`, `not_found`, `stale`, `action_failed`, in that order; success has no reply. A listener's controller may use `transportControls` (checked on API 29 and 37). Volume is the **phone's `STREAM_MUSIC`** (`AudioManager`, no UI flag), or the session's own for a cast route; the lowest level a `level` or `delta` sets is index 1 (only `mute` silences), every call is wrapped (`SecurityException` is `action_failed`), a `delta` moves at least one step. The new volume goes back as `media.volume`; changes made on the phone itself are not watched (no public callback), so the PC's slider is as fresh as the last state.

### PC to phone: the PC's media on this phone

- **One `MediaSession` ("kin-pc-media") and a `MediaStyle` notification** (channel `kin_pc_media`, low importance, silent, one ID, local only). It plays **nothing**: no `MediaPlayer`, no audio focus, **no `mediaPlayback` foreground service** and no new permission; the notification is posted from the process the link service already holds. Testing found that this is enough for the quick-settings carousel on Android 17 and the shade on Android 10.
- Title line = the title (else the app); second line = `<artist> · <PC name>`; sub text `<app> on <PC name>`; the picture is the large icon and the session art (decoded with a bounded decoder: rejected over 512 px or 2 MiB). The buttons come from the session's `PlaybackState` actions on Android 13+ and from the notification's own actions before. A press sends one `media.cmd` (`play` or `toggle`, `pause`, `next`, `prev`, `seek`) and has **no local effect**: the PC's next `media.state` moves the display. The session reports `playing` while the PC plays (user decision 2). The progress bar is drawn by System UI from the position and speed; a playing state 5 s past its end with nothing new is shown paused (one delay).
- **Lock screen:** `VISIBILITY_PRIVATE` with a public version that says only "Media from <PC>" unless "Show PC media on the lock screen" is on; Android applies it only when the phone's own setting hides sensitive content. A swiped-away notification stays away until the PC plays again or the track changes.
- **Volume keys** (user decision 3, off by default): with the switch on and a PC volume known, the session is a remote one (`VolumeProvider`, absolute, 100) and the phone's volume keys send `media.cmd volume` (`delta` +-5 or `level`); while the PC session is playing it takes the keys, even if a local player also plays. With the switch off the volume is a slider on the Home card.
- **Everything is removed** (`release`, notification cancelled, art dropped) on `media.clear`, on connection close, when `show` goes off, on unpair, and when the notification permission is missing (the card line says so).
- **Limits:** a viewer takes states at a bucket of 20 refilled 5 per second (over it: dropped, counted, one `rate_limited` error without `ref` per 10 s); a viewer whose `show` is off drops state, image, clear and volume silently.

### Settings, Home, logs

- **Settings → Media:** "Show this phone's media on your PC" (one switch for every app), "Show your PC's media on this phone", "Show PC media on the lock screen", "Use the phone's volume keys for the PC", with a line under each that says what is wrong (access off, PC not showing, PC needs 0.2.0, notifications off). **Home** has a card while either direction is on: while the PC's media is shown, its art, title and "on <PC>", previous / play-pause / next (the same `media.cmd` kinds as the notification) and the PC's volume slider. Showing the title in the open app was decided on 2026-10-26 (Sam); the logs still never carry it. Four booleans in a DataStore of their own (`kin_media`); nothing else is stored.
- **Logs:** counts only, at most one line a minute and only when something changed: `media: sent N states, N images, N cmds, shown N states, N cmds in, dropped {...}`, and `media: share on`. No title, artist, album, app name, `sid` or art (a unit test and the emulator run grep for them).
- **Skip rule (2B.2):** the PC-media notification is Kin's own (rule 1) and a `MediaStyle` one (rule 7), so it is never mirrored as a notification.

## Presence, Pause, Ring, Screenshots (built in 2B.4)

[protocol.md "Presence, pause and ring"](protocol.md#presence-pause-and-ring) (changelog 58). Code: `presence/`, `pause/`, `ring/`, `shots/`, `features/`, `ui/PresenceScreens.kt`. Nothing about the PC's battery or pause, and no screenshot name or path, is ever stored or logged: counts and enums only (a unit test greps the code for it).

### Presence (battery and pause, both ways)

- **Capabilities.** The phone's `hello` lists `link, notif, media, presence, alert` (2B.5 added `alert`) and, **only while "Let my PC ring this phone" is on, `ring`**. A change of that switch while connected goes out as a new `hello` on the open connection (`LinkConnection.updateCapabilities`, a no-op when the list is the same; **a change made before the PC's `hello` was accepted is now said once it is**: the first `hello` carries what is wanted at that moment, and a later change goes out right after the handshake). `presence` goes only to a PC whose latest `hello` lists it, checked per message.
- **Sending** (`PresenceSender`, the only writer): one snapshot of "what is true about me" (`battery {level, charging, saver}`, `pause`) right after both `hello`s (even `{}`), then on change. A battery-only change goes when the level moved 2 points from the last **sent** one, crossed 15, 20 or 100, or `charging` / `saver` flipped, **at most once per 30 s** (the latest value goes at the end of the window if it is still a change); a pause change **1 s after the first change of a burst** (nothing if it nets to nothing), never held back by the battery limit; a timed pause's end **at that moment** (one `delay` of `PauseController`). **No periodic timer.** The battery is a sticky read plus a dynamic receiver for `ACTION_BATTERY_CHANGED` and `ACTION_POWER_SAVE_MODE_CHANGED` **registered only while a session is ready and "Share this phone's battery" is on**; the system does the broadcasting.
- **Receiving** (`PresenceHub`): a bucket of 10 refilled 1 per 3 s per connection, one `error rate_limited` per 10 s; a snapshot **replaces** the previous one; the PC's pause is kept as `arrival (monotonic) + remainingMs` (`PeerPauseView`) and ends at that time, or when a snapshot without `pause` arrives; a closed connection forgets it. The PC's battery is shown (a laptop only) and the last one is kept in memory until Kin quits.
- **Where it shows.** The persistent notification: `Connected to Desk PC · 82% · charging · Kin paused on the PC until 14:30` (a battery-only change is posted at most once per 30 s, a state or pause change at once; the switch "Show your PC's status here" hides it), and the same words on Home. The low-battery state machine (`LowBatteryNudge`) drives the phone's nudge for a laptop since 2B.5 (below).

### Pause

- **One persisted state** (`PauseStore`, DataStore `kin_pause`: `paused_until_ms`, `until_resumed`), read at service start, so it survives a restart and a reboot. `PauseController.paused()` is **a wall-clock comparison** read at each entry of an automatic feature, so nothing is started or stopped by pausing and no timer is needed to resume; a `pausedUntil` more than 8 days ahead counts as expired. Choices: **1 hour**, **until tomorrow** (the next 08:00 local time at least 2 hours away, built from the local date so a daylight-saving change in between still ends at 08:00 on the wall), **until I resume**. A second pause replaces the first; unlinking the last peer clears it. **After a time-zone change** (a flight, a manual change) a stored "until tomorrow" still ends at **08:00 of the zone it was set in**, because only the end instant is stored; a new pause made after the change uses the new zone. What the tile, Home and the notification show is **read from the wall clock each time** (`PauseController.viewNow()`), not from the last published view, so a pause that ended while the phone was in deep sleep shows as ended at once. If the stored pause can't be read at start, Kin starts not paused (the gates never wait for ever).
- **What stops** (this phone paused **or** the PC paused, for what the phone sends): `MirrorSender` drops `notif.post` (not `notif.remove` / `notif.sync`); `MediaHub` acts as both media switches being off (one `media.clear`, `media.status` says so, the viewer removes what it shows and drops the rest); `ShotController` sends nothing and **moves the baseline up**; the PC-to-phone automatic `clipboard` is dropped at the receiver too. **Ring, `presence`, `unpair`, `ping`, `ack`, `error` and transfers in flight are unchanged.**
- **Manual arrivals are quiet** (`IncomingHandler`, `TransferNotifications`): a `text`, `link` or file from the PC is recorded in the history as usual, and **no notification or toast appears, the clipboard is not written (the loop guard is not armed either), no link is opened**; files are saved. Home counts them ("3 received while paused", in memory, reset on resume). A download's progress notification stays; its "arrived" notification does not.
- **Where to pause.** The "Pause Kin" tile (`PauseTile`: tap = pause 1 hour or resume, `STATE_ACTIVE` with the end as its subtitle; **pausing works on a locked phone, resuming asks for the unlock first, the same for the notification's button** (2B.5 review: pausing only makes Kin quieter; resuming turns auto-send, Do Not Disturb following and alerts back on. The tile uses `unlockAndRun` when it is paused; the notification's action is rebuilt with each change of the pause and has `setAuthenticationRequired(true)` only while it says "Resume"); long-press opens `PauseSettingsActivity`), the notification's "Pause 1 h" / "Resume" (its second and last action), the Home card, and Settings (with "Add the Pause tile": `StatusBarManager.requestAddTileService` on Android 13+, the steps as text below that).

### Ring my phone

- **Where it lives.** `RingController` inside the process `LinkService` holds: **no new foreground-service type**, no `FOREGROUND_SERVICE_MEDIA_PLAYBACK`. `ring.start` and `ring.stop` are acked and de-duplicated (only an `ack` is remembered; `disabled` and `rate_limited` are not), never queued and never re-sent. The phone answers `disabled` itself when its own `hello` lacks `ring`, `rate_limited` beyond 3 starts in 60 s or during the 60 s lock-out after the 2-minute continuous cap; otherwise the `ack` goes out once the sound is running, then `ring.status ringing {audible}`. It stops after 30 s, on Stop, on `ring.stop` and at the cap, each with a `ring.status stopped {reason}`.
- **Sound.** `MediaPlayer` on `USAGE_ALARM` (independent of the ringer mode: a phone on silent rings), the default alarm sound, else the default ringtone, else the bundled tone `res/raw/kin_ring.wav`; looping; a vibration on the alarm usage (800 ms on, 400 ms off); **no audio-focus request**; one partial wake lock with a 35 s timeout while ringing. `audible: false` when Do Not Disturb silences the alarm stream: "total silence", **or Priority mode when the user's own policy does not allow alarms** (`AlarmAudibility.silenced(filter, policy.priorityCategories)`, shared with the 2B.5 code; Priority with alarms allowed, the default, and Alarms only play). **The alarm volume** is saved to DataStore (`ring_saved_alarm_index`) **before** it is raised to the maximum (setting "Ring at maximum volume", on by default), and put back on every stop **and at every app start (`AppGraph.warmUp`, with or without a paired PC) and every `LinkService` start** while a saved value is still there (a crash mid-ring); never touched on a volume-fixed device. **Not saved or raised under a Do Not Disturb that silences the alarm** (nothing could be heard, and the platform may refuse the change), and **the saved value is cleared only if the volume really changed back** (it is read again after the call): a refusal keeps it and the next start tries again. The Stop notification is **always** taken down by Stop and at every start (a ring that died with its process left it behind); a replaced timer carries a generation number and can't stop a ring that was extended. No `FLAG_SHOW_UI`.
- **The Stop screen.** Channel `kin_ring` (high, no sound or vibration of its own), `CATEGORY_ALARM`, ongoing, `VISIBILITY_PUBLIC` with a text that says only "<PC> is ringing your phone", a **Stop** action, and a **full-screen intent** to `RingActivity` (over the lock screen, keeps the screen on, one huge Stop button, a countdown). The notification is **not** marked silent (`setSilent(true)` puts it in androidx's muted group, which suppresses the heads-up and the full-screen intent; the channel already has no sound), and **a restarted ring (a second `ring.start` while ringing) posts it again** with the new end (same id), so the Stop button and the countdown last as long as the sound; its own timeout is the 2-minute cap plus 5 s, only a safety net. **On Android 14+ the full-screen intent is limited to calling and alarm apps** (Google Play revokes `USE_FULL_SCREEN_INTENT` from other apps): when `canUseFullScreenIntent()` is false the notification **still posts, as a heads-up with its Stop button**, and Settings shows "Show the Stop screen on a locked phone" (`ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`). Ringing never depends on it. With the notification permission denied the ring still sounds.
- **Debug.** `RING_SET --ez silent true` (`files/debug-ring-silent`): no player, no vibrator, **the alarm volume is not touched**; the save / raise / restore order is unit-tested on fake ports.

### Auto-send screenshots (opt-in, `shots/`)

- **Turning it on** (Settings "Screenshots": "Send screenshots to your PC", "Also send new camera photos", both off by default): a dialog says what is read, the permission is asked **now** (`READ_MEDIA_IMAGES` on 13+, `READ_EXTERNAL_STORAGE` on 10 to 12; never at start-up), a **baseline** (the highest `_ID` of `MediaStore.Images`, one number) is taken, and the phone **refuses if the PC's `hello` lacks `presence`** (an old PC would put the screenshot on its clipboard and in Windows clipboard history). Kin does **not** declare `READ_MEDIA_VISUAL_USER_SELECTED`, `ACCESS_MEDIA_LOCATION`, `READ_MEDIA_VIDEO` or `MANAGE_EXTERNAL_STORAGE`. The permission is read from the system **at each use and never stored**: Android 14's "Select photos" is a session-only grant that can't work for a background watcher, so a partial or revoked grant shows "Needs access to all photos" (Settings and Home) and no observer runs.
- **Detection.** A `ContentObserver` on `MediaStore.Images` registered **only while** a switch is on, the access is held, a PC is paired and `LinkService` runs; no polling, no timer. Events are coalesced 500 ms. `ShotPicker` decides per row from `_ID`, `RELATIVE_PATH`, `MIME_TYPE`, `IS_PENDING`, `DATE_ADDED`, `SIZE` and `OWNER_PACKAGE_NAME` only (never the file path, EXIF, location or a thumbnail): old / handled, pending, not an image, **older than 15 s** (a re-index), **Kin's own folders** (`Pictures/Kin/`, `Download/Kin/`: received files are never sent back), a screenshot (a path with "screenshot" in it, or owned by `com.android.systemui`), a camera photo (`DCIM/Camera`), anything else never; then the pause (skipped and the baseline moves) and a bucket of 5 refilled 1 per 20 s. An image whose `DATE_TAKEN` is **older than the moment the baseline was taken** (an old screenshot copied in: fresh `DATE_ADDED`, old date taken) is skipped as `old`; that moment is stored as one number next to the baseline. **The baseline moves past every image with a final decision** (sent, cancelled, or skipped for any reason), in `_ID` order, **and stops at the first one still pending** (an `IS_PENDING` row, or an image waiting out its hold); the query returns at most 50 rows, so a pass asks again from the last row until a page is not full (a run of more than 50 skipped images can't stall the watcher). A row stuck `IS_PENDING` for more than 15 s is decided as `stale`.
- **The hold.** A notification "Sending screenshot (or photo) to <PC> in 5 s" / "Tap to cancel" with **Cancel**, on its own channel **`kin_shot_hold`** (2B.5: importance high, no sound, vibration or badge, so it comes up as a heads-up with the button visible; a tap on it also cancels; sending and the result stay on *File transfers*) (a cancelled one never comes back: the baseline moves). **It is shown only if it can really be seen** (`POST_NOTIFICATIONS` granted, the app's notifications on, the `kin_shot_hold` channel not blocked): otherwise there would be no Cancel, so the image is **not sent** (skipped as `no_hold`, the baseline moves past it), the observer isn't registered, turning the switch on is refused, and Settings and Home say **"Needs notifications"**. The hold has one owner at a time: the 5-second job **claims** it (and replaces the notification with a non-cancellable "Sending…") or the Cancel button removes it, whichever comes first, under a short lock that no upload ever holds; a Cancel after the claim does nothing and leaves "Sending…" / "Sent" alone. After 5 s it is uploaded through the transfer engine with `origin` in `POST /v1/transfers` (database version 6: `transfers.origin`) **under a generic name** ("Screenshot 2026-10-17 14.32.05.png", "Photo …": the time only; a real screenshot name says which app it came from, and none is stored in the history). **Never queued, never resumed later**: with no ready connection after the hold, or if the PC doesn't answer the first `POST` within 5 s, it is cancelled and counted; a leftover queued **or active** one of an earlier connection is ended as "not sent" when the next connection comes up, and the queue flush never starts it. Hold notifications of an earlier run of the process are taken away at app start. No progress or result notification of the transfer engine is shown for an `origin` upload (the hold's own notification says "Sent" or "Not sent: PC away").
- **Play.** `-PkinAutoSendShots=false` builds without the feature: `BuildConfig.AUTO_SEND_SHOTS` is false (no switch, no watcher) and `src/noshots/AndroidManifest.xml` removes both photo permissions. A source set has one manifest, so for the **debug** build `build.gradle.kts` writes a copy of `src/debug/AndroidManifest.xml` with the same two removals to `build/generated/kin-noshots/` and uses that one (the overlay used to replace the debug manifest and a debug build lost its debug receivers); the release build uses the overlay as it is.
- **The hold notification and a drop mid-upload (2B.4 review).** The 5-second hold has a group key of its own per screenshot (without one Android grouped it under the persistent notification and Cancel showed only after expanding). **An upload with an `origin` ends as "not sent" the first time the connection is lost** (`UploadRunner`: the retry branch and a recovered `active` one); it used to wait up to 15 minutes for a reconnect and resume without looking at Pause. `TransferEngine.createUpload` marks the id as being created from before the row exists until its job is registered, so a connection coming up in that gap can't end a brand-new auto-sent upload (`endAutoSentUnfinished` skips it).

### Unlinking

"Unpair" is "Unlink" on Home and in Settings, with a confirmation that says what happens ("This phone and the PC stop working together right away: no sending, notifications or ringing. Your history stays on this phone. You can pair again with a new code."); "Remove this PC" stays on the `PairAgain` card. `LinkController.unpair` and `onPeerUnpaired` (the PC removed this phone) both call `AppGraph.peerGone`, which **checkpoints the database first** (`Durable.flush`: `PRAGMA wal_checkpoint(FULL)`, also after pairing, so a power cut can't bring a removed PC back or lose a new pairing), ends the transfers, deletes the peer's feature overrides, clears the pause, drops the screenshot baseline and switches, stops a ring with the alarm volume put back, and (2B.5) releases a held Do Not Disturb and forgets what it knew of the PC's battery.

### Per-feature settings (`features/Features.kt`)

`Features.enabled(featureId, peer)` is the override for that peer, else the default (today's flat key). Override store: DataStore `kin_features`, one key `feature_overrides` (`{ "<peerDeviceId>": { "<featureId>": true|false } }`), empty and with no UI in 2B.4; unlinking a peer deletes its overrides. Ids: `text.autoCopy`, `notif.share`, `media.share`, `media.show`, `presence.share`, `presence.show`, `ring.allow`, `shots.screenshots`, `shots.camera`, and (2B.5) `dnd.follow`, `dnd.share`. The new switches' defaults live in `kin_presence` (`presence_share_battery`, `presence_show_pc`, `ring_allow`, `ring_loud`, `ring_saved_alarm_index`) and `kin_shots` (`shots_screenshots`, `shots_camera`, `shots_baseline`), and **only `Features` reads them as feature switches** (a grep test).

## Focus, Do Not Disturb and alerts (built in 2B.5)

[protocol.md "Do Not Disturb and Focus" and "Alerts"](protocol.md) (changelog 59). Code: `dnd/`, `alerts/`, `presence/PcBatteryNudge.kt`, `ui/DndScreens.kt`. **No Focus or Do Not Disturb history and no alert text is ever stored in a log** (a unit test greps the code), and the Do Not Disturb stores keep only the switches and Kin's own record of its silence.

### PC Focus to phone Do Not Disturb (`dnd/`)

- **What it does.** Setting "Silence this phone while my PC is in Focus" (`dnd.follow`, **off** by default) with "How much": **Priority only** (default) or **Alarms only**. **Never total silence**: it would mute the alarm and "Ring my phone". When the PC's `presence` says `focus: true` the phone asks for that filter, and gives it back when the PC leaves Focus. **Kin only adds silence and only removes its own**: if the phone is already in some Do Not Disturb when the PC enters Focus, nothing is changed and nothing is held; if the user changes or turns off Do Not Disturb while Kin holds, Kin lets go and does not re-apply until the next time the PC *enters* Focus.
- **Pieces.** `DndWire` (the maps `dndMap[]`, `dndRequest[]`, and `AlarmAudibility`), `DndFollower` (pure: the rules of design 4.2 as a state machine over events, run against every timeline of `alerts.json` `dndFollow[]`), `DndApplier` (the one writer of the filter; pure over `DndPorts`), `DndStore` (DataStore `kin_dnd`: the two switches, "How much", and `we_hold` / `held_filter` / `held_route`, written **before** the request and cleared on release), `DndController` (wiring: one inbox, so events never interleave; the reader; the 60 s grace is one one-shot timer), `DndWatchdog` + `DndAlarm` + `DndWatchdogReceiver` (2B.5 review: while Kin holds, one inexact `ELAPSED_REALTIME_WAKEUP` alarm backs the grace and the link's dead-link detection up, because neither a coroutine `delay` nor OkHttp's ping runs while the phone is in deep sleep: at the grace's end the follower releases; a connected PC silent for 240 s gets a probe, `checkAlive`, and no answer starts the grace; the alarm is cancelled when nothing is held; the bound is 240 s + probe 10 s + grace 60 s = 310 s as set, **about 5 minutes awake and, because `setAndAllowWhileIdle` may fire up to 0.75 of its delay late, realistically up to about 9 minutes with the phone asleep**). `DndFollower` starts a hold only on a **live connection**: a pause that releases during the grace forgets the remembered Focus, and the controller reads the filter again before a pause or resume is evaluated.
- **Release.** On `focus` absent, on a peer whose `hello` no longer lists `presence`, **60 s after the connection closed** (a snapshot clears the timer), on **pause** of this phone, switch off, **unlink**, **access lost**, user override, and **at every start** (`AppGraph.warmUp`, every `LinkService` start): a `we_hold` that outlived the process is released then. A release that can't be made (the access is gone) keeps the record and a "release owed" flag (`DndReleaseGuard`): it is tried again on the access-changed broadcast, on the watchdog alarm **only while access exists** (with no access the alarm is not re-armed, so a phone with revoked access is not woken every 5 minutes for ever), at the service start and at the next app start. The "release owed" flag is **persisted with the `we_hold` record** (`release_owed` in the `kin_dnd` DataStore, additive; absent reads as "nothing owed"), so a process that dies while a release is owed still owes it at the next start. With access present but the call keeping being refused, the retry alarm **backs off** (5, 10, 20, then 40 minutes) and then stops; the access-changed broadcast, a service start, an app start and "Release now" remain and start the ladder again. A follower rebuilt around a persisted hold expects the filter Kin **saved** (`held_filter`), not the current "How much" setting. A screenshot's notifications use the screenshot's own id as the notification slot (`ShotNotificationIds`, with the `kin-shot` tag), so two can never share one. **While a release is owed, any filter other than the one Kin set is the user's change**: the record and the debt are cleared, so the retry can never switch off the user's own Do Not Disturb (Android 10 to 14). On Android 15+ a user's change with Kin's own rule still on (and no access to switch it off) keeps the record: the rule is Kin's to take off. **After a force-stop the silence stays until Kin is opened again** (Android keeps Kin's rule; Kin can't run to give it back), and Settings says so. Settings shows "Silenced by Kin (Priority only)", the level **actually held** (not the "How much" setting), with **Release now** while Kin holds, and Home says so too.
- **Which access.** `DndApplier.path()`: Do Not Disturb access (`isNotificationPolicyAccessGranted` → `NotificationManager.setInterruptionFilter`), else the bound listener (`requestInterruptionFilter`), else nothing, and Settings opens the system's **Do Not Disturb access** screen (never the notification-access one), with the text "Kin can turn Do Not Disturb on and off. It cannot read your notifications." **Both routes work on API 29 and 37, and the platform reports policy access as granted for an app that has notification access**, so a user who already gave Kin notification access for mirroring is asked for nothing. The access is asked for **only when the user turns the feature on** and none exists, never at start-up. `ACCESS_NOTIFICATION_POLICY` is declared (it only names the special access).
- **On Android 15+ (Kin targets 37)** neither call changes the *global* filter: the system makes or updates **Kin's own rule**, "Do Not Disturb (Kin)" ("Managed by Kin"), listed in Settings → Modes; the effective filter is the most restrictive of all active rules. `ruleModel` = `SDK_INT >= 35`. Releasing there is `setInterruptionFilter(ALL)`, which deactivates only Kin's rule. On 10 to 14 the global filter changes, and a release restores `ALL` **only if the filter is still the one Kin set**.
- **The reader.** `NotificationManager.getCurrentInterruptionFilter()` once per ready session and a dynamic receiver for `ACTION_INTERRUPTION_FILTER_CHANGED` and `ACTION_NOTIFICATION_POLICY_ACCESS_GRANTED_CHANGED`, **registered only while a session is ready and one of the two switches is on**. Neither needs notification access; `MirrorListenerService` still ignores interruption-filter callbacks. Neither piece starts `LinkService`.

### Phone Do Not Disturb to the PC (`presence.dnd`)

Setting "Tell my PC when this phone is on Do Not Disturb" (`dnd.share`, **off** by default, no access needed). `PresenceSender` puts `dnd` (`priority`, `alarms` or `total`; `ALL` and unknown are left out) into the snapshot, **sent within 1 s of a change (trailing, nets to nothing if undone) and never held back by the battery rule**, like `pause`. It sends the filter whoever set it (the user, a schedule or Kin's own rule: the PC shows "Phone: Do Not Disturb" while Kin holds the phone silent, which is true). **A paused phone leaves `dnd` out** (and ignores a `focus` that arrives in a race).

### Alerts (`alerts/`)

- **`alert`** (PC to phone, capability `alert`, listed in every `hello`): `AlertWire.parse` cleans `text` (required, cut to 300 code points) and `title` (60) with the five steps of `link.title` and cuts `waitedMs` to 7 days; acked, de-duplicated by `id`, **a frame over 4 KiB is `too_large`**, and a bucket of **10 per 60 s (one token back per 6 s, per process, `AlertBudget`)** is asked only for a new valid alert: over it is `error rate_limited` with `ref` and the id is not remembered. The receiver always handles an alert (the capability is the **sender's** rule).
- **What the phone does** (`AlertInbound`): a **history row of kind `alert`** (the `texts` table's `kind` is a plain string: no schema change, no migration; the row reads "title: text"), then a notification on the channel **`kin_alerts`** ("From your PC", default importance): title = the alert's title or the PC's name, text = the alert, sub text = the PC's name (and "· 3 h ago" when it waited over 2 minutes), `VISIBILITY_PRIVATE` with a public version "Alert from <PC>"; **several alerts share one updating notification** (`AlertArrivals`, at most twice a second) and a tap opens History (`MainActivity.EXTRA_TAB`). **No buttons, no clipboard, nothing opened.** While **paused** it is quiet: the history row and the "received while paused" count only. Android's own Do Not Disturb applies to the channel as to any other: Kin never overrides it.
- **The PC's low battery** (`PcBatteryNudge`, in `presence/`): `LowBatteryNudge` over the PC's `presence.battery`, one per discharge episode per PC (at 15 % or less and not charging, re-armed at 20 % or by charging), in memory until Kin quits. It posts "Desk PC battery is 14%" on `kin_alerts`. It is tracked always but **suppressed (without disarming) while "Show your PC's status" is off or this phone is paused**.
- **Logs:** `alerts: received N, shown N, quiet N` and lengths, never a text or title. The counts of presence, ring, screenshots and alerts are also written **once, when the service stops** (counts only).

- On an `offer` the phone checks free space *before* the ack. If the files don't fit it answers with an `error` (`disk_full`) instead of the ack. Otherwise it acks, stores the transfer in Room (`transfers`, `transfer_files`) and downloads on its own coroutine: the WebSocket is never blocked by file I/O.
- Photos go to `Pictures/Kin` and videos to `Movies/Kin` through MediaStore, so they appear in the gallery. Everything else goes to `Download/Kin`. The folder follows the file's extension when that says what it is, and the sender's MIME type only when the extension says nothing (a `.exe` that claims `image/jpeg` is a download).
- Files are written with `IS_PENDING=1`, so half-written files show up nowhere. The flag is cleared when that file is complete, so photos appear one by one.
- **Names:** cleaned per protocol.md ("File names", `FileNames`), then created new, never overwriting. Scoped storage shows the app only its own files, so `existing` is what the app listed plus what unfinished transfers claimed. MediaStore may still rename on insert, and **the name MediaStore chose is the one stored and shown**.
- **Resume:** the pending entry keeps its bytes, and the next `GET` asks for the rest with `Range: bytes=N-` (never for a 0-byte file). N is the entry's real length, not a counter. A `200` to a range request restarts the file at byte 0, a `416` starts it over once. Appending works through `openOutputStream(uri, "wa")` and through a read-write descriptor positioned at the end, on Android 10 and on Android 17, and the app uses the second (it can also cut off a longer entry). The fallback "write in the app's folder and move it" is **not needed**. A brand new pending entry has no file yet: opening it for reading fails with `ENOENT` until it was opened for writing once, so `MediaStoreSink.create` opens it for writing at once. (The emulator found this: without it the app took the entry for deleted and made new ones in a loop. It now also gives up after two re-creations.)
- **A file that fails for good** (`404`, `409`) fails the whole offer: partial files are deleted, a `cancel` with reason `error` goes to the PC, files already saved stay.
- **A dropped connection** is not final. The transfer waits (no wake lock, no polling) for the PC to come back, up to 15 minutes, then goes back to `queued` and resumes when the link is up again.
- When done: `complete` (re-sent with the same ID if not acked) and a notification "Photo from <PC>", "Video from <PC>", "File from <PC>" or "<n> files from <PC>" with Open (the first file) and Share (all of them).

### Sending files

- Share intents only grant temporary access to the shared files, and `ShareActivity` closes at once. It therefore passes the URIs to `LinkService` in the start intent with `FLAG_GRANT_READ_URI_PERMISSION`, and finishes only after the transfer was created. **Verified in 1.3:** the service's grant outlives the activity and the sending app; without it the files are unreadable within seconds (control run). Only `content:` URIs are accepted from an intent.
- **Reading a shared file uses an *unstable* provider client** (`acquireUnstableContentProviderClient`), not `ContentResolver.openFileDescriptor`: that one keeps a stable reference to the provider for as long as the descriptor is open, and Android then kills Kin when the owning app (a gallery) dies mid-upload. Seen on the emulator.
- **Upload:** `POST /v1/transfers`, then one `PUT` per file from its offset. `409 offset_mismatch` continues from the offset the PC returns; `507`, `413`, `500` fail the transfer with no retry; a dropped connection waits and resumes (`POST` again); a source that changed size or modified time means `DELETE` and a new transfer ID. A cancel sends `DELETE` (a `404` on it counts as done).
- **Queued while offline:** the transfer stays `queued` with a "PC not reachable" notification (Retry, Discard), and files under 50 MB are copied into `cacheDir/queue/<local ID>/`. When the link is up the queue flush starts it (1.4). A larger file that lost access fails with "Share it again". The cache folder is named after the transfer's stable **local ID** (`transfers.localId`), not its transfer ID, so it survives a new ID (a changed source starts over under a new one). Cached copies go when the transfer ends, and after 7 days (the queue's expiry).
- **A `404` to `POST` (1.4 ruling):** the PC ended that transfer for good, or the ID belongs to another device, or it was used and is over. An **automatic** resume (a reconnect, the queue) marks the transfer failed ("the PC no longer has it") and **never sends again**. Only the user's **Retry** may: it first `POST`s the old ID (a transfer the PC finished within 24 h is recognised and just finishes), and on `404` sends **only the files that never got a `200`** under a new ID, as a new transfer; the old transfer stays failed and points at it (`retriedAs`), and the cache is shared through the local ID.
- **Free space during a download (1.4):** a new `offer` is checked against what the unfinished downloads *still have to write*, counted from the bytes really written (the in-memory `LiveProgress`), because the phone's free space already shrank by them. The stored `bytesDone` is only saved when a download stops.
- **Progress** is a notification with Cancel, updated at most every 500 ms: "N of M files done · P%" (several files are on the wire at once, so there is no "current file"), and the aggregate of all files in flight for the bar.
- **Wake lock:** a partial wake lock is held only around a `PUT` or a `GET` that moves bytes, and released at once (reference counted, with a 30-minute safety timeout).

### Parallel files (v0.1.1)

A 50-photo batch took 6 to 9 s PC → phone and 7 to 14 s phone → PC against about 3 s for LocalSend (measured with a scripted LocalSend sender on one real phone, version 0.1.0): one file at a time pays the gallery's, the provider's and the connection's round trips for every file. Now **up to 4 files of one transfer are on the wire at once, in both directions** (`TransferTimings.maxParallelFiles`; protocol.md says a client MAY run up to 4 file requests per transfer). Still one transfer at a time per direction (the engine's two locks), and **still one request per file**: a file is never split, so one big file goes exactly as before (one stream, one `GET` or `PUT`).

- **The pool.** `DownloadRunner.downloadAll` and `UploadRunner.uploadAll` start workers that take the next unfinished file, in the order of the list, the moment a slot frees. They run under the attempt's coroutine scope, so the connection watcher, the cancel and the wake lock work as before (the wake lock is counted per request).
- **What ends an attempt.** A file that **fails for good** (`404` or `409` on a `GET`, a `507`/`413`/`500` on a `PUT`, a file that can't be written or read) stops the files in flight and fails the transfer exactly as in 1.3 and 1.4 (an offer: the partial files are deleted, a `cancel` with reason `error` is owed to the PC, files already saved completely stay). A file whose **connection broke**, or that the PC answered oddly (`GET` other than `200`/`206`/`404`/`409`/`416`), fails only **that file for this attempt**: the others go on and finish, then the next attempt (after the usual short delay, or after the PC is back) resumes only what is missing: a `GET` with `Range` from the entry's real length, or a new `POST` whose offsets tell where each `PUT` goes on. Several `409 offset_mismatch` are handled per file.
- **Pipelining, PC → phone.** One producer makes the gallery entries of the next files while the earlier ones download (a channel as long as the pool), so a small file doesn't wait for MediaStore between two requests. Being one producer, it also hands out the names one at a time (two files of one offer may have the same name: each must see what the other took), and the names already in the folder and claimed by other transfers are read **once per attempt** instead of once per file (a gallery query per file grew with the folder).
- **Pipelining, phone → PC.** A producer opens the source of the next files at the offset the PC returned, ahead of their requests. A source that was opened and not used (the attempt ended early) is closed again.
- **The first look at a share.** `enqueueUpload` used to `stat` each shared file one after the other (a content-provider round trip each, about 40 ms for a gallery), and the first attempt did it all over again: about 4 s for 50 photos between the tap and the first byte. Now the looks run 8 at a time (`mapParallel`) and the **first attempt of a transfer made a moment ago skips the second look** (`sourcesJustChecked`); every later attempt (a reconnect, the queue, a Retry) still checks that each file is unchanged, now also 8 at a time.
- **Progress.** One counter adds up the bytes of all files in flight (each file adds what it already had when it starts, and takes it back if a `200` to a `Range` restarts it), plus `LiveProgress` per file (the free-space check of a new `offer` reads it). `files` of a run is replaced as a whole under a lock, because files now finish at the same time.
- **HTTP client.** Each file request is a synchronous call on its own connection (OkHttp's `maxRequestsPerHost` limits only the queued calls, which these are not, but it is set to 16 anyway). The file client has a connection pool of its own: 8 idle connections, kept 20 s (the PC closes a connection that moved nothing for 30 s, and a reused connection it has closed would fail the next request: `retryOnConnectionFailure` is off). TLS 1.3 with a client certificate is the price of a new connection, so the connections of a batch are kept for the next file.
- **Memory.** Nothing is buffered: each file in flight streams through its own 256 KiB buffer (the largest block is 1 MiB for four files).
- **Database.** Room writes are one row per file (the entry made, the file finished) and one `setBytesDone` per unfinished file when a download stops; Room runs them one after another, so there is no contention to manage.
- **Tests.** `ParallelFilesTest` (concurrency of exactly 4, never 5, in both directions; `maxParallelFiles = 1` gives the old order; one file breaking mid-batch while the others finish and only it resumes; a fatal file stopping the others; cancel with several in flight; aggregate progress; same-name files; no source left open; the parallel share look), and the replays of the shared HTTP vectors run with one file at a time (they are one fixed sequence of requests).

### A silent network (v0.1.1 fix)

A router or access point that fails without telling the phone (the packets just stop, no reset) used to fail a transfer for good after about a minute (`connection_lost`, a manual Retry) while the link still said "connected": the WebSocket's own ping goes out only every 240 s (battery) and its pong is waited for another 240 s, so the session stayed "ready" for 4 to 8 minutes and every attempt reused it. Now:

- **Who asks.** `StallGuard.kt` runs beside every attempt of an upload and a download. When no byte has moved for `TransferTimings.stallProbeAfterMillis` (15 s), it asks `LinkConnection.checkAlive(probeTimeoutMillis = 10 s)`. A transfer that keeps moving bytes never asks; an idle link never asks. A runner also asks after any attempt that ended in a retry on a connection that still says "ready".
- **What it asks.** A new TLS handshake to the PC (`AddressRacer`, the same check the reconnect loop uses; it sends nothing after the handshake). Not the JSON `ping` message: protocol.md makes the receiver show "Ping from <name>", so a ping every few seconds would be a stream of toasts on the PC. Not the WebSocket ping frame either: OkHttp sets the interval once per client, and the PC sends none.
- **If the PC doesn't answer** the connection is abandoned (`socket.cancel()`, `LinkConnection.foundDead`). The session ends, `LinkLoop` reconnects, and the runner (which was already waiting for the connection to end) waits for the new one and resumes with `Range` / a new `POST`, within the same `reconnectWaitMillis` (15 min, then `queued`) and the 7-day queue rules. The attempts that dead link cost do **not** count towards `maxStalledAttempts`, so the transfer can't fail because the network was silent. A PC that does answer the check but refuses every request still fails after 5 attempts, as before.
- **Keepalive unchanged.** The WebSocket ping stays at 240 s (setting `ws_ping_interval_s`), idle and during a transfer. The guard is event-driven, so idle battery use is exactly what it was.

### The reconnect loop while a transfer waits (v0.1.1 fix)

`LinkLoop` still backs off 5 s, 30 s, 2 min, 10 min (architecture.md, "Finding each other"), and the backoff still resets only on a network change, a user action, or a connection that lasted 60 s. One addition: while something waits for the link (`LinkController.connection` counts the callers; a transfer that was moving, a share waiting for its first connection, a text send), a step is at most **10 s** (`LinkLoop.WAITING_RETRY_MILLIS`), and the moment something starts waiting a loop that sleeps a long step tries **now** (`LinkLoop.workIsWaiting`). With nothing waiting the steps are the same as before, so a PC that is off costs no more battery than it did. The cost while a transfer waits: one race (1.5 s) plus, if the last addresses fail, one mDNS lookup (5 s) per attempt, for at most the 15 minutes a transfer waits.

### Which foreground service type carries a transfer

Transfers run inside the existing `LinkService`, which is a `connectedDevice` foreground service. Reasons: (1) it is already running and keeps the process in the foreground state for the whole transfer, with no extra start; (2) `connectedDevice` has no time limit, while a `dataSync` service gets about 6 hours per 24 on Android 15 and can't be started from a boot receiver; (3) `dataSync` needs one more permission (`FOREGROUND_SERVICE_DATA_SYNC`), and this document's list says no more; (4) a user-initiated data transfer job (Android 14+) would add a second mechanism that runs on a job constraint (network type) instead of "the PC is on this Wi-Fi", and only for API 34 and later, while minSdk is 29. A 2 GB video over Wi-Fi takes minutes, far from any limit. If the service is killed, the transfer rows are `active`: the next `LinkService` start resumes them when the link is up (uploads need the source access to have survived: otherwise "Share it again").

## Battery and OEM killers

- **Setup (onboarding, built in 1.4):** one screen, shown once after the first pairing and reopened any time from Settings → "Fix connection reliability". Each step shows done or to do: notifications (Android 13+), Nearby devices (Android 17), the battery list, and the steps for the phone's maker. It reads the real state again when the user comes back from a settings screen.
- **Battery exemption: the compliant route (decision).** Google Play restricts the permission `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (behind the one-tap "Let Kin always run in the background?" dialog) to apps whose core function is hurt without it. Companion and device-connection apps are among the listed use cases, but the permission has to be declared in the Play Console and the review decides (the policy wording was checked through secondary sources only). The route that needs **no permission and no declaration** is the system's own list, `Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, where the user sets Kin to "Not optimised" with two taps. **Kin uses that and does not declare `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.** Whether it is done is read with `PowerManager.isIgnoringBatteryOptimizations` (no permission needed). If Phase 2 wants the one-tap dialog, it is one permission, one intent and a Play declaration (`SetupActions`).
- **OEM steps:** `Build.MANUFACTURER` (and `Build.BRAND` for Redmi and POCO) picks a guide from **one table**, `setup/OemTable.kt`: Xiaomi, Redmi and POCO (MIUI, HyperOS: Autostart, battery saver "No restrictions", lock the card), Samsung ("Never sleeping apps"), Oppo, Realme and OnePlus (ColorOS: startup manager, battery), Vivo and iQOO (autostart, background power), Huawei and Honor (App launch). Each guide has short text steps and a list of settings activities; the first that exists on the phone is opened, and if none does Kin's own settings page opens, so a stale entry costs nothing. Update the table when a vendor moves a screen. Other makers get only the general battery step.
- **Detecting kills:** if the service died without a clean stop, count it on its next start. Kills show on the debug screen and in the soak logs.

## Queue, history, notifications (built in 1.4)

- **The queue.** Every explicit send is stored as `queued` before it is attempted: a text in `texts`, a file upload in `transfers`. After the PC's `hello` the `OutboxFlusher` sends the queue in **creation order**, texts and uploads together: a text is sent and waits for its ack (5 s); an upload is only *started* (its bytes move on their own coroutine), so a big file doesn't hold back the texts after it. An unacked text is re-queued and the flush stops (the connection is treated as dead); the next `hello` flushes again. A new send while connected flushes the whole queue (older items first). One flush at a time. The **automatic clipboard is never queued** (it is not an explicit send, and nothing is stored for it). The phone's clipboard sends (tile, notification button) are manual, so they are explicit sends and are queued.
- **Expiry and cancel.** A queued text or an upload **that never started** and has waited **7 days** from its creation (`QueuePolicy`, expired at exactly 7 days; a Retry does not reset the creation time) fails with code `expired`, shows as failed ("Expired") in the history, and never goes out. An upload the PC has answered (`started`) follows the PC's `.part` rule (24 hours without progress) instead: the phone learns it from a `404` when it resumes, and never expires it at 7 days. Retry is not offered for an expired upload, one whose shared file can't be read any more (`source_lost`), or one meant for a PC that is no longer paired (`peer_changed`): their cached copies are gone. A user cancel of a queued item means it never goes out (`claim` is `queued → active` for one caller, so a cancel that came first wins; an item that is being sent can't be canceled).
- **Texts and PCs.** A queued item is for one PC. Unpairing cancels what was queued for it; an item for a PC that is no longer paired fails with `peer_changed`; an item for the paired PC stays queued while only another PC's connection is up (the re-pairing window).
- **History.** The `HistoryScreen` lists both directions, newest first, the last 500 (`QueuePolicy.HISTORY_LIMIT`; see "Storage" below for what is kept for older ones): time, direction, status, size, error. A sensitive text and an automatic clipboard sync are **never shown** (a sensitive text keeps its body only while it waits; a received sensitive text isn't stored at all). Tap a finished received file to open it, a finished text to copy it; **Retry** on a failed outgoing item (a failed text goes out again as a **new row** with a new message ID, and the failed row stays and says "Sent again as a new message"; a failed upload follows the `404` rule above). A **Retry made while the PC is away** is stored on the transfer (`userRetry`) and stays the user's until its run has reached its `POST`, so the queue flush that starts it after the reconnect may still send the files under a new ID on a `404`, **Cancel** on a waiting one. A file the phone sent is on the PC, so there is nothing to open. **Filter** (a button beside the title, a bottom sheet) searches all file names, the full text and the title, picks types (Photos, Videos, Documents, Apps, Other files, Texts, Links; a transfer matches if any of its files does) and a direction, and sorts by Newest, Oldest, Name or Size; the choices show as removable chips and live in `rememberSaveable` (kept on rotation, never saved to disk). The type table is `history/HistoryTypes.kt`, equal to the PC's `FILE_TYPES` (plan 01, C3); it works on the 500 loaded items, and failed rows stay red with Retry.
- **Success rate (targets.md #1).** The Debug screen counts the sends that ended: delivered on the first attempt over delivered or failed. Expired, unpaired and wrong-PC items aren't sends gone wrong; a retried item never counts as a first try (`attempts`).
- **Notifications.** Six channels (`NotificationChannels`): *Connection status* (`link`, low), *Arrivals* (`arrivals`, default: text, files and pings from the PC), *File transfers* (`transfers`, low: progress, and the results of what the phone sent), *Ring my phone* (`kin_ring`, high but silent: the Stop button; the ring plays on the alarm stream), *From your PC* (`kin_alerts`, default, private on the lock screen: alerts a script or the browser sent, and the PC's low battery) and *Screenshot about to be sent* (`kin_shot_hold`, high but with no sound or vibration: the 5-second hold with its Cancel). The channels of earlier builds are deleted. Android drops **new** notifications once an app has 50, so each group (sends and progress; arrivals) keeps at most 10 transfers on screen (`NotificationLedger`: a new one pushes out the oldest) with a summary notification ("N file transfers") when there are two or more. A result is a new notification under its own tag, never an update, so it is never rate-limited away. Texts from the PC are **one updating notification** ("60 texts from Desk PC", the last five previews, a sensitive one counts but shows no preview), updated at most twice a second with the last update always posted (`TrailingThrottle`). The two **summaries are the only notifications that are updated**, and Android sheds updates of an app that posts more than about five a second (the last one, in a burst), so each summary is posted at most once a second with the last request always posted (`TrailingThrottle`). The ledger is the record of what the app posted, with the time of each post: it forgets a slot only when its notification is missing from `activeNotifications` **and** was last posted more than 2 s ago, because that list lags a fresh `notify` (a 15-file storm now leaves 10 notifications and a summary that says 10). Send problems keep at most 5 notifications, on the **Arrivals** channel (default importance: a "Not sent" notice has to be seen).
- **Database.** (Version 6 since 2B.4: `transfers.origin`; `devices` writes are checkpointed to disk, see "Unlinking".) Version 4 (`app/schemas/` has the exported schema of every version; the 2 → 3 and 3 → 4 migrations are tested on a real SQLite): `texts` and, on `transfers`, `localId`, `retriedAs`, `attempts` (v3) and `userRetry`, `started`, `owed`, `owedId` (v4), `retriedAs` on `texts`, and indexes for the queue and history queries. `rename`, `delete` and `supersede` are single transactions, and a transfer that is over is never rewritten by a late status change.
- **The PC in every request.** A connection knows the PC it is pinned to (`LinkConnection.peerDeviceId`); a transfer, an offer, a cancel and a queued text are only started, accepted, cancelled or recorded for that PC. Right after a re-pair the old PC's connection is briefly still the current one, and none of them may go to it.

- **`complete` and `cancel` are owed until acked (1.4 review, protocol item 52).** A download that ends writes the message it owes the PC (`complete`, or `cancel` with reason `user` or `error`) **in the same database write as its status** (`owed`, `owedId`). It is sent at once if there is a connection, and **again after every `hello`, before the queue flush** (`OwedMessages.resendAll`, called from `TransferEngine.onLinkReady`), under the same message ID, until the PC acks it (an `error` answer is final). It survives a dropped connection and a process restart. An `offer` whose ID the phone knows is decided by `TransferEngine.offerHistory`: the **same paired PC with the same file IDs and sizes** is a *repeat* (the first response, the ack, and nothing downloaded again; an unfinished download carries on, a done one sends its unacked `complete`, a canceled or failed one its unacked `cancel`); **anything else** (an upload of ours, another PC, other files, an ID a `text` used) is `bad_request` with `ref` = the offer ID. A `cancel` from the owning PC turns a transfer that failed with `not_found` into "Canceled on <PC>" (`peer_canceled`); it never changes `done`.
- **Storage.** A transfer ID is never used twice, so **every transfer row is kept for ever** and every text row too. Beyond the newest 500 the history shows, the file rows of finished transfers (names, URIs; kept while a message is still owed) and the bodies of finished texts are dropped (`QuerySql`, run on every connect, at start and once a day). The cached copies of an upload are swept at start unless the transfer is queued, active, or failed with its files and not retried (`liveLocalIds`); the 7-day age sweep that ignored this is gone.
- **Logs and the export.** A text is logged as its length and `sha=` + 4 bytes of **HMAC-SHA256 with a random per-install key** (`LogFingerprint`, `LogKeyStore`: the key is stored wrapped by the Android Keystore and never exported; with no key only the length is logged); a sensitive text is not fingerprinted at all, not even on the loop-guard path. File names are never logged. **Export logs** runs every file through `ExportRedactor` (the same rules as the desktop's `export.rs`): IPv4 addresses and ports become `<ip>`, the names of the PC (every PC the log names) `<pc>`, the phone's own name `<phone>`, a full device ID is cut to 8 characters, and the debug build's `debug: CMD` echo lines are dropped. A failed export (no space, no share target) shows a message instead of crashing.
- **Reconnect on a new network.** `LinkLoop.networkChanged()` resets the backoff and tries at once when the network came back or changed under a loop that is still connecting (a new loop for a new Wi-Fi network already started from the first step; `LinkRuntime` now also calls it when the addresses of the current network change or it becomes validated). Repeated failures on an unchanged network still climb 5 s, 30 s, 2 min, 10 min. A text whose send is cancelled while it waits for the ack goes back to `queued` instead of staying `active`.

## UI

Screens: Home (PC status, the three newest history items), History, Settings, Debug, the setup (onboarding), and the pairing screens (scan, confirm). Tabs: Kin, History, Settings; Debug and the setup open from Settings (and the setup after the first pairing).

- **Settings:** the device name sent in `hello` (a change applies at the next connection), **"Show notifications on your PC" (2B.2: the switch, the apps, "Dismiss on the phone too")**, **"Media" (2B.3: the four switches)**, **"Status, pause and ring" (2B.4: share the battery, show the PC's status, Add the Pause tile, Let my PC ring this phone, ring volume, the full-screen Stop row)**, **"Screenshots" (2B.4: auto-send, off by default)**, "Fix connection reliability", the notification channels (links to the system's channel settings), **"Links and text from your PC" (2B.1): "Show link previews on the lock screen" (default off) and "Copy received text automatically" (default on)**, a note on the clipboard (PC → phone is automatic, phone → PC is manual; there is no images-to-clipboard on the phone), Unlink with a confirmation (2B.4: renamed from Unpair), About.
- **Debug:** the notification-mirroring counters (and, in a debug build only, the "Mirror test" buttons), first-try success rate, recent errors with their codes, ping round trip and tap-to-ack (last and median of the last 20), the connect and disconnect history (read from the log), the service kill count, **Export logs** (a zip of the log files and a state dump of counts and codes, no secrets and no text, shared through the share sheet with a `FileProvider` grant), and the log tail.
