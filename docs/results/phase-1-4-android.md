## Battery-exemption policy decision

**Kin does not request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.** The setup opens the system's own battery optimisation list (`Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`), where the user sets Kin to "Not optimised"; whether it is done is read with `PowerManager.isIgnoringBatteryOptimizations` (no permission). Why: Google Play restricts the permission behind the one-tap dialog to apps whose core function is hurt without it, and it has to be declared in the Play Console. A companion app that holds a `connectedDevice` connection is among the use cases the policy lists, but the review decides, and the Play review of the foreground service is already in Phase 2 (R4). The list route needs no permission and no declaration, so it is compliant whatever the review says. The cost is one more tap and the user having to find Kin in the list; the setup says exactly what to do. If Phase 2 wants the dialog it is one permission, one intent in `SetupActions` and a declaration. **Caveat:** the search tool found no copy of Google's own policy text; the "companion apps are a listed use case" part comes from third-party developer docs (e.g. https://www.mintlify.com/ivangonzalezg/react-native-background-guardian/concepts/battery-optimization) and must be checked against the Play Console policy page before Phase 2. Recorded as R14 in [risks.md](../risks.md); the OEM intents drifting is R15. The permission list is unchanged: the same nine as in 1.3 (checked with `aapt2 dump permissions` on the release APK).

## Spec ambiguities and decisions

1. **Expiry at exactly 7 days.** The spec says "expires after 7 days". I made age `>=` 7 days expired, the same edge as the 24-hour window (open while below it, `404` at exactly 24 h). `QueuePolicy.isExpired`, tested at 7 days minus 1 ms and at 7 days.
2. **Queued uploads expire too**, at the same 7 days (the spec names only text), and the cache of a queued upload is kept 7 days instead of 24 hours; otherwise a file queued for two days would find its copy gone. Expired uploads show as failed ("expired") like texts.
3. **What "a new ID for the files without a 200" looks like.** I made the retry a **new transfer row** and left the old one failed with `retriedAs`, rather than renaming in place: then the PC's transfer and the row's file list are always the same set (a resume `POST` must list the same `fileId`s). The history shows both. The old row's Retry disappears.
4. **A text Retry** goes out under a **new message ID**, in place of the failed row (the PC remembers the old ID and would repeat its first answer, an `error`). The attempts already made stay counted, so a retried text and a retried upload are never first-try successes. A sensitive text has no body left and can't be retried (and isn't shown).
5. **Automatic 404 on something never sent.** A queued upload whose first `POST` gets `404` (an ID collision with another device) also fails; it is never restarted automatically.
6. **"First-try success"** (targets.md #1) is delivered on the first attempt over delivered plus failed, outgoing only (texts and uploads). Not counted: canceled, still waiting, and failures that aren't a send gone wrong (`expired`, `unpaired`, `peer_changed`). An upload's attempts are connection attempts, so a resume after a drop makes it not-first-try. Items from before 1.4 count as first-try (their counter is 0).
7. **"In creation order" across kinds.** Texts and uploads are started in creation order; a text waits for its ack but an upload is only started, so an upload's bytes may still be moving when a later text goes out.
8. **An offer from a connection that isn't the paired PC's** (only possible right after a re-pair) is refused with `bad_request` (the spec has no code for it).
9. **Cancel of an `active` upload or download from the history** is allowed (as the progress notification's Cancel always was); a text that is being sent can't be canceled (it may already be on the PC).
10. **The phase doc's "auto clipboard sync on/off"** setting is not on the phone's Settings (the task didn't list it and Android can't read the clipboard in the background anyway); PC → phone clipboard writes are always on.
11. **Device name** applies at the next connection (it is sent in `hello`); Settings says so. There is no immediate reconnect, so a running transfer is not interrupted.
12. **A sent file isn't openable from the history** (it is on the PC); a received file opens through the MediaStore URI, a text copies.
13. **The 24-hour window (ruling 3)** has no timer on the phone: it only shows in what the PC answers to Retry's first `POST`. The five `transfer-id-*` vectors pass.
14. **Play policy.** See the decision above: I could not read Google's policy page; the route chosen is compliant either way.

### Decisions

1. **Transfer rows are never deleted** (the reviewer's "keep transfer IDs forever"); the same for text rows, whose bodies go. A repeat of an offer whose file rows were dropped has nothing to compare and counts as a repeat.
2. **A started upload never expires at 7 days.** `started` = the PC answered a `POST` with success; an upload that was only tried (connected, `POST` failed) is still "never started".
3. **Retry is hidden** for `expired`, `source_lost` and `peer_changed` uploads (no cached copies, or no readable source); other failures keep it. An expired text keeps Retry (its body is kept).
4. **A retried item counts once** in the success rate: the failed row that was retried is skipped, and the new row counts with its attempts (so it is never a first try). This also changes the upload case from 1.4 (before, both rows counted).
5. **File-name "hashes".** Android never hashed file names; the real leak was the names themselves in a few log messages, now removed.
6. **The export drops `debug: CMD` lines** (debug builds only) because they carry file names.
7. The summary throttle (1 s) is behaviour beyond the review's list, needed to make the count right on a device.
