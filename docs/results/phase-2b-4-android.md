# 2B.4 Android: presence and quick wins

Date: 2026-10-17. Android coder (Claude Sonnet 5.5). Not reviewed, **not committed**. `versionName` stays 0.1.1 (`versionCode` 2). Spec: [protocol.md "Presence, pause and ring"](../protocol.md#presence-pause-and-ring) (changelog 58) and its vectors (`protocol/presence.json`, the `presence-*` and `ring-*` cases of `messages.json`); design: [phase-2b-4-design.md](../phases/phase-2b-4-design.md). Description of the code as built: [android.md](../android.md) ("Presence, Pause, Ring, Screenshots"). User decisions taken: screenshots wait **5 s** with a Cancel; auto-send is built behind a flag so it can ship **sideload-only** if Play refuses the photo permission; **ring ignores Pause** and is **on by default**; "until tomorrow" = **08:00** local; battery sharing **on by default**; camera photos **never** go to the PC clipboard.

**Read this first: nothing in this milestone has run on a device.** A game was running on this PC for the whole session (`Get-RunningGames`: `EOSOverlayRenderer-Win64-Shipping`, `EpicGamesLauncher`, ...), so by the rules of the task every emulator and end-to-end step is **pending**: the spikes S4b (a) to (f), the emulator checks (`kin_api37`, `kin_api29`), the screenshots of the new screens. What is done: all code, **806 unit tests (0 failures)** including every Android-relevant vector of `protocol/presence.json` and the new `messages.json` cases, lint (0 errors), a debug and a signed release APK. Section 1 lists the pending spikes and what each one decides, section 6 the commands to run them in a few minutes once the PC is free.

## 3. Spec and design points found (not edited: protocol.md, protocol/ and the design are not mine)

1. **The vectors fix what the design left open, and I followed the vectors:** a battery "crossing" of 15, 20 or 100 is `(level >= threshold)` differing between the last sent and the new level (15 to 14 crosses, 16 to 15 does not, 19 to 20 crosses, 99 to 100 crosses); a **pause change goes 1 s after the first change of a burst** (not at once, and nothing is sent if it nets to nothing), while a timed pause's end goes at that moment; `ring.stop` is always acked; a nudge suppressed by the receiver's pause does not disarm; `remainingMs` 0 is `bad_request`; `ring.status` needs `presence` on both sides.
2. **Overrides are stored per peer, then per feature** (`{ peer: { feature: bool } }`), the shape the `features[]` vectors use; the design text said only "per peer device ID".
3. **`PRESENCE_STATE` prints the PC's battery level** (design 5.9 asks for it) while design 5.8 says a level is never logged. It is a debug build's `CMD` line only, and the log export (`ExportRedactor`) already drops `debug: CMD` lines. The integration agent's "grep the logs for the test levels" (design 10.2 step 7) must therefore skip the `CMD` echo lines, or `PRESENCE_STATE` must not be used in that run.
4. **`SHOTS_INSERT --ei ageSec N` can't set `DATE_ADDED`** (MediaProvider sets it). It moves the picker's clock forward by N seconds for 3 s instead (`files/debug-shots-offset`, debug build only), so the 15-second rule can be seen.
5. **Unlinking switches auto-send off** (my addition to design 5.7, which says "clears the saved baseline"): otherwise a switch left on and a baseline of 0 would offer every photo of the last 15 seconds to the next PC. Turning it on again takes a new baseline.
6. **While paused, `media.status` says `show: false, share: false`** (my reading of "act as both switches off"); it goes back when the pause ends. The design didn't say what the status carries.
7. **`PauseGate.inbound` answers `QUIET` for an auto-sent image** (the vector `screenshot-pc-paused-is-saved-quietly`): a phone never receives one, the table is shared.
8. **Android 14 partial access:** Kin does not declare `READ_MEDIA_VISUAL_USER_SELECTED`, so lint reports `SelectedPhotoAccess` (kept on purpose; the manifest says why). Whether `checkSelfPermission(READ_MEDIA_IMAGES)` really reads "denied" for a session-only "Select photos" grant in the compatibility mode is **[U]** (design 5.6): the code treats the system's answer at the point of use as the truth and never caches it.
9. **The bundled tone is a WAV** (`res/raw/kin_ring.wav`, 5.6 KB, 8 kHz 8-bit, two beeps), not the "Ogg of a few KB" of the design: there is no Ogg encoder on this PC. `MediaPlayer` plays it the same.
10. A `ring.start` that is **rate limited** answers `rate_limited` with `ref` and is not counted as a start; the 4th start inside a minute is the first refused (vector `the-4th-start-in-a-minute-is-rate-limited`).
11. The hold notification and its result live on the existing channel *File transfers* (low importance), as the design says; its text is "Sending screenshot to <PC> in 5 s".
