# v0.1.1, desktop: parallel files in a batch, and the 1.5 cleanup

Done 2026-10-16 by the desktop coding agent (Claude Sonnet 5.5) on Windows 11 Pro 10.0.26300. Code in `desktop/`, the protocol in [protocol.md](../protocol.md#concurrent-file-requests) (changelog 53) and `protocol/`, the scripts in `tools/` and `desktop/`. The Android half (up to 4 concurrent requests, pipelining) is the other agent's; the extension is a third agent's. **Nothing is committed** (the reviewer commits). The release installer is built and **not installed**.

**Summary.** The PC server already kept every file of a transfer apart (own `.part` file, writer lock, offset, finish), so up to 4 concurrent `PUT`s or `GET`s of one transfer worked. What did not work was **a resume `POST` in the middle of a batch: it stopped the writer of every file of the transfer**, which with four files going would have failed the other three with `409` each time one file was retried. That is fixed, with tests that fail on the old behaviour. The database was the real bottleneck of a small-file batch (four commits of two `fsync`s per received file behind one lock, on the async threads): write-ahead logging brought 50 photos over loopback from about 1.2 s to 0.3 to 0.6 s with four connections. The protocol now says a client may run 4 file requests of a transfer at once and pipeline small files, and the progress view says how many files are moving. All the 1.5 cleanup items are done (one of them with an exception, see "For the reviewer"), and the desktop is **0.1.1**.

`cargo test`: **393 passed, 0 failed, 7 ignored** (the ignored ones: three real-clipboard tests (one is new: `clear_if_text`), the 2 GB runs, and the new speed test). `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` clean. `bun protocol/check-vectors.ts`: **OK, 6,413 checks** (6,387 before). `bun run build` (tsc and vite): clean. ## Parallel files

### What the server does with several files at once

| | Before | Now |
|---|---|---|
| 4 `PUT`s of different files of one transfer at once | worked (a lock per file, none per transfer) | same, now covered by a test with 4 connections held half way through their bodies |
| 4 `GET`s of different files of one offer at once | worked | same, covered; one resumed with `Range` while the others carry on |
| A resume `POST` for the transfer while other files are being written | **stopped every writer of the transfer** (`409` for the other files) | stops a writer only if no byte arrived for a second (a dead connection); waits up to 250 ms for a writer whose connection just closed (so the offset it reports is exact); leaves a writer that is receiving alone and reports that file at the bytes stored so far |
| A `PUT` at an offset behind a request that is still writing | takes over, old request gets `409` | unchanged |
| A request still being served when the transfer is canceled | `409 offset_mismatch` for an upload (it was "stopped by a newer request") | `404 not_found` |
| Several files finishing together | the transfer is done once | unchanged (`end_if_active`), covered: one toast, one send record |
| Speed of a transfer with several files | `note_moved` took the total outside the lock, so samples could arrive out of order | taken under the lock |
| Pipelined requests on one connection (small files) | not tested | tested: a `POST` and 20 `PUT`s in one write, and 12 `GET`s in one write, are answered in order |
| More than 4 requests | not limited | **not limited, and documented as not promised**: no `429` (there is no such code in v1), no queue; the bound is the pool of 24 paired connections |

Why no queue or `429`: a queue (a semaphore per transfer) would make the new requests of a phone that just lost four connections wait behind the four writers that haven't noticed yet (up to the 30 s idle timeout), which is the case that matters most. And a new error code would be a wire change for a limit a well-behaved phone never reaches.

Code: `transfers.rs` (`stop_idle_writers`, `SETTLE_WAIT`, `TAKEOVER_IDLE_MS` with a test hook `Hooks::takeover_idle_ms`, `FileShared::active`, `ActiveGuard`, `files_active` in the view, the `404` after a cancel), `fileserver.rs` (the `GET` body counts as active), `drop.ts` (the row says `3 of 50 files · 120 MB of 171 MB · 45 MB/s · 4 at once`), `storage.rs` (WAL).

### Protocol

[protocol.md](../protocol.md#concurrent-file-requests): new section "Concurrent file requests" (a client MAY run up to 4 file requests of one transfer, in either direction, on their own connections or pipelined; a server MUST accept that; a client MUST NOT run more; the Windows app doesn't enforce it and never answers `429`); the "one writer per file" rule says what a `POST` does now; "the phone sends files one at a time" is gone; changelog 53. **Vector:** the format of `http.json` is sequential and can't interleave, so concurrency is tested with real connections (`tests/parallel_files.rs`); one sequence was added for what is expressible, `batch-files-of-one-transfer-are-independent-and-a-resume-leaves-the-others-alone` (one file cut off, another completes, a resume `POST` in the middle, a third file, the first continues, every file complete), with a `scope-0.1.1` group in `check-vectors.ts` and a paragraph in `protocol/README.md`. ### Speed on this PC (loopback, so it measures the PC only, not Wi-Fi)

50 photos of 3.4 MB (171 MB) phone to PC, the database a real file, release build:

| Shape of the phone's requests | Before (default journal) | After (WAL, `synchronous = NORMAL`), two runs |
|---|---|---|
| One file at a time | 1.34 s | 1.09 s, 1.48 s |
| 4 connections at once | 1.24 s | 0.32 s, 0.62 s |
| Pipelined on one connection | 1.52 s | 0.72 s, 0.82 s |

One run before and two after, so these are indications, not medians: a loopback run is not the phone's Wi-Fi, which was 12 to 24 MB/s phone to PC on the speed test of [phase-1-speed.md](phase-1-speed.md) (7 to 14 s for the batch), so the PC will not be what limits it any more; the phone's request pattern and its uplink are. The target of the plan, 50 × 3.4 MB in about 3 to 4 s, is for the integration run on the emulator and the user's phone.

**The database change, in one place** (`storage.rs`, `Db::open`): `journal_mode = WAL`, `synchronous = NORMAL`. Why: the numbers above. What it gives up: after a power cut the last moments of progress may be missing from the database (never a corrupt file), which the resume rule already covers (smaller of the database and the `.part` file); at worst a file being moved to its final name at that moment arrives twice. `kin.db-wal` and `kin.db-shm` appear next to `kin.db`. An existing database switches to WAL at its first open and an older Kin opens it fine. **This is a decision for the reviewer** (see below).

## For the Android agent and the integration run

- **New vector** in `http.json`: `batch-files-of-one-transfer-are-independent-and-a-resume-leaves-the-others-alone` (it has a `PUT` cut off after 1 MiB and a resume `POST` that lists three files). The Android `HttpVectorsTest` reads `http.json` and will run it.
- **A resume `POST` can report a file that is still being written at less than it will be**: do not trust a `POST`'s offset for a file you have a request running on; a `PUT` from a stale offset answers `409` with the real one, retry from there. A `POST` for a file whose connection died more than a second ago is exact.
- **Cancel:** a `PUT` that is in flight when the transfer is canceled (by the PC's `cancel` message or a `DELETE`) is answered `404` (it was `409`); treat it as "canceled", never retry it.
- **Pipelining:** the PC answers pipelined requests in order. An error answer (`400`, `404`, `409`, `507`) is given before the body is read and the PC may close the connection, so **requests that were pipelined behind a failed one are not answered**: treat that as a dropped connection and send them again (a `POST` first, to learn the offsets).
- **No limit:** the PC doesn't enforce 4 and doesn't answer `429`; it has 24 paired connections for everything (the WebSocket included) and 8 connections per address while they handshake or are unpaired, so 4 file connections plus the WebSocket are far inside.
- **Speed:** the PC side takes about 0.3 to 0.6 s for 50 × 3.4 MB over loopback with 4 connections. On the real Wi-Fi the phone's uplink and its request pattern are what is left.
- The progress rows of the PC say `N of M files … K at once` when `filesActive` is above 1: useful for a screenshot of a parallel run.

## Dev Kin beside the installed Kin

Done 2026-10-16 by the desktop coding agent. **Nothing is committed.** The problem: the user's installed Kin 0.1.0 runs all day (autostart, tray), every e2e/check script refused to start beside another Kin, and the single-instance plugin would have handed a second launch to it anyway, so no end-to-end test could run without the user quitting Kin. Now a test Kin runs beside it, and the installed Kin is never touched.

**Summary.** *A Kin is identified by its data directory* (`instance.rs`, decision D17). `%APPDATA%\Kin` is the installed Kin; any other `--data-dir` is a separate instance with a key (12 hex characters of a hash of the normalised path). The key makes: the **single-instance lock** (mutex, window class and name of the plugin, all built from the bundle identifier, which the app replaces at start by `app.kinrelay.desktop.dev-<key>`), the **app user model ID and toast identity** (same string), the **port** (never the default 47821: `--dev-port` or any free one), **mDNS** (never advertised), the **hotkey** (the default `Ctrl+Alt+Shift+K` is not registered), the **web view data** (`<data dir>\webview`) and the **clipboard writes** (marked, below) separate from the installed Kin's. Two guards keep a mistake from reaching the installed Kin: `--dev-*` settings without a `--data-dir` of their own are refused at start (they would run against the user's identity, pairing and history), and **a launch with no data directory refuses to hand its command line to a running Kin that is another program file** (so `target\release\Kin.exe --quit` can never quit the installed Kin; the "Send to" shortcut runs the same file as the running one and is never refused). `tools\kin-dev.ps1` is the script side: every command carries `--data-dir`, processes are recognised by program file *and* data directory and stopped by ID, and "another Kin is running" now means a Kin on *our* data directory (plus the lock).

### The clipboard marker, checked in the 0.1.0 code

The installed Kin is **0.1.0** (tag `v0.1.0`), and its automatic sync does skip marked content. `git show v0.1.0:desktop/src-tauri/src/clipboard.rs`: `exclusion()` returns a reason when the content has the format `ExcludeClipboardContentFromMonitorProcessing` (presence is enough), or `CanIncludeInClipboardHistory` / `CanUploadToCloudClipboard` with a value of 0 (or no readable value), or `Clipboard Viewer Ignore`; `git show v0.1.0:desktop/src-tauri/src/sync.rs`, `process_clipboard_change` (line 518): "if let Some(why) = clipboard::exclusion(&snapshot.formats) { ... not sent, the source app marked it ...; skip }", before the text is even looked at. **Confirmed in the installed Kin's own log** (read only): its log already had `clipboard changed: not sent, the source app marked it ExcludeClipboardContentFromMonitorProcessing` lines from the marked tests of 2026-10-15, and the proof run below added exactly 2 more, nothing else.

**So the rule is: nothing unmarked goes on the real clipboard.** The dev Kin does it itself: an instance with a key writes every text and image it puts on the clipboard (a text from the phone, a history copy, `--dev-set-clipboard`, a received image) with `ExcludeClipboardContentFromMonitorProcessing` plus a format of ours, `KinRelayDevTestContent`. Only an instance with a key treats content that carries the second format as ordinary content, so its own sync, hotkey and echo guard behave as for any copy (and `status.json` still says `echo_of_phone_text`, not `password_manager:...`), while a real password manager's mark (without ours) still holds a copy back there, and the installed Kin sees only the first format and skips it. The scripts get the same through `Set-QuietClipboardText` (replaces every `Set-Clipboard` and `[Windows.Forms.Clipboard]::SetText` in a test), and **`Restore-Clipboard` now adds the exclusion mark to what it puts back** (`-NoMark` to turn that off), because a restore is a clipboard change too and an installed Kin would send the user's own text to the phone a second time. The ignored real-clipboard unit tests write quietly now (one of them used to write plain text). Nothing had to be marked "unsafe": no test is left that can't run beside the installed Kin, except the hotkey press (below).
