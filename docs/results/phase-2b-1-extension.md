Agent: Sonnet 5.5, extension coder. Date: 2026-10-16. Owns `extension/`, `docs/extension.md` and this file. Nothing else was changed, nothing was committed.

## What is built

- **`docs/extension.md`**, the contract with the native messaging host: architecture, host names (`app.kinrelay.desktop` release, `app.kinrelay.dev` dev and tests), the Chromium and Firefox host manifests, registry keys per browser, framing and size limits, message schema (`{v, id, type}` / `{v, ref, type, ok, code?, message?}`), the `status`, `start`, `open` and `send` requests, the four send kinds, the image round trip, error codes, the pipe between host and Kin, security notes and build notes for the host.
- **`extension/`**, one Manifest V3 codebase (TypeScript, bun, no runtime dependencies) that builds for Chromium (service worker) and Firefox (event page, `gecko.id` `kin@kinrelay.app`).
  - Right-click "Send to Kin" on selection, link, image and page. One phone gives one item (with "offline, will queue" in the title when it is offline); several give a submenu.
  - Toolbar popup: state of Kin ("Kin is running", "Kin isn't running" with **Start Kin**, "No phone paired", "Kin unavailable"), the phones with online/offline and queued count, a phone picker, **Send this tab**, the last 10 sends (labels only, never the content) with **Clear**, and clear error text.
  - `Alt+Shift+K` sends the current tab. Menu and shortcut sends show a toolbar badge for 4 s (`✓` sent, `Q` queued, `!` failed) with the message in the tooltip (there is no notifications permission).
  - YouTube (`youtube.com`, `www.`, `m.`, `music.`, `youtu.be`): the video's `currentTime` is read at click time with `activeTab` + `scripting`, and `t=<seconds>s` replaces any old `t`. Skipped for time 0, live streams, ads (`ad-showing`), and links to a different video than the one on screen.
  - Images: by URL first (Kin downloads); on `IMAGE_NEEDS_BYTES` the extension fetches in the page with the page's cookies and resends the bytes; `data:` URLs go straight to bytes; `blob:` URLs are fetched in the page.
  - Permissions exactly `contextMenus`, `nativeMessaging`, `activeTab`, `scripting`, `storage`. No host permissions, no content scripts, no `<all_urls>` (a unit test asserts this for every target and flavor; only the *test* flavor adds `127.0.0.1`, `localhost` and the two YouTube hosts, so the test can inject without a toolbar click).
  - A stable dev extension ID, `cbioefpddjpaionhljhffgbedncfchmn`, from a `key` in the manifest (public key in `extension/manifest-key.json`, the private key was discarded). The store zip leaves the `key` out.
  - Placeholder icons generated by `scripts/gen-icons.ts` (committed in `assets/icons`).
- **Builds:** `bun run build` (release), `build:dev`, `build:test`, `package` (zips). Outputs in `extension/dist/` (git-ignored): `kin-chromium-0.1.0.zip` (17.0 KiB, 9 files, no `key`) and `kin-firefox-0.1.0.zip` (17.1 KiB). `web-ext lint` on the Firefox build: 0 errors, 0 warnings, 0 notices.
- **`extension/README.md`:** build commands, load-unpacked steps for Chrome, Edge, Brave, Vivaldi, Opera and Firefox, what the smoke test touches.

## What the desktop agent must implement for the host

Everything is in `docs/extension.md`; in short:

1. **`kin-native-host.exe`** (Rust, no Tauri): native messaging framing (u32 LE length + UTF-8 JSON), binary stdio, nothing but frames on stdout; loops until stdin EOF; max 1 MB to the browser, 64 MiB from it; passes `origin` (first argument) and `hostVersion` to Kin; no console window.
2. **Requests:** `status` (never starts Kin; `running:false` is a normal answer), `start` (starts Kin, waits up to 10 s), `open` (optional), `send` kinds `text`, `link`, `page`, `image` (URL or bytes). The host starts Kin for a `send` when it isn't running.
3. **Kin side:** re-validate everything (http/https only, 8 KiB URL, 300-character title cleaned like a file name, 4 MiB text, 32 MiB image bytes, image by content), the `link` message and its handling are the 2B.1 protocol work, the image download (no cookies, `Referer` = `pageUrl`, 5 redirects, 30 s, 64 MiB cap, image by content, `IMAGE_NEEDS_BYTES` on failure), the offline queue answer (`queued:true` with `DEVICE_OFFLINE_QUEUED`), a 30 per 10 s rate limit on `send`.
4. **Pipe:** `\\.\pipe\<host name>.<user SID>`, DACL for the current user only, `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`; the host checks the pipe server is the installed `Kin.exe` of the same user.
5. **Installer:** the two manifests (`allowed_origins` has `chrome-extension://cbioefpddjpaionhljhffgbedncfchmn/`, `allowed_extensions` has `kin@kinrelay.app`), HKCU keys for Chrome, Chromium, Edge, Brave, Vivaldi and Mozilla, removed on uninstall.
6. **Conformance:** `extension/tests/smoke/mock-host.ts` (and `tests/unit/mock-host.test.ts`) is the answer sheet: run the same framed requests against the real host.
7. **Dev Kin** must listen on the `app.kinrelay.dev` pipe, so extension tests never reach the installed Kin.

## Deviations and decisions to confirm

- **Image bytes fallback is capped at 32 MiB, not 64 MiB.** The native message limit is 64 MiB and base64 adds a third, so 32 MiB of image is the safe size. Kin's own download by URL still goes to 64 MiB. A chunked upload would remove the gap; I left it out (open question 3 in the contract).
- **Cross-origin images that need cookies and send no CORS headers can't be fetched by the extension** (the in-page `fetch` follows the page's CORS rules). The user gets `IMAGE_UNREACHABLE` with "save it and send the file instead".
- **`DEVICE_OFFLINE_QUEUED` is a success** (`ok:true, queued:true, code, message`), not an error. A client that only reads `ok` works too.
- **`status` never starts Kin**; `send` and `start` do. Opening the popup should not launch a program.
- **`sourceApp`** of the `link` message is left to Kin (the extension can't tell Brave from Chrome reliably).
- **Menu staleness:** the menu is rebuilt when the browser starts, after each send, and whenever the popup opens (or the shortcut/menu send refreshes status). Without an alarms permission there's no timer, so if a phone is paired or goes offline while the browser sits idle, the menu title can be out of date until the next of those events. The send itself always works (Kin decides).
- **The test build** has host permissions for local pages; the release and dev builds don't, and a unit test enforces it.

## Review cleanup

- **`checkUrl` now refuses what Kin refuses, with a clear message.** It used to let `user@host` and similar through (Kin then answered with a generic `BAD_URL`). Before `new URL`, it now applies the authority rules of docs/protocol.md (steps 4 to 6): user information (`@`), a `\` or `%` before the first `/`, one of `[ ] < > ^ |` in a host that is not a bracketed IPv6 literal, an empty or dots-only host, a bad port (not `[0-9]+`, or outside 1 to 65535), and a scheme not followed by `://`. `UrlCheck` has a new `message` for the user ("Kin won't send a link with a username or password in it (like user@host). Remove that part and try again."), which `buildSendLink`, `buildSendImageUrl` and `sendTab` now show instead of the generic text. Valid URLs are still sent as `new URL(x).href`.
- Trimming now uses the protocol's `White_Space` set (U+0085 is trimmed, which JavaScript's `trim()` doesn't do; U+FEFF is no longer trimmed).
- **Tests** (`tests/unit/validate.test.ts`): the new cases, plus `protocol/urls.json` and `protocol/links.json` run through `checkUrl`: every URL Kin refuses is refused, and every URL Kin accepts is accepted, except the two a browser's `new URL` cannot parse at all (`1.2.3.4.5`, `[abc]`: the extension can't send those, which is fine). `bun test tests/unit`: 110 pass; `tsc --noEmit` clean; `bun run package` rebuilt both zips (`dist/kin-chromium-0.1.0.zip`, `dist/kin-firefox-0.1.0.zip`).
