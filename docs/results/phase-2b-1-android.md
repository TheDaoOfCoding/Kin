## 2. Findings worth knowing

1. **`<queries>` for `ACTION_VIEW https` alone does not make "Open in YouTube" possible.** It shows only the browsers (apps whose filter has no host). An app that owns a host (YouTube: `www.youtube.com`) stays invisible, so the label said "Open in browser" for a link the app owned (seen on kin_api37 with the test app). Fix: the manifest also lists **one `<intent>` per well-known host** (about 55: YouTube, Spotify, X, Reddit, Instagram, TikTok, Twitch, GitHub, Wikipedia, …; none of this is `QUERY_ALL_PACKAGES`); the debug build adds the test app's host. A site not on the list still opens in its app on a tap (the system picks it); only the label is then the neutral **"Open link"** (the label never claims "browser"). The plan said "Open in browser" for that case; it was wrong to claim it. **Decision for the reviewer/user:** the host list is a maintenance item (add hosts as needed).
2. **Android 12+ routes a web link to a non-browser app only when the app is verified for the host or the user approved it** ("Open by default"). The unverified test app got the link in Chrome until `pm set-app-links` approved it (`verify-2b1.ps1` does that). Real YouTube is verified, so this only affects tests. It also means `REQUIRE_NON_BROWSER` correctly falls back to the browser for an app the user hasn't approved.
3. **`VISIBILITY_PRIVATE` hides content only when the phone's own lock-screen setting hides sensitive content.** The AOSP emulator default shows everything (the first run showed the full title on the lock screen). The test turns that system setting on for the run (and puts it back). Kin can't change it; the Settings text says so. Also: a group summary has its own visibility, and a private summary hid links that were public, so the summary now follows the setting.
4. **Spec point (not edited): a backslash in the authority.** `https://evil.example\@google.com` passes the openable-URL rule (a backslash is neither whitespace nor control), and by the rule's own reading the host is `google.com` (everything before the last `@` is user info), but a browser reads `evil.example` (WHATWG: `\` ends the authority). The notification shows the browser's reading and marks the URL (warning sign); the same mark for a login part (`https://google.com@evil.example`), an escape in the host, and a non-ASCII host (shown as punycode). The spec could reject a backslash before the first `/`, `?` or `#`; the desktop shows the address too and will have the same question.
5. **Spec point: `sourceApp` has no display on the phone.** It is cleaned and kept in `ReceivedLink` but shown nowhere (the notification already has the sender and the address). Fine ("display only", optional).
6. **The phone's `hello` now carries `capabilities`**, which a 0.1.x PC ignores (unknown field). Verified against the real `Kin.exe` of this tree, which has no `link` yet: the shared URL arrived as a `text` (phone log "on the wire as a text") and the phone history shows it as a link, done.
7. `uiautomator dump` of the notification shade sometimes fails right after the shade opens; the verify script retries.

## B1/B2 alignment (2026-10-17, Android coder)

Aligns the phone with the tightened URL rule and the display spec ([phase-2b-1-desktop.md](phase-2b-1-desktop.md) "B1/B2 spec change"; protocol.md "Links: `isUrl` and openable URLs" steps 4 and 5, "Showing the address of a link", changelog 55; the vectors win). Not committed. `versionName` still 0.1.1.

### What changed

| Item | Result |
|---|---|
| **1. The rule** | `UrlRules.httpUrl` (`protocol/UrlRules.kt`) is the one acceptance check behind everything: receiving a `link` (`MessageReceiver` → `LinkWire.isLinkUrl`), a received `text`'s Open action, the share → link path (`ShareIntents.linkOf`, `OutgoingSender.sendLink`, a text's `isUrl`), `LinkOpenActivity`/`LinkOpener` and Copy link (`LinkRules.acceptUrl`). The authority (text after `://` up to the first `/`, `?` or `#`) is **rejected if it has `@`, `\` or `%`**, and a host that is not a bracketed IPv6 literal is rejected if it has any of `[ ] < > ^ |`. The old "ignore everything up to the last `@`" is gone. So `https://evil.example\@google.com` (which Android itself reads as `google.com`) is refused **at acceptance**: nothing is posted, nothing can be tapped. |
| **2. The display** | `links/LinkDomain.kt` is rewritten as the WHATWG host reading: UTS 46 **non-transitional** punycode through `android.icu.text.IDNA` (`NONTRANSITIONAL_TO_ASCII \| CHECK_BIDI \| CHECK_CONTEXTJ`; the errors WHATWG does not count, `CheckHyphens` and length, are ignored; any other error = "a browser refuses it"), IPv4 in any spelling → dotted decimal (the WHATWG "ends in a number" check, hex/octal parts, 1 to 4 parts, range checks), IPv6 parsed and serialised compressed (`[::ffff:127.0.0.1]` → `[::ffff:7f00:1]`), the default port dropped (`:00443` too), a refused host shown as written, ASCII lower case, each code point outside U+0021..U+007E as U+FFFD, no port. `warn` (was `suspicious`) = host as written is non-ASCII, or the shown host has an `xn--` label, or it is an IP, or it is refused. The notification puts ⚠ in front of the address when `warn`. Plain ASCII hosts (no `xn--` label) never touch ICU. |
| **3. Phone → PC** | A share that fails the new rule is not a link: `ShareIntents.linkOf` is null, so it goes as a **text with `isUrl` false** (same bytes, no Open action on the PC). Tested for `\`, user info, `user:pw@`, `%` (`LinkFlowTest`). |
| **4a. Copy link and the clipboard loop** | `TransferActionReceiver` `ACTION_COPY_LINK` now calls `clipboardGuard.notePeerSet(url)` before it writes (as Copy text does), so the clipboard sync does not send the URL straight back to the PC. |
| **4b. Unique PendingIntent** | The copy-link `PendingIntent` carries the URL as the **intent data** (`setData`), like the open intent; the `("copy$url").hashCode()` request code is gone (both use request code 0 now; `filterEquals` compares data, extras and hash collisions no longer matter). The receiver reads `intent.dataString`; `EXTRA_URL` is removed. |

New seam: `fun interface Uts46` (`LinkDomain.of(url, uts46 = AndroidUts46)`). `android.icu` is a stub on the JVM, so the unit tests pass an ICU4J adapter (`Icu4jUts46`, test source set; **new `testImplementation` `com.ibm.icu:icu4j:78.3`**). The shipped code only uses `AndroidUts46`.

## 6. B1/B2 alignment (protocol.md changelog 55, `protocol/links.json` `display[]`)

The phone now follows the tightened URL rule (B1) and shows the address the way a browser reads it (B2). Both come from the spec; nothing here was decided on the phone.

### What changed

- **B1, the rule (`protocol/UrlRules.kt`).** The authority (up to the first `/`, `?` or `#`) must have no `@`, no `\` and no `%`, and a host that is not an IPv6 literal has none of `[ ] < > ^ |`. Before, everything up to the last `@` was taken as user info and the rest was the host, so `https://evil.example\@google.com` passed and the notification showed `google.com` while a browser goes to `evil.example`. Such a URL is now **refused, not shown with a warning mark**. The rule is the one in `UrlRules.httpUrl` / `LinkWire.isLinkUrl`, so every path uses it.
- **Where the rejection happens.**
  - *Received:* `MessageReceiver.onLink` answers `bad_request` with the frame's `ref` and nothing is delivered; if a link ever got past it, `IncomingHandler` logs "a link from '…' was refused: not an http or https address" and posts nothing.
  - *Sent:* `OutgoingSender.sendLink` says "That isn't a web link." and queues nothing.
  - *Share fallback to text:* `ShareIntents.linkOf` uses the same rule. A share that is exactly one URL goes as a `link`; a share the rule refuses (a backslash, user info, `javascript:`, a URL inside a sentence) is not a link and stays a plain `text`, as before. The old-PC fallback (a `link` sent as a `text` to a PC without the capability) is unchanged.
- **B2, the display (new `links/LinkDomain.kt`).** `LinkDomain.of(url)` returns the host a browser connects to, plus a `warn` flag: WHATWG host parsing for special schemes, with UTS 46 ToASCII (non-transitional, CheckBidi, CheckJoiners, no STD3, no hyphen or length checks). It gives lower case ASCII/punycode, IPv4 in dotted decimal (hex, octal and short forms included), compressed IPv6, the port unless it is the default for the scheme, and, for a host a browser refuses, the host as written (ASCII lower case, other characters as U+FFFD, no port) with `warn`. `warn` is set for a non-ASCII host as written, a punycode label, an IP address, or a refused host. Plain ASCII hosts never load ICU.
- **UTS 46 on the phone is `android.icu.text.IDNA`** (API 24+, minSdk is 29), through a one-method seam `Uts46`. `java.net.IDN` is IDNA 2003 (`faß.de` becomes `fass.de`) and is not used.
- **Copy link fixes (`Notifications`, `TransferActionReceiver`).** The "Copy link" button's `PendingIntent` now carries the URL as the intent's data, so each link gets its own `PendingIntent`. `TransferActionReceiver` checks the URL again with `LinkRules.acceptUrl` before it goes on the clipboard, calls `clipboardGuard.notePeerSet(url)` first (like Copy text: the clipboard sync must not send the link straight back to the PC it came from), and tells the user "Link copied" or "Couldn't copy the link".
- **ICU4J is test-only.** `testImplementation(libs.icu4j)` (`icu4j = 78.3` in `libs.versions.toml`): `android.icu` is only a stub on the JVM, so the unit tests run the same UTS 46 algorithm on ICU4J through `Icu4jUts46`. It is in no APK: `com.ibm.icu` has 0 entries in the release or the debug APK.
- Other: the `display[]` vectors are an asset of the test APK (`androidTest.assets` points at `../../protocol`); `verify-2b1-alignment.ps1` is the emulator check; `verify-2b1.ps1` and `share-source` were fixed for the new rule.
