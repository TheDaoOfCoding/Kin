# Phase 0 result: .NET (WPF) tray spike for D2

Measured 2026-10-14 on Windows 11 Pro 10.0.26300, Ryzen 9 7900X, 31 GB RAM. Code is in `spikes/desktop-dotnet/`. The Tauri side is in [phase-0-tauri.md](phase-0-tauri.md). D2 was decided for Tauri on 2026-10-14 (see [decisions.md](../decisions.md)), and this spike stays as a record of the comparison.

## What was built

A tray-only WPF app on .NET 10 (LTS). Assembly `Kin`, product "Kin Relay", identifier `app.kinrelay.desktop` (used as the single-instance mutex name).

- Starts with no window and a tray icon (tooltip "Kin").
- Menu: **Open** shows a small window reading "Hello from Kin Relay". The window is created on open and dropped on close. **Quit** hides and disposes the icon, then exits.
- Tray is the built-in WinForms `NotifyIcon` (`UseWindowsForms`), so there is no third-party package. WPF has no tray API of its own, and `NotifyIcon` is the usual answer.
- Placeholder icon: white "K" on an indigo rounded square, generated by `gen-icon.ps1` with `System.Drawing`.

Checked by driving the real tray with UI Automation: the icon appeared in the overflow flyout with tooltip "Kin", the menu had Open and Quit, Open showed the window with the expected text, and Quit ended the process and removed the icon from the flyout. It ran 62 s without crashing.

## SDK, PATH gotcha, build and run

- **SDK:** .NET SDK 10.0.402 (LTS), installed per user with the official `dotnet-install.ps1` (Microsoft-signed, checked) into `%LOCALAPPDATA%\Microsoft\dotnet`. No admin was needed. `DOTNET_ROOT` is set per process by `_sdk.ps1` (and passed on to Kin by `run.ps1`). `build.ps1` and `run.ps1` put the previous value back when they finish, even on error, so nothing leaks into an open PowerShell window. It is deliberately NOT set globally: apphosts read it before `C:\Program Files\dotnet`, so a user-level value would hide the Program Files runtimes from other apps (for example MSI Center's Smart Image Finder needs .NET Core 3.1, which only exists there). The machine PATH and `C:\Program Files\dotnet` were not touched. The SDK's first run did add `C:\Users\Anna Berg\.dotnet\tools` to the user PATH. It is harmless and was left in place.
- **Gotcha:** `C:\Program Files\dotnet` is on the machine PATH and holds runtimes only (3.1 and 9.0). Machine PATH wins over user PATH, so a bare `dotnet` is that muxer, and `dotnet --list-sdks` prints nothing. `DOTNET_ROOT` does not change which SDKs that muxer sees. The fix is to call `%LOCALAPPDATA%\Microsoft\dotnet\dotnet.exe` by full path. `_sdk.ps1` does that (and fails with a clear message if the SDK found is older than 10), and `build.ps1` and `run.ps1` use it. To check the SDK by hand: `& "$env:LOCALAPPDATA\Microsoft\dotnet\dotnet.exe" --version`.
- **Build:** `powershell -ExecutionPolicy Bypass -File spikes\desktop-dotnet\build.ps1`. Output is `bin\Debug\net10.0-windows\Kin.exe`.
- **Run:** `run.ps1` builds and launches. Look for the "K" in the tray overflow ("Show hidden icons"). Quit from the tray menu. Don't use `Stop-Process -Name Kin`: it skips `OnExit` and leaves a ghost tray icon until the mouse hovers over it.
- **Publish:** `build.ps1 -Publish` writes `publish\fdd` and `publish\sc-single`.
- **Runtime for the framework-dependent build:** it needs the .NET 10 Desktop Runtime. `C:\Program Files\dotnet` only has the .NET Desktop Runtime 9.0 (plus .NET Core 3.1), so the framework-dependent exe runs only when `DOTNET_ROOT` points at the per-user install, which `run.ps1` does for the process it starts. The final app would use Kestrel (see the D2 table), and the ASP.NET Core Runtime is not part of the Desktop Runtime. So a framework-dependent build would make end users install two runtimes, or we ship self-contained.

## Metrics

Idle, after 62 s, tray only, window never opened (one run each, so treat as rough):

| Build | Working set | Private working set | Private bytes (commit) | Threads | Handles |
|---|---|---|---|---|---|
| Framework-dependent | 57.1 MB | 8.9 MB | 13.8 MB | 9 | 329 |
| Self-contained single-file | 60.7 MB | 10.2 MB | 14.8 MB | 9 | 376 |

- With the Hello window open (framework-dependent, one reading): working set 128 MB, private bytes 73 MB. I did not measure memory after closing it.
- **Startup:** time from process start until the app is idle with the tray icon registered (`WaitForInputIdle`). First launch after publishing is 216 ms (fdd) and 182 ms (single-file). Warm launches are about 130 ms (fdd) and 125 ms (single-file). A truly cold boot start was not measured.

Publish sizes, `win-x64`, Release:

| Variant | Size |
|---|---|
| Framework-dependent | 0.2 MB (`Kin.exe` 164 KB + `Kin.dll` 20 KB), needs the .NET 10 Desktop Runtime |
| Self-contained single-file | 147.6 MB |
| Self-contained single-file, `EnableCompressionInSingleFile` | 66.2 MB, but about 250 ms startup and about 187 MB working set and 86 MB private bytes after 20 s (one run). Compression looks like a poor trade |

WPF does not support trimming (`PublishTrimmed`) or NativeAOT, so the self-contained size can't be cut that way. ReadyToRun is untested.

## Network category (D12)

`Get-NetConnectionProfile`: interface `Ethernet`, network "Network 4", **NetworkCategory = Public**, IPv4 Internet. This is the new-network default on Windows 11, as D12 expects. A Private-only firewall rule would not have covered this network. The phone-to-PC test over Wi-Fi was not done.

## D2: Windows-side needs with .NET

"Unverified" means I know it from documentation or memory and did not build or run it here.

| Need | .NET approach | Snag |
|---|---|---|
| HTTPS server + mutual TLS + WebSocket | ASP.NET Core Kestrel via `<FrameworkReference Include="Microsoft.AspNetCore.App"/>`. `ConfigureHttpsDefaults` with `ClientCertificateMode.RequireCertificate`, a custom `ClientCertificateValidation` that checks the pinned device ID, `app.UseWebSockets()`. Peer cert is at `HttpContext.Connection.ClientCertificate`, so no custom accept loop (unlike axum). | Unverified. Self-signed client certs need the custom validation callback. **TLS version:** Kestrel uses Schannel on Windows, and Schannel turns TLS 1.3 on by default only on Windows 11 and Server 2022 or later. On Windows 10 it was experimental at best, so Kestrel there gives TLS 1.2. That conflicts with [protocol.md](../protocol.md) ("TLS 1.3 only"), because [windows.md](../windows.md) targets Windows 10 and 11. The options are to relax the protocol to TLS 1.2+ on .NET, or to drop Windows 10. rustls (the Tauri plan) does TLS 1.3 everywhere. Client certificates over TLS 1.3 with Kestrel are unverified. Adds the ASP.NET runtime to the self-contained size. A framework-dependent build also needs the ASP.NET Core Runtime, which is not part of the Desktop Runtime, so end users would need two runtimes |
| Certificates (P-256, self-signed, SPKI hash) | `CertificateRequest` + `ECDsa.Create(ECCurve.NamedCurves.nistP256)`, `ExportSubjectPublicKeyInfo()`, built in | Windows may need the cert exported and re-imported as PFX for Kestrel to use the key. Unverified |
| Private key encryption | `ProtectedData.Protect(..., DataProtectionScope.CurrentUser)` (DPAPI) | **Verified (presence only, not run).** `System.Security.Cryptography.ProtectedData.dll` ships in `Microsoft.WindowsDesktop.App` 10.x (runtime and reference pack, 10.0.13), so no NuGet package is needed |
| mDNS advertising | No built-in. `Makaretu.Dns.Multicast` (NuGet) or P/Invoke `DnsServiceRegister` in `dnsapi.dll` (Windows 10+) | Unverified. Package maintenance state unknown. The native API avoids a dependency but is more P/Invoke work |
| Clipboard change listener | `AddClipboardFormatListener` on a message-only window (`HwndSource`, `WM_CLIPBOARDUPDATE`). Opt-out formats are readable via `Clipboard.GetDataObject()` | WPF `Clipboard` throws `CLIPBRD_E_CANT_OPEN` under contention, so retry. Unverified |
| Toasts with click actions | `Microsoft.Toolkit.Uwp.Notifications` (`ToastNotificationManagerCompat`), which handles unpackaged apps. Or the Windows App SDK `AppNotificationManager`, which also supports unpackaged apps and is the current Microsoft option. Or WinRT directly with a `net10.0-windows10.0.19041.0` target | Unverified. The toolkit package has had no release since 7.1.3 (Nov 2022), and `ToastNotificationManagerCompat` needs a `-windows10.0.17763.0` or later target framework. Unpackaged apps need an app ID (a Start Menu shortcut or registry entry); the toolkit does this per user. This is the "buttons are impractical?" question in windows.md 1.3, so test it first |
| Tray | `System.Windows.Forms.NotifyIcon` | **Verified.** The WinForms context menu does not follow Windows 11 styling or dark mode. Win11 hides new tray icons in overflow by default (same for any stack) |
| Global hotkey | `RegisterHotKey` P/Invoke on an `HwndSource` (a few lines), or `NHotkey.Wpf` (NuGet) | Unverified. Registration fails if another app owns the combination, so show that in settings |
| Explorer "Send to" | `.lnk` in `%APPDATA%\Microsoft\Windows\SendTo`, created through `IShellLink` COM interop. Single-instance forwarding via named pipe | Unverified. No managed shortcut API. The mutex half is done in the spike, the forwarding is not |
| Autostart | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` via `Microsoft.Win32.Registry` | Per user, no admin. Unverified |
| Firewall rule at install | `netsh advfirewall` or `INetFwPolicy2` COM, run by the installer. WiX has a `FirewallException` element | Needs admin on any stack. Not tested here. Binding a non-loopback port triggers the Windows Firewall prompt |
| Installer | WiX Toolset (MSI, per-machine, with firewall support), or Inno Setup, or Velopack (per-user, no admin, no firewall rule) | Unverified. Which fits depends on whether the firewall rule stays in the installer (D12 and windows.md "Install") |
| SQLite | `Microsoft.Data.Sqlite`, which bundles the native library | Unverified |
| QR rendering | `QRCoder` (NuGet), SVG or bitmap output | Unverified |
| UI | WPF (XAML) | Different language from the TypeScript UI plan. Not a Tauri-style web UI. The XAML in the spike is minimal; richer UI was not tried |

Notes for the comparison:

- Everything above sits inside one language and one runtime. There is no Rust and no separate web UI, and no custom TLS accept loop.
- The cost is size. Even a hello world is 148 MB self-contained, or tiny but tied to a runtime install. The Tauri numbers are in [phase-0-tauri.md](phase-0-tauri.md): a 1.1 MB installer and 1.5 MB idle private working set.
- Idle memory with no window is about 57 MB working set and 14 MB private bytes. The window-open number (128 MB working set) shows WPF windows are heavier than a tray-only process, which is relevant to the "destroy windows on close" rule.

Against [targets.md](../targets.md) (the PC footprint and App size rows):

| Target | Goal | .NET spike | Result |
|---|---|---|---|
| PC footprint (idle) | Under 30 MB active private working set | 8.9 MB private working set, tray only. Measured twice: 62 s after launch in the first run (the Metrics table above), and 63 s after launch in the second, on 2026-10-14 after the review fixes, with the same number | Passes. This is only a hello world with no networking, and the target is measured after 1 h idle, so it will grow |
| App size | About 10 MB or less | 147.6 MB self-contained single-file (0.2 MB framework-dependent, but it needs two runtimes) | Fails badly when self-contained |
