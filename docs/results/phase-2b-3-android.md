# 2B.3 Android: media controls in both directions

Date: 2026-10-17. Android coder (Claude Sonnet 5.5). Not reviewed, **not committed**. `versionName` stays 0.1.1 (`versionCode` 2). Spec: [protocol.md "Media controls: `media.*`"](../protocol.md#media-controls-media) (changelog 57) and its vectors (`protocol/media.json`, the `media-*` cases of `messages.json`); design: [phase-2b-3-design.md](../phases/phase-2b-3-design.md) section 4. Description of the code as built: [android.md](../android.md) ("Media controls"). User decisions taken: (1) phone to PC media is **one switch for all apps, off by default**; (2) Kin's session for PC media reports **`playing`** while the PC plays; (3) the phone's **volume keys for the PC are off by default**, behind a switch.

## 3. Spec and design points found (not edited: protocol.md, protocol/ and the design are not mine)

1. **`rateMilli` is not tied to the state.** The design's mapping said speed only while playing; the vectors (`androidMap[]`) say `round(speed x 1000)` cut to 0..4,000 whatever the state, a negative speed is 0 (a paused session at speed 0 sends 0). Followed the vectors.
2. **`toggle` is `ACTION_PLAY_PAUSE` alone in `toAndroid[]`** (vectors: 512), not play + pause + toggle as I first wrote. System UI draws the play/pause button from the play and pause bits, so the **session** (not the vectors' `maskOf`) adds `ACTION_PLAY | ACTION_PAUSE` when only `toggle` is offered (`sessionMaskOf`), and a press is then sent as the `toggle` the source listed.
3. **Images after a `media.clear`.** The spec says "once per hash per connection". A viewer may well drop its pictures with the session, so the sender **forgets what it sent after a `media.clear` it sent** (share off, no session) and the next session sends the art again (a few KiB). The same after a viewer's `show: false`. If the desktop keeps images across a clear this is harmless; if it drops them it is needed.
4. **Turning the share switch on with no access** opens the system's notification-access screen and shows the 2B.2 restricted-setting steps in the card, instead of opening the 2B.2 mirroring wizard (that wizard also asks which apps to mirror, which media does not need). The status says `access: missing` until access is there.
5. **The status that says `access: granted` can lag on Android 10:** after the grant the system binds the listener several seconds to a minute later, and the update follows that binding or the user coming back to Settings (`refreshAccess`). Not a problem for a user (the card re-reads on return); the verify script waits 60 s there.
6. **A viewer that has nothing for `sid` of a command** (`media.cmd` with a `sid` that isn't the active one) gets `stale`, but a `sid` of a session that never existed and an old one look the same; fine by the spec.
7. **Two sessions of one app** (same package, same `sid`) count as one: the first in the system's order is used. Not in the design; needed because `sid` is per app.
8. `onAudioInfoChanged` takes a non-null `PlaybackInfo` in the API 37 stubs (compile error found first time); `onPlaybackStateChanged` and `onMetadataChanged` are nullable.
9. **Volume changes made on the phone itself are not watched** (design 4.4): the PC's slider is as fresh as the last `media.state` or `media.volume`. `media.volume` goes out only after a PC command or with the next state.
10. The app label of a player Kin can't see (no launcher entry; `<queries>` lists only launcher apps) falls back to the session tag (API 30+) and then to "Media". Not exercised (the emulator's only player is Kin's own).
