## The four spec changes

- **`sensitive`:** the sender sets it when the clip's `ClipDescription` extras have `EXTRA_IS_SENSITIVE` (API 33+; the clipboard send path and a share whose clip data carries it) and writes the field only when true. A received `sensitive` text is put on the clipboard marked sensitive, shown as "Text from <PC>" with **no preview and no Open action** (the vectors say so too), and nothing about it is logged, not even length or hash. A `text` with a non-boolean `sensitive` is `bad_request`. `protocol/IncomingHandler.kt`, `clipboard/ClipboardPort.kt`, `link/Notifications.kt`, `link/OutgoingSender.kt`. Tests: `text-sensitive-*` cases of `messages.json` (`MessageVectorsTest`), `receiver[]` and the phone cases of `sensitiveSender[]` of `text-rules.json` (`TextAndUrlVectorsTest`), `TextFlowTest` (flag on the wire, absent when false, nothing in the log).
- **128 KiB threshold:** `TextRules.plan` (`protocol/TextRules.kt`): over 128 KiB of wire-form UTF-8 goes as a `.txt` file through the upload (name `Kin text <date time>.txt`, `text/plain`, LF, no BOM); a sensitive text over 128 KiB is not sent at all (the desktop agent's addition to the spec, the `senderSize[]` cases). The 1 MiB frame check stays as the receiver's hard limit. The old "too long for now" tests are replaced.
- **Line ends:** `Frames.wireText` (CRLF to LF in one pass, lone CR stays). A received text is kept as received. Loop-guard hashes are of the wire form: `notePeerSet` hashes a received text as received (no second conversion), `isEcho` converts a clipboard text first (`ClipboardGuard`). `lineEndings[]` of `text-rules.json`.
- **Openable URL rule:** `UrlRules` rewritten to the rule (explicit White_Space list, split at the **first** `:`, port 1-65535 with leading zeros allowed, bare `:` refused, host not only dots, `[IPv6]` non-empty, 8 KiB). `urls.json` (106 cases) passes.

## R5: does passing the URIs to the service keep access? Yes (and one more thing it found)

Test rig: a second app, `android/share-source/` (a throwaway; not in the build or the release), with a provider that is **not exported**, so Kin can read its files only through the grant on the share intent, like a gallery. It shares N files with `FLAG_GRANT_READ_URI_PERMISSION` and can kill itself half a second later.

- **With the grant to the service:** files of 40 to 60 MB were uploaded one after another (the second file of a batch is opened tens of seconds after `ShareActivity` had finished, and after the source app had died and been restarted by Android); all read fine. (Also on API 29, 3 x 3 MB.)
- **Control (debug switch `files/debug-no-grant`, the share doesn't hand the URIs to the service):** the upload failed at its first source check, `source_lost: Kin can't read shared-1.bin any more. Share it again.` So the step is necessary, and the failure message is the one android.md asks for.
- **Even a killed Kin kept access:** in the first run Android killed Kin ("depends on provider ... in dying proc") when the sending app died; the sticky service restart resumed the `active` upload from the Room row and read the original URI, so the grant survives a process death too (the service record outlives the process).
- **The kill itself is a bug that was fixed.** `ContentResolver.openFileDescriptor` (and `getType`) keep a *stable* provider reference while the descriptor is open, and Android kills the client when the provider's process dies. A gallery app dying during a 2 GB upload would have killed Kin. Shared files are now read through `acquireUnstableContentProviderClient` and the client is closed at once; a re-run with the source dying mid-upload left Kin alive (same pid) and the upload finished (`transfer/AndroidSourceFiles.kt`).
- Not tested: a source that is force-stopped (not killed), the phone rebooting with a queued transfer (the cached copies cover small files; a large one says "Share it again"), Google Photos or any real gallery.

Real resumes confirmed it end to end: a dropped `GET` after 500,000 or 700,000 bytes, then `Range: bytes=N-`, and the SHA-256 of the saved file on the phone (`adb shell sha256sum`) equals the PC's, on both. The junk was removed with the new debug command `DELETE_RECEIVED`.

## Foreground service type and Android 14+ transfers: decision

Transfers run inside the existing `connectedDevice` `LinkService`. No `dataSync` type and no user-initiated data transfer job. Why: the service is already running and keeps the process in the foreground; `connectedDevice` has no time limit while `dataSync` gets about 6 hours per 24 on Android 15 and can't start from boot; `dataSync` needs one more permission and the task says no new ones; a UIDT job would be a second mechanism, driven by a network constraint instead of "the PC is on this Wi-Fi", only on API 34+ while minSdk is 29. A 2 GB video over Wi-Fi takes minutes. If the service is killed, the Room rows are `active` and resume at the next connect. Full text in android.md. This should be re-checked on a real Android 14/15 phone with the battery settings (not possible on the emulator).

## Spec ambiguities and decisions

1. **Free space on the phone:** the PC has no reserve; the phone uses the same rule (`needed > free` is `disk_full`). protocol.md doesn't say. The check is on the sum of the offer's sizes, before the ack.
2. **A refused `offer`** is answered with `error` (`disk_full`, `ref` = the offer id) and that response is remembered like an ack (a repeated offer gets the same `error`).
3. **A complete file at `POST`** (offset = size): the spec says it is complete but not whether the PC has finalised it, and `upload-lost-final-response` finishes with an empty `PUT`. The phone always sends the `PUT` for every file (empty body when complete), which is idempotent. A 0-byte file always gets its own `PUT`.
4. **Transfer IDs must be new.** An `offer` whose ID was seen in the last 24 hours is acked and ignored (de-duplication), which is right but a trap for tools that reuse IDs (the fake PC commands, an integration script).
5. **`Content-Length` of a `GET` that isn't the expected size** fails the file (`internal`) instead of being trusted. Spec silent.
6. **The `upload-source-changed...` vector** has a stale `PUT` to the old ID as its fifth step. It shows the server's 404; the phone never sends it, so the replay test skips it. The `upload-offset-mismatch-recovery` and `upload-lost-final-response` sequences start with a `PUT` and no `POST`, which the phone never does, so those two are tested with equivalent explicit flows, not replayed.
7. **"Changed" means size or modified time**, and the modified time is only compared when the provider reports one (some don't). A file that changes without changing size or time can't be noticed.
8. **Waiting limits are mine:** a moving transfer waits 15 minutes for the PC, then goes back to `queued`; 5 attempts that move no bytes fail it; 5 offset mismatches in a row fail it.
9. **The `.txt` name** for long text is `Kin text <yyyy-MM-dd HH.mm.ss>.txt` (the spec's `Text.txt` is only an example). The content is the wire form (LF), without a BOM.
10. **Sensitive text with a link:** no Open action. The vectors agree; the text of the task didn't say.
11. **`complete` goes after the transfer is marked done** and the notification is shown; it is re-sent with the same ID up to 3 times (30 s waits) and not stored beyond that (the persistent queue is 1.4).
12. **Open** opens the first file for a batch, Share shares them all. A better "open the folder" can come with the history screen.
13. **MediaStore's SIZE column** can be stale for media it can't scan (a fake video); not a spec matter.
