# Phase 2B.2 integration: phone notifications on the PC, end to end

Date: 2026-10-17, integration/test agent (Sonnet 5.5). Nothing is committed. Contract: [phase-2b-2-design.md](../phases/phase-2b-2-design.md), [protocol.md](../protocol.md) "Notifications" (changelog 56); the two coders' own results: [phase-2b-2-desktop.md](phase-2b-2-desktop.md), [phase-2b-2-android.md](phase-2b-2-android.md). No product code was touched. The script is [tools/e2e-2b-2.ps1](../../tools/e2e-2b-2.ps1) (and a throwaway test app, `tools/e2e-2b-2/bankdemo/`).

## Result in one paragraph

**Scenarios 1 to 9 pass.** The final script ran once, whole, on `kin_api37` against the real release `Kin.exe` as a dev Kin beside the installed one: **106 checks, 0 failed** (including the 100 s later look at the registry). The Android 10 pass on `kin_api29` (S1 to S5): **89 checks, 0 failed** (then `-Only S4` once more after a note was reworded: 22, 0 failed). Scenario 9 (the fixed 2B.1 S6) **failed twice on its first runs, and both times it was the script's own model of the URL rule, stale since changelog 55** (not the product); fixed, then 22 of 22. **No product bug found.** What I found are four observations (section 4) and several test-script mistakes of mine (section 6). Not covered, because it can't be from a script: a person's click on a real toast, Windows 10, a real phone (section 7).

## 1. How it ran

* **PC:** the release `Kin.exe` (built after the last 2B.2 change) copied to a temp folder, with its own data directory, `--dev-bind 127.0.0.1`, `--dev-toast-quiet` (every toast goes to the Action Center, no popup, no sound), no window, `"mirrorNotifications": true`, no hotkey, no automatic clipboard sync. Its identity was always a dev one (`app.kinrelay.desktop.dev-<key>.phone` and a CLSID from the key); the installed Kin (PID 25796) was never started, stopped or restarted and `app.kinrelay.desktop.phone` was never written.
* **Phone:** the real debug APK on `kin_api37` and `kin_api29`, paired to that dev Kin over the real TLS link; listener access given with `cmd notification allow_listener`.
* **"Clicks":** what the shell does and nothing else: `toast_probe activate <clsid> <aumid> <arguments> reply=...` is COM `CoCreateInstance` of the registered class and `Activate`, with the arguments **read back from the toast Windows holds** (so the test uses what the shell would). The X is `Kin.exe --dev-toast dismiss` (the function the `Dismissed(UserCanceled)` handler calls). No input injection anywhere.
* **What Windows holds** is read with `toast_probe history` (tag, group, buttons, input box, private form, and the toast XML in memory only, to look for the test texts).
* **Notifications from:** the debug "Mirror test" posts (Kin's own `kin_debug_mirror` channel), `cmd notification post` (package `com.android.shell`, incl. `-S messaging`/`-S media`), and a **throwaway test app "Demo Bank"** (`test.bank.demo`, built by `tools/e2e-2b-2/bankdemo/build.ps1` with the SDK's `javac`/`d8`/`aapt2`/`apksigner` and a throwaway key; never Kin's keystore) that posts what the shell can't: call, alarm, ongoing, group summary and child, secret, media, transport, progress, and a **real foreground service** (API 34+). Its package name has the whole word `bank`, so the phone's `AppCatalog` flags it as likely sensitive (scenario 6). It is uninstalled at the end.
* **Phone log** (`logcat`, saved to a file before every scenario and cleared) and the **phone's app data** (one `tar` of everything through `run-as`, read as bytes) are grepped at the end; so is every file of the dev Kin's data directory.

## 4. Product observations (none blocks 0.2.0; for the reviewer / TESTING.md)

1. **`status.json` counters lag until something else happens** (low, `desktop/src-tauri/src/mirror/mod.rs:256` `count()` never emits `Event::StateChanged`, so e.g. `dismissals_sent` (line 587) shows in `status.json` only when the next state change rewrites it: seen as "1 to 1" 18 s after a dismissal and "2" at the next toast). The Settings window reads the same state. The checks of this run use the Kin log (`notif.dismiss sent to device`) where it matters. Not a functional bug.
2. **A cancel through the listener is not echoed** (by design, 4.4: reasons 10 and 11 are Kin's own PC-dismiss), so `MIRROR_CLEAR_ALL`, and any other listener app cancelling, leaves the PC's toasts until the next `notif.sync` or expiry. The user's "Clear all" in the shade is reason 3 and is echoed; the real shade could not be driven from a script (no input injection). For the test it means the script removes the dev identity's toasts with `toast_probe clear` (Kin's ledger is stale afterwards, which, I think, is why one flood run showed "over-cap removed +2": probably stale ledger entries from the earlier scenarios counted towards the cap of 30; an artifact of the test, not seen in the last run).
3. **A group summary with no child loses `FLAG_GROUP_SUMMARY`** (Android 17 strips it: `flags=AUTO_CANCEL groupKey=demo_group` in `dumpsys`), so the filter's summary rule (`MirrorFilter.kt:60`) does not see it and it is mirrored as an ordinary notification. A real summary has children and Android cancels it with the last one, so this is rare; found because my first test posted a summary alone.
4. **Android 10/11 "Open"**: see the comment on spec point 4.

## 5. Comments on the Android coder's four spec points (phase-2b-2-android.md section 2)

1. **A sensitive post needs a body** (the phone sends the app name as `title`). *Observed:* works end to end. The flagged Demo Bank post (title `ZQBankTitle`, text `ZQBankText`) arrived, and the toast Windows holds is the private form with only "Demo Bank"; neither string is in the toast XML, the Kin log, the DB or the phone's data. Nothing leaks through the placeholder title. A spec change (let a `sensitive` post be empty) would be tidier but is not needed.
2. **OTP "at least 10 characters closer" vs "more than 10"**. *Observed:* with `> 10`, "Verification code 846201 or 517308" gives **no** Copy button, which is the design's own negative; a single code next to a keyword gives `Copy 731946`; a promo code and a number with no keyword give none (API 37 and API 29 the same). So the wording of design 4.10 should say "**more than** 10 characters closer".
3. **`label` of a reply is the hint**. *Observed:* with the debug test's hint "Reply" the PC sent that as the label and the phone **acked**, the text arrived exactly (hash equal). Not exercised end to end: a reply with **no** hint, or a hint over 30 characters (needs an un-flagged third-party app with such a RemoteInput; the Kin debug test always has the label "Reply"). The phone compares both cut to 30, so they stay equal; the unit tests cover it.
4. **Android 10/11: "Open" is offered and (it was feared) silently fails.** *Observed on `kin_api29`:* the toast had **3 buttons** (Send, Mark as read, **Open**). Pressing Open through the COM class got an `ack`, **no "background activity launch blocked" line, and the resumed activity went from the launcher to Kin's own `MainActivity`**: the activity **was started**. So at least for an activity `PendingIntent` that Kin itself created (the debug test; Kin has a foreground service and a bound listener) Android 10 does not block it. What happens for a third-party app's own activity `PendingIntent` can't be tested without a real app (WhatsApp, Telegram, Signal, Google Messages: TESTING.md): it may open the app on the phone's screen, which a user of "a button on my PC" may not expect. On API 37 Open is not offered (`PendingIntent.isActivity()` exists there). The 2B.2 text "pressing it is acked while Android silently blocks the start" should say "may open the app on the phone or be blocked; the PC cannot know".

## 6. Mistakes found in the tests (fixed; for whoever reuses them)

* `tools/e2e-2b-1.ps1` S6 `Test-OpenableSpec`: stale since changelog 55 (above). Also its table shows `âš ` for the warning sign when the output is captured in a non-UTF-8 console: only the console's code page.
* `dumpsys notification` on API 29 prints `appImportanceLocked=...` straight after the key (no space): a regex that took `key=(0\|[^\s:]+)` built a wrong `nid` and every toast looked "missing" on the first Android 10 run.
* A 2-byte marker (`ZQ`) in a grep of 235 KB of binary data is a false positive (expected about 3 hits); every marker is now at least 6 characters.
* `cmd notification post` can't make ongoing, category, FGS or summary notifications and `FLAG_FOREGROUND_SERVICE` set by a plain app is stripped by Android (the first "FGS" test posted an ordinary notification): hence a real foreground service in the helper app (API 34+; on Android 10 the check is skipped with a note).
* Every `toast_probe` call is retried (a transient "file in use" when starting an exe); `status.json` is not trusted for "nothing was sent" checks (observation 1).

## 7. Not covered (can't be, or not by a script)

* A **person's click** on a toast (popup, Action Center, after a Kin restart, Kin not running), the X on a popup and clearing from the Action Center, the look of a toast, Focus assist: R21 and the manual checklist of phase-2b-2-desktop.md stay open. Windows 10.
* The **Android 15+ redaction itself**: the emulator image has System Intelligence but does not redact (the Android coder's finding). "Code hidden by Android" was checked with a post whose text *is* the placeholder.
* The **restricted-settings** flow (`adb install` is a session install), OEM listener unbinding, battery, Doze, a real phone's WebSocket after a deep sleep.
* Real **messaging apps'** reply and button `PendingIntent`s, hint-less replies, contact `Person` URIs.
* The PC's own rate limit through a real phone (section 2, row 8), the changed-clipboard variant of Copy (cargo tests only), and the link from Windows' Action Center store (R23).
