## Result

**The full script passes: 132 of 132 checks on `kin_api37`, and 123 of 123 on `kin_api29`** (the API 29 run skips the three checks that have no shell mechanism there, see "Not testable here"). The regressions on the new build pass: `e2e-2b-3 -Only S1,S2` 63/63, `e2e-2b-2 -Only S1` 41/41, `e2e-1-3 -Only S1,S4` 34/34 (all kin_api37). **No product bug was found.** There are six findings and observations (section 4); none blocks.

The path to a green run was not straight, and the failures were all in the script, not the product: a `Pc-Wait` helper whose parameter hid the outer one, `sc` (the alias of `Set-Content`) shadowing a function called `SC`, a status read before an asynchronous command had finished, a pairing URL file left over from an earlier pairing, and a wrong expectation about how the PC notices a dead Wi-Fi link (see 4.5). Each was fixed in `tools/e2e-2b-4.ps1` and the whole thing was run again.

One run was **mislabelled** and is worth knowing about: `tools\emulator\start.ps1` reuses an emulator that is already running, so a "kin_api37" run started while `kin_api29` was up ran on API 29. It still passed in full (that is the 123/123 run). The script now throws if the running AVD is not the one asked for, and the API 37 run was repeated after `stop.ps1 -All`.

## 4. Findings and observations (no product bug)

1. **The Cancel of the screenshot hold is hidden in the shade.** The hold is on the silent *File transfers* channel (by design), and Android groups it under Kin's own persistent notification: in the shade it reads "Sending screenshot to DESK-PC in 5 s" with a "2" expander and **no visible Cancel until the group is expanded** (`08-s4-screenshot-hold-notification.png`). With 5 s to act, a user has to open the shade, notice it and expand it. Not a bug (the design says low importance and the real-phone item is already in TESTING.md), but the Cancel is harder to reach than the design text suggests. If it is a problem on a real phone: give the hold its own group key, or a heads-up. (The script cancels through `SHOTS_CANCEL`; tapping the action is unproven.)
2. **Do Not Disturb "total silence": the phone saves 0 and does not raise the volume.** `getStreamVolume(STREAM_ALARM)` is 0 under that filter, so `savedAlarmIndex=0` and the alarm index stays 6. It is restored to 6 after the stop and after DND goes off. Harmless on this image, but the saved 0 would be wrong on a phone where the raise still works under total silence. Worth a look at `RingController` (`AndroidRingPorts`), not a blocker.
3. **The PC cannot restart a ring, so review fix B2 and the phone's 3-per-60-s limit cannot be exercised end to end.** `ring.rs:93` refuses a press while a ring is `Requested` or `Ringing` (`AlreadyRinging`), so the phone only ever sees a second `ring.start` if the PC lost the stop status. **B2 therefore stays verified only by `RingMachineTest` and the `ring[]` vectors**; what the script shows is that a second press changes nothing (`started 1`) and the Stop notification is there at 25 s. Driving it would need a fake PC (the repo has only a fake phone).
4. **The app writes no count line of its own** (design 5.8 says logs hold `presence: sent N...`, `ring: ...`, `shots: ...`): those lines exist only as the debug `CMD` echoes (`debugLine()`). Nothing leaks; the documentation and the code disagree. Either the doc should say "debug builds only" or the counts should be logged once at stop.
5. **After Wi-Fi goes off the PC still shows the phone as connected** (status `phone_connected`) until its ping timeout (about 240 s: R30/R41). The phone knows at once. So "the PC sees the phone go away" cannot be waited for with a short timeout; the script waits on the phone's own link state. Consequence seen in S5b: a PC-side send to that phone is queued and unlinking turns it into `peer_changed`, as intended.
6. **`cmd appops set <pkg> POST_NOTIFICATION deny` does not change what the app sees on API 37** (`SHOTS_STATE notifications=true`), and a screenshot was then sent. Revoking the runtime permission (`pm revoke ... POST_NOTIFICATIONS`) is the real mechanism and gives the B3 behaviour (`notifications=false`, no observer, nothing sent). I took the appops result to be a bad test lever (the system gates `areNotificationsEnabled` on the permission, not the app op), not a product bug; if a real phone with notifications blocked in Settings still sends, TESTING.md item 1 covers it.

## 5. Not testable here (and what covers it)

- **B2 restart** and the **3 starts per 60 s / `rate_limited`**: unit tests only (finding 3).
- **DND total silence on API 29**: `cmd notification set_dnd` is API 30+ and `settings put global zen_mode` does not change the interruption filter; checked on API 37 only (a Note in the script).
- **B3 on API 29**: no `POST_NOTIFICATIONS` permission there; unit test and the real-phone list.
- **`FSI denied` on API 29**: the restriction is Android 14+; not applicable.
- **Audible ring, vibration, silent/vibrate/Priority-only modes, Bluetooth, Doze; the Stop screen on a Pixel/Samsung and over DND; the tile on a real lock screen; the photo dialog and "Select photos"; EXIF/GPS; a laptop battery; a power cut (R38); the tray menu's look; sleep/resume with a pause that ends while asleep**: the real-hardware list in `docs/TESTING.md`. The PC's tray menu items cannot be clicked without OS input, so the CLI (`--pause`, `--ring`, `--ring-stop`) stands for them and the tooltip/status text are checked in `status.json`.
- **The 08:00 rule** is a unit test (`pauseUntil[]`); the script only checks "2 to 26 hours ahead".
- **`saver`** (power-saving flag) in `presence`: unit test only.
- The S3 screen (phone paused) showed the launcher, not Kin's Pause card (the tile tap leaves the phone on the home screen), so it is not kept; the pause itself is asserted from `PAUSE_STATE` and the PC. Other captures that showed only the launcher (S1 phone battery, S2 ring after wake with FSI denied, the FSI-deny spike) were not kept either.
